# Нагрузочная проверка (04.10.2026)

Сколько сотрудников выдержит kronto, что кончается первым и что
поменять до выдачи боевым клиентам. Мерили в песочнице разработки, а не
на стенде, с имитацией модели — что это значит для цифр, в §2 и §7.

## 1. Коротко

- **Сам сервер — не узкое место.** Один процесс API на четырёх ядрах
  отвечает примерно на 30 вопросов в секунду, упор — одно ядро процесса
  Python (§3). Это в десять раз больше, чем пропускает квота Яндекса.
- **Потолок — квоты Yandex Cloud, общие для всех компаний.** Эмбеддинги
  вопросов — 3 в секунду (доля из 10 на каталог, остальное — индексации),
  генерация — 8 одновременных ответов на процесс (10 на каталог). При
  настоящей модели (Alice AI LLM Flash, ответ 0,7–0,85 с по медиане по
  замерам ML) первыми кончаются эмбеддинги: **около 3 вопросов в секунду
  на всю платформу**, ~10 тыс. в час.
- **Нашли и исправили два дефекта** (§4).
  1. Ответ держал соединение с базой, пока ждал модель и пока она писала.
     При 200 одновременно работающих сотрудниках пул соединений кончался
     и вставал весь API: открыть kronto — 2,7 с по медиане, колокольчик —
     14 с; при 400 — 11 с и 37 % вопросов с ошибкой. После исправления —
     0,1 с и 0,4 с, ошибок «сбой» нет.
  2. Поток ответа мог висеть вечно: если и ошибку не удалось сохранить,
     сервер так и слал «пинг», а сотрудник смотрел на «Ищу в документах».
- **Перегрузка теперь — быстрый понятный отказ**, а не зависание: «Сейчас
  очень много вопросов. Попробуйте через минуту» (код `busy`; в
  `/faq/ask` — 503 с `Retry-After: 30`).
- **Всплеск «все спросили разом»** раньше пропускал ~16 вопросов, дальше
  — отказ. Очередь к квоте эмбеддингов увеличена с 5 до 10 с: 30 вопросов
  разом проходят целиком, из 60 — 34 (§5).
- **Большая компания** (§6): до 20 тыс. фрагментов поиск почти не виден
  в ответе (0,15 с); на 100 тыс. — 0,28 с и потолок компании ~6 ответов
  в секунду, всё ещё выше квоты. Почему дорого — разобрано, исправлять
  вместе с ML, когда появится компания больше ~50 тыс. фрагментов.
- **Что это в людях.** В тесте каждый сотрудник спрашивал раз в
  полминуты без перерыва — это в десятки раз чаще жизни. Если считать
  10 вопросов в день на человека (допущение, живой статистики нет) и пик
  втрое выше среднего за 8 часов, 3 вопроса в секунду хватает примерно на
  3 тыс. активных сотрудников на всю платформу. Дальше — повышать квоту
  у Яндекса или делить компании по каталогам (§8).

## 2. Как мерили

- **Где.** Песочница разработки: 4 ядра, 16 ГБ, Postgres 16 + pgvector и
  Redis локально, **один процесс uvicorn** — как в контейнере стенда,
  плюс воркер. Не стенд: на стенде те же 4 vCPU, но 8 ГБ, Docker, nginx с
  TLS спереди, реранкер и мониторинг рядом. Логи — цветной вывод
  разработки (дороже JSON боевого режима): цифры сервера скорее
  занижены.
- **Компания.** `tools/loadtest/seed.py`: компания `loadtest`, 1 000
  сотрудников и администратор. Документы — корпус проверки стенда
  (16 файлов, 365 фрагментов), загружены через API и проиндексированы
  воркером как обычно (`run.py corpus`).
- **Вопросы** — из того же корпуса (`tests/fixtures/stand_quality`):
  одиночные и пары «вопрос — уточнение».
- **Вход не нагружали**: токены доступа генератор выпускает сам ключом
  `SECRET_KEY` (сессия в токене случайная — проверка выхода из системы
  идёт как обычно).
- **Модель — имитация** (`LLM_PROVIDER=fake`) в двух режимах.
  - *Сервер*: модель и эмбеддинги отвечают мгновенно — видно, сколько
    тянет сам сервер.
  - *Квоты*: `LLM_FAKE_LATENCY_MS=1000` до первого слова, ответ печатается
    по 100 мс на слово, `LLM_FAKE_QUOTAS=true` включает те же лимиты, что
    у настоящей модели: семафор генерации `LLM_MAX_CONCURRENCY=8` и темп
    эмбеддингов вопросов `EMBEDDING_QUERY_RPS=3`. Это медленнее
    настоящей Flash — оценка с запасом.
- **Сценарии** (`tools/loadtest/run.py`).
  - `capacity` — N вопросов одновременно без пауз: пропускная способность.
  - `burst` — N сотрудников нажимают «Спросить» в одну секунду.
  - `cycle` — сотрудник как в жизни, только намного чаще: открыл kronto
    (профиль, диалоги, уведомления, подсказки, первые шаги — разом, как
    браузер), вопрос, пауза 20–40 с, уточнение, пауза…; колокольчик — раз
    в минуту. 4 минуты на уровень, сотрудники приходят вразнобой в первые
    40 с.
- **Что пишется.** Время до первого слова (событие `delta`) и до конца
  ответа (`done`), коды ошибок, процессор API и Postgres раз в секунду,
  число соединений к базе (`pg_stat_activity`).

Повторить:

```bash
# Postgres и Redis локально, миграции применены; переменные — как для разработки
OWNER_DATABASE_URL=… uv run python tools/loadtest/seed.py --users 1000 --out users.json
uv run python tools/loadtest/run.py corpus --users-file users.json
LLM_FAKE_LATENCY_MS=1000 LLM_FAKE_STREAM_DELAY_MS=100 LLM_FAKE_QUOTAS=true uvicorn corp_ed.main:app
uv run python tools/loadtest/run.py cycle --users-file users.json --levels 50,100,200,400 --duration 240
```

Только локально: у учёток компании `loadtest` одинаковый пароль, а
токены выпускаются без входа.

## 3. Сервер без квот

**A. Пропускная способность** (`capacity`, 60 с на уровень; до
исправления §4 — после него те же ~30 ответов в секунду, §6).

| Одновременно | Ответов в секунду | p50 | p95 |
|---|---|---|---|
| 5 | 33,6 | 0,14 с | 0,19 с |
| 10 | 32,1 | 0,29 с | 0,42 с |
| 25 | 31,4 | 0,77 с | 1,04 с |
| 50 | 29,5 | 1,63 с | 2,45 с |
| 100 | 28,2 | 3,45 с | 5,14 с |

Процессор API — ~100 % (одно ядро: процесс Python однопоточный),
Postgres — ~60 % одного ядра, соединений к базе не больше 20. Ошибок нет.
Больше одновременных — та же пропускная способность, дольше очередь.

**B. Всплеск** (`burst`, все в одну секунду): 50 / 100 / 200 вопросов —
последний ответ через 1,9 / 3,6 / 6,1 с, ошибок нет.

**Вывод.** Сервер упирается в одно ядро процесса API, база недогружена.
Расти дальше — второй процесс uvicorn (`--workers 2`), но тогда семафор
генерации делится вручную (RISKS №20). Пока квота пропускает 3 вопроса в
секунду, это не нужно.

## 4. С квотами: цикл сотрудников

**C. До исправления.**

| Сотрудников | Открыть kronto p50 / p95 | Колокольчик p50 | Вопрос p50 / p95 | Принято вопросов в секунду | Ошибки вопросов |
|---|---|---|---|---|---|
| 50 | 0,08 / 0,21 с | 0,01 с | 1,8 / 6,4 с | 0,9 | 0 |
| 100 | 0,08 / 0,36 с | 0,02 с | 3,3 / 7,4 с | 1,8 | 0 |
| 200 | 2,7 / 9,7 с | 14 с | 35 / 38 с | 1,9 | 2 из 588 |
| 400 | 11 / 25–34 с | 14 с | 42 / 56 с | ~2,7 ¹ | 416 из 1 114 (37 %) |

¹ Уровень 400 завис: три потока ответа не закончились никогда, прогон
закрыт принудительно через 30 минут; число в секунду пересчитано на
4 минуты работы. Среди ошибок: 329 «сбой» в потоке, 79 ответов 500,
5 оборванных соединений и эти 3 зависших.

**Причина.** В логе API — 571 раз «QueuePool limit of size 5 overflow 10
reached, connection timed out, timeout 30». Ответ в чате открывал
транзакцию чтения (кредиты, компания, словарь, поиск) и держал её — а с
ней соединение — пока ждал места в очереди к модели и пока модель
писала. 15 соединений пула (5 + 10 по умолчанию) заняли ответы, ждущие
модель; остальные запросы — профиль, колокольчик, список диалогов — ждали
соединение по 30 с и падали с 500. Сами ответы, не дождавшись соединения
для записи, уходили в «сбой».

**Исправление** (`FaqService._release`). До модели база только читается,
поэтому перед каждым внешним вызовом — переписывание вопроса, эмбеддинг,
реранкер, ответ — транзакция чтения закрывается и соединение
возвращается в пул; следующий запрос начинает новую с тем же тенантом
(RLS ставится в начале каждой транзакции). Запись журнала и сообщения —
по-прежнему одна транзакция после ответа. Увеличить пул — не решение:
обрыв просто сдвинулся бы на большее число сотрудников.

**Второй дефект — вечный поток.** 425 ответов в логе ушли в «сбой», а
клиент получил 422 события «сбой»: три задачи ответа упали, когда и запись
ошибки не получила соединение, и не отправили потоку ничего. Поток ждал
итога, раз в 15 с слал «пинг», и соединение жило, пока API не убили.
Теперь `ChatGenerator.run` всегда отправляет итог: если не сохранилась даже
ошибка — «сбой» без сообщения, интерфейс перечитает диалог, а сообщение
станет «прерван» через 10 минут, как любое недописанное.

**C. После исправления.**

| Сотрудников | Открыть kronto p50 / p95 | Колокольчик p50 / p95 | Вопрос p50 / p95 | Принято в секунду (вопросы + уточнения) | Отказ «busy» |
|---|---|---|---|---|---|
| 200 | 0,1 / 0,4 с | 0,01 / 0,03 с | 6,7 / 11,4 с | 2,1 + 0,5 | 47 % |
| 400 | 0,4 / 0,9 с | 0,01 / 0,04 с | 6,8 / 11,3 с | 2,4 + 0,2 | 75 % |

Ошибок «сбой», 500 и зависших потоков — ноль; пул не кончался ни разу.
Соединений к базе — не больше 20 (15 API + воркер); долгих открытых
транзакций нет (`pg_stat_activity` раз в 2 с: «idle in transaction» —
только короткие окна внутри обычных запросов, пик 15 при входе 400
человек разом).

**Почему столько отказов.** Сотрудник в тесте спрашивает раз в ~37 с:
200 человек — ~5,4 вопроса в секунду, а доля квоты эмбеддингов — 3.
Принимается ~2,6 в секунду вместе с уточнениями — почти вся доля,
остальное — быстрый отказ, а не очередь на минуты. Ответы, которые приняты,
приходят за те же 6–11 с при 200 и при 400 сотрудниках: квота защищает
тех, кого пустила.

## 5. С квотами: всплеск

**D.** N сотрудников нажимают «Спросить» в одну секунду.

| Одновременно | Ожидание слота до 5 с: принято / отказ | p50 / p95 принятых | Ожидание до 10 с: принято / отказ | p50 / p95 принятых |
|---|---|---|---|---|
| 15 | 15 / 0 | 4,7 / 6,8 с | 15 / 0 | 4,7 / 7,6 с |
| 30 | 17 / 13 | 5,2 / 7,2 с | 30 / 0 | 7,1 / 11,6 с |
| 60 | 18 / 42 | 5,1 / 8,1 с | 34 / 26 | 8,1 / 12,9 с |

Эмбеддинг вопроса ждёт свой слот в доле квоты не дольше
`QUERY_MAX_WAIT`; при 3 слотах в секунду за 5 с проходит ~16 вопросов.
Показ пилоту, где 30 человек спрашивают по команде, — почти половина
получила бы «очень много вопросов». Ожидание увеличено до 10 с
(`main.py`): всплеск в 30 вопросов проходит целиком, из 60 — 34. Цена — при
длительной перегрузке принятые ждут слота до 10 с, а не до 5; такая
перегрузка (3 вопроса в секунду без перерыва) далеко за реальным спросом
пилота.

## 6. Большая компания

**E.** Индекса по вектору нет (RISKS №27): поиск считает расстояние до
каждого фрагмента компании и сортирует. `tools/loadtest/big.py` добавляет
компании синтетические документы — векторы случайные, текст-заглушка
длиной с настоящий фрагмент. Модель мгновенная: разница с базой — цена
поиска. 50 фрагментов на документ (~20 страниц): 100 тыс. фрагментов —
это ~2 000 документов, ~40 тыс. страниц.

| Фрагментов у компании | Один сотрудник подряд: ответов/с, p50 | 10 одновременно: ответов/с | p50 / p95 | Postgres, ядер |
|---|---|---|---|---|
| 365 (корпус) | 15,5 — 0,06 с | 30,5 | 0,30 / 0,44 с | 0,7 |
| 2 000 | 10,8 — 0,09 с | 25,5 | 0,37 / 0,54 с | 1,4 |
| 20 000 | 6,3 — 0,15 с | 11,7 | 0,84 / 1,06 с | 1,6 |
| 100 000 | 3,4 — 0,28 с | 6,0 | 0,86 / 4,6 с | 1,2 |

Строка 365 — после исправлений §4 (с ними пропускная способность та же,
что в A: 30,5 и 30,8 ответа в секунду при 10 и 25 одновременных). Строка
100 тыс. — повтор после `VACUUM ANALYZE`: первый прогон дал то же.
При 100 тыс. в число соединений к базе попадают параллельные процессы
Postgres — отсюда 22 при пуле 15.

**Что видно.** До 20 тыс. фрагментов (~8 тыс. страниц) поиск почти
незаметен в ответе. На 100 тыс. один вопрос — 0,28 с, а компания
упирается в базу на ~6 вопросах в секунду с длинным хвостом (p95 4,6 с).
Это всё ещё вдвое больше всей квоты Яндекса (3 в секунду), поэтому до
пилотов — не узкое место. Когда у компании будет больше ~50 тыс.
фрагментов — заняться (RISKS №27).

**Почему дорого — разобрали, но не чинили.**
1. Вектор (768 чисел, 3 КБ) pgvector по умолчанию хранит вне строки, в
   TOAST: перебор достаёт каждый отдельным поиском. План на 100 тыс.:
   ~400 тыс. обращений к страницам, перебор 166 мс. С вектором в строке
   (`STORAGE PLAIN`) — ~50 тыс. обращений и 49 мс; голый запрос на копии
   таблицы (без RLS и соединения с документами) — 55 мс вместо 170 и
   26 запросов в секунду вместо 11 при 10 одновременных.
2. Но в продуктовом запросе `LIMIT 5` стоит над соединением с таблицей
   документов (фильтр прав), и Postgres сортирует **все** фрагменты
   компании вместе с самим вектором. Пока вектор в TOAST, сортируется
   18-байтная ссылка; в строке — 3 КБ на фрагмент, и сортировка уходит
   на диск (~100 МБ на процесс). Через API одна миграция хранения дала
   **хуже**: 4,4 ответа в секунду вместо 6,0 — её не взяли.
3. Хвост p95 на 100 тыс. — ожидание `LWLock:LockManager` в Postgres на
   запросе поиска; отключение параллельных процессов не помогло (2,4
   ответа в секунду, p50 4,1 с). Корень не найден.

Чинить хранение и форму запроса нужно вместе: сначала отобрать
ближайшие с учётом прав, без вектора в сортировке, затем вектор в
строке. Или индекс по вектору (HNSW) — он приближённый, его ML
проверяет на качество. Оба пути трогают поиск — вместе с ML.

## 7. Чего не мерили

- **Настоящий Yandex Cloud.** Задержки модели и эмбеддингов имитированы;
  сетевые задержки до Яндекса, ретраи после 429 и поведение квоты на их
  стороне — нет. Квоты те же числа, что в настройках.
- **Стенд.** Песочница, а не 4 vCPU / 8 ГБ стенда с nginx, TLS,
  реранкером и мониторингом рядом. Повторить на стенде нельзя без
  тестовой компании на 1 000 учёток и выпуска токенов в обход входа — на
  стенде этого делать не будем.
- **Индексация под нагрузкой.** Воркер в прогонах простаивал; загрузка
  документов во время вопросов делит процессор и базу и берёт свою долю
  квоты эмбеддингов (6 в секунду), вопросам она не мешает.
- **Вход, второй фактор, вложения, реранкер.** Реранкер выключен
  решением ML (R-14); с ним каждый вопрос — ещё ~1,9 с четырёх ядер на
  30 фрагментов на том же сервере (RISKS №54).
- **Много компаний одновременно.** Компания одна; квоты общие, поэтому
  результат для нескольких компаний тот же, если сложить их спрос.

## 8. Что делать

- **Сделано в этой ветке:** соединение отпускается на время модели,
  поток всегда заканчивается, перегрузка — `busy`, очередь к слоту
  эмбеддинга — 10 с.
- **Следить на стенде и в бою:** доля ответов `busy` (лог
  `chat_answer_busy`) — первый признак, что квоты не хватает.
- **Когда `busy` станет заметной долей** — сначала перераспределить
  доли эмбеддингов (днём вопросы важнее индексации: например, 5 и 4
  вместо 3 и 6 — `EMBEDDING_QUERY_RPS`, `EMBEDDING_INGEST_RPS`, сумма не
  больше 10), затем просить у Яндекса больше квоты, затем — каталог на
  группу компаний.
- **Пул соединений** — оставить по умолчанию (5 + 10 на процесс): после
  исправления его хватает с запасом, Postgres по умолчанию держит 100.
- **Второй процесс API** — только если процессор API на стенде будет
  постоянно выше 70 %; тогда же — общий семафор генерации в Redis
  (RISKS №20).
- **Выкатка с открытыми потоками.** uvicorn по SIGTERM ждёт открытые
  потоки ответов без ограничения; в Docker их обрывает SIGKILL через 10 с
  (`docker stop`). Недописанный ответ становится «прерван» — как и раньше
  при выкатке; менять не стали.
