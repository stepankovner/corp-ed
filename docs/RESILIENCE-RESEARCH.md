# Отказоустойчивость: ML-часть, хостинг и остальное (29.09.2026)

Вопросы команды:

- **как сделать отказоустойчивой не только систему, но и ML-часть**;
- **подходит ли Timeweb** или есть варианты лучше;
- что ещё стоит сделать.

Контекст, который меняет выбор: Яндекс стал прямым конкурентом —
«Алиса AI для бизнеса» вышла 08.09.2026
([Яндекс](https://yandex.ru/company/news/08-09-2026-02)). Поэтому ко всем
выборам ниже добавлен критерий «не зависеть от конкурента». Мониторинг
разобран отдельно — в `MONITORING-RESEARCH.md`.

Цены даны на 29.09.2026 по ссылкам, с НДС, если источник не говорит
иное. Суммы, которые мы посчитали сами из тарифов, помечены «расчёт».
Объёмы и трудозатраты — наша оценка, тоже помечены. Что проверить не
удалось — раздел 7.

## 0. Коротко

1. **ML — самое слабое звено системы.**
   - Эмбеддинги и генерацию даёт один поставщик — Yandex AI Studio.
   - Отказ любой из двух частей означает 502 для сотрудника, хотя
     полнотекстовый поиск в базе уже есть.
   - Если эмбеддинги недоступны дольше ~7,5 минут, документы навсегда
     получают статус `FAILED`.
   - Запросы (вопросы сотрудников и фрагменты документов клиентов)
     Яндекс по умолчанию сохраняет и использует для улучшения своего
     сервиса. Отключающий это заголовок мы не передаём.
2. **Главная идея для ML — открытые модели, которые продают несколько
   провайдеров и которые можно поднять у себя** (gpt-oss-120b,
   Qwen3.6-35B-A3B, bge-m3).
   - Запасной путь — та же модель у другого поставщика: не нужно
     заново подбирать порог и промпт.
   - Конкурент не видит документов.
   - Для эмбеддингов это единственный способ переключаться без второго
     индекса: векторы разных моделей несовместимы.
3. **Хостинг.**
   - **Timeweb** — самый дешёвый, но:
     - у управляемой PostgreSQL нет восстановления на момент времени
       (PITR), только снимки;
     - база размещается в одной зоне, а от концепции зон Timeweb
       отказывается;
     - юридический SLA — 99,8 % в год, это до 17,5 ч простоя;
       компенсация — не больше месячного платежа;
     - у Timeweb есть свои AI-агенты с базой знаний.
   - **Selectel** — единственный из проверенных, у кого есть всё нужное
     и нет конкурирующего ассистента:
     - PostgreSQL с синхронной репликой в другом ЦОД и PITR за 7 дней;
     - pgvector;
     - аттестация УЗ-1, включая базы;
     - GPU;
     - свой каталог открытых моделей.
     Выходит примерно вдвое дороже Timeweb.
   - **Cloud.ru и MWS** технически подходят, но продают конкурирующих
     корпоративных ассистентов. **VK Cloud** не поддерживает pgvector в
     управляемой PostgreSQL.
4. **Предложение (§6).**
   - Неделя работы в коде без смены поставщиков: не сохранять запросы у
     Яндекса, быстрый отказ, частичный ответ вместо 502, документы не
     теряются.
   - Затем ML замеряет запасную модель и открытые эмбеддинги.
   - Хостинг — Selectel; бэкапы копировать ко второму провайдеру.
   - Если бюджет критичен — Timeweb, но PostgreSQL на своей ВМ с
     непрерывным архивом WAL в S3 другого провайдера.
5. **Ещё (§5).**
   - Резервная копия `.env`: без ключей `CONNECTOR_SECRETS_KEYS` после
     потери сервера останавливаются все подключения клиентов, а в плане
     восстановления её нет.
   - Контроль балансов у провайдеров: кончились деньги — тоже отказ.
   - Нагрузочный тест под лимиты Яндекса.
   - Учения по отказам.

## 1. Как ML-часть отказывает сейчас (по коду)

| Что ломается | Что происходит | Где в коде |
|---|---|---|
| Эмбеддинг вопроса (Yandex) недоступен | `LLMError` → 502 «Сервис языковой модели недоступен». Полнотекстовый поиск есть (колонка `tsvector`), но запасным путём не служит; `search_fulltext` сейчас ещё и требует вектор — считает по нему расстояние | `services/faq_service.py` (`answer`, `_retrieve`), `core/exception_handlers.py` (`llm_error_handler`), `repositories/chunk_repository.py` |
| Модель ответа недоступна | 502; найденные выдержки сотрудник не видит | там же |
| Провайдер отвечает медленно | таймаут чтения 60 с, 3 попытки, паузы 1 и 2 с плюс джиттер — до ~3 минут на этап. nginx обрывает ответ через 90 с (`proxy_read_timeout`), а API продолжает ждать. Предохранителя (circuit breaker) нет: запросы копятся и занимают семафор `LLM_MAX_CONCURRENCY` | `llm/retry.py`, `llm/yandex*.py`, `deploy/nginx/kronto.conf` |
| Сбой эмбеддингов при загрузке документа | 5 попыток с паузами 30, 60, 120, 240 с. Если сбой длится дольше ~7,5 минут, материал получает `FAILED` (`embedding_provider_error`) и сам не восстанавливается | `worker.py` (`MAX_ATTEMPTS`, `retry_delay`, `_fail`) |
| Сбой при синхронизации коннектора | 3 попытки | `worker.py` (`SYNC_MAX_ATTEMPTS`) |
| Квоты | эмбеддинги — 10 запросов в секунду на каталог, общие для вопросов и загрузки; генерация — 10 одновременных синхронных запросов ([лимиты](https://aistudio.yandex.ru/docs/ru/ai-studio/concepts/limits)) | `llm/throttle.py` |
| Сохранение запросов | «По умолчанию модели сохраняют все данные запросов». Запросы с `x-data-logging-enabled: false` «не будут использоваться для улучшения сервиса» ([AI Studio](https://aistudio.yandex.ru/docs/ru/ai-studio/operations/disable-logging.html)). В коде заголовка нет | `llm/yandex.py`, `llm/yandex_openai.py`, `llm/yandex_embedding.py` |
| Подпись кластеров пробелов | при сбое — `gaps_label_failed`, отчёт всё равно строится. Это правильная мягкая деградация | `services/gap_report_service.py` |
| Без вектора нельзя записать | `qa_log.question_embedding` и `chunks.embedding` — NOT NULL: ни вопрос, ни фрагмент без вектора не сохранить, а деградация без этого не сработает | `domain/models.py` |

## 2. Варианты для ML

### 2.1. Быстрый отказ вместо зависания

- **Таймауты по этапам:**
  - эмбеддинг вопроса — 5–10 с;
  - ответ модели — 30 с;
  - на запросе сотрудника — одна повторная попытка, три — только в
    фоне;
  - общий бюджет запроса — меньше 90 с, которые даёт nginx.
- **Предохранитель:** после N ошибок подряд провайдер считается
  недоступным на 30–60 с, и запросы сразу идут по запасному пути (§2.2,
  §2.3). Процесс API один, поэтому хватит состояния в памяти; при
  нескольких процессах — в Redis, рядом с лимитами.

### 2.2. Частичный ответ вместо ошибки

| Что недоступно | Что получает сотрудник | Кредиты | Что нужно в коде |
|---|---|---|---|
| Модель ответа | найденные выдержки со ссылками и пометка «Модель временно недоступна — вот что нашлось в документах» | 0 | новый `origin` (например, `fragments`), экран на фронте, запись в `qa_log` |
| Эмбеддинги | полнотекстовый поиск → выдержки. Отдавать ли их модели — решает ML: порог сейчас стоит на векторном расстоянии, у полнотекста его нет | 0 или по факту | `search_fulltext` без вектора; `qa_log.question_embedding` допускает NULL |
| Оба | полнотекстовый поиск → выдержки | 0 | то же |
| Эмбеддинги — при загрузке документа | фрагменты сохраняются сразу, и полнотекстовый поиск находит документ в тот же момент; векторы досчитываются позже. При ошибке провайдера — не `FAILED`, а откладывание до суток с растущей паузой | — | `chunks.embedding` допускает NULL; векторный поиск — `WHERE embedding IS NOT NULL`; отдельный статус «ждёт провайдера» |

Токенизаторы у моделей разные, поэтому цены за 1 млн токенов напрямую
не сравнить. Сравнивать нужно стоимость одинаковой пачки наших
вопросов.

**Стоимость вопроса.** Расчёт: выдержки — 3 000 токенов
(`RAG_CONTEXT_MAX_TOKENS`) плюс промпт и вопрос ≈ 3 500 токенов на вход
и ≈ 500 на выход.

| Модель | Вход | Выход | Итого за вопрос |
|---|---|---|---|
| Alice AI LLM Flash | 3,5 × 0,1 ₽ | 0,5 × 0,2 ₽ | ≈ **0,45 ₽** |
| gpt-oss-120b у MWS | 3 500 × 13,42 / 10⁶ | 500 × 54,90 / 10⁶ | ≈ **0,07 ₽** |

**Когда окупается своя GPU.** Аренда A100 за 152 474 ₽/мес окупается при
152 474 / 0,45 ≈ 340 тыс. вопросов в месяц против Alice и при
152 474 / 0,07 ≈ 2,2 млн против gpt-oss у MWS. Пилот мы оцениваем в 5
компаний × 100 сотрудников × 5 вопросов × 22 дня ≈ 55 тыс. вопросов в
месяц (предположение). Значит, своя GPU для генерации сейчас — вопрос
независимости, а не денег.

**Как устроить переключение.**

- Одна и та же открытая модель у нескольких поставщиков. gpt-oss-120b
  (Apache 2.0) есть у Яндекса, MWS, Cloud.ru и Selectel, и её можно
  поднять на своей GPU. Переключение между ними не требует нового
  промпта под каждого провайдера.
- Шлюз — в коде: `FallbackGateway` поверх существующего контракта
  `LLMGateway`, основной и запасной адаптер плюс предохранитель. Для двух
  провайдеров это проще отдельного сервиса.
- LiteLLM proxy (MIT: запасные маршруты, повторы, бюджеты, ключи —
  [GitHub](https://github.com/BerriAI/litellm)) имеет смысл, когда
  провайдеров станет три и больше или понадобятся бюджеты по ключам. Это
  лишний компонент и лишняя точка отказа.
- **Качество до включения:** ML прогоняет золотой набор (52 вопроса) на
  кандидате и проверяет ссылки `[n]`, честный отказ и общий ответ. Порог
  отказа стоит на эмбеддингах, поэтому от смены модели ответа он не
  зависит.

### 2.4. Эмбеддинги — самое дорогое место

**Почему.**

- Векторы разных моделей несовместимы. Переключиться на другую модель
  «на лету» можно только со вторым индексом.
- Порог отказа 0,51 и расстояние кластеров пробелов подобраны под
  `text-embeddings-v2`.

**Варианты.**

| | Что даёт | Цена |
|---|---|---|
| Полнотекстовый поиск как запасной путь (§2.2) | поиск работает без эмбеддингов, хуже по смыслу | дёшево: колонка `tsvector` уже есть |
| Второй индекс другой моделью | мгновенное переключение | индексация и место на диске ×2 |
| **Открытая модель у себя + та же модель у провайдера** (bge-m3: Cloud.ru 0,61 ₽ за 1 млн, MWS 0,61 ₽, Selectel FMC) | векторы совместимы между источниками (с оговоркой о точности вычислений); документы не уходят конкуренту; у Яндекса эмбеддинги стоят 10,1 ₽ за 1 млн | переиндексация + новые пороги (работа ML) |

**Кандидаты.** Цифры — с карточек моделей. Версии бенчмарка разные,
поэтому сравнивать можно только внутри одного источника.

| Модель | Параметры | Размерность | Лицензия | Русский бенчмарк (источник) |
|---|---|---|---|---|
| ai-sage/Giga-Embeddings-instruct-480M | ~480M | 1024 | MIT | MTEB(rus v1.1) 70,98 ([карточка](https://huggingface.co/ai-sage/Giga-Embeddings-instruct-480M-0826)) |
| deepvk/USER-bge-m3 | 359M | 1024 | Apache 2.0 | 62,80, поиск 73,63 ([таблица deepvk](https://huggingface.co/deepvk/USER2-base)) |
| BAAI/bge-m3 | 567M | 1024 | MIT | 61,58, поиск 74,79 ([ruMTEB](https://arxiv.org/abs/2408.12503)) |
| deepvk/USER2-base | 149M | 768, Matryoshka | Apache 2.0 | 61,12 ([карточка](https://huggingface.co/deepvk/USER2-base)) |
| intfloat/multilingual-e5-large-instruct | 560M | 1024 | MIT | 66,03 ([ruMTEB](https://arxiv.org/abs/2408.12503)) |
| Qwen3-Embedding-0.6B | 0,6B | 1024 | Apache 2.0 | 63,64 ([карточка Giga](https://huggingface.co/ai-sage/Giga-Embeddings-instruct-480M-0826)) |
| jina-embeddings-v3 | 572M | 1024 | **CC BY-NC** — коммерческое использование только по лицензии Jina | — |

**Как Яндекс выглядит на этом фоне.**

- Яндекса в ruMTEB нет, и свои замеры качества он не публикует.
- Единственное внешнее сравнение, которое мы нашли, — статья на Хабре
  (30 вопросов, судебный корпус): у эмбеддингов Яндекса nDCG@5 = 0,630,
  у USER2-base — 0,773 ([Хабр](https://habr.com/ru/articles/1030706/)).
  Это слабое свидетельство, но оно не говорит в пользу того, что открытые
  модели хуже.

**Как запускать у себя.**

- Text Embeddings Inference (Apache 2.0) — есть CPU-образ; поддерживает
  XLM-R (bge-m3, e5, USER-bge-m3), ModernBERT (USER2) и Qwen3, но не T5
  (FRIDA) ([модели](https://huggingface.co/docs/text-embeddings-inference/supported_models)).
- Infinity (MIT) — OpenAI-совместимый API.
- Размерность 1024 помещается в HNSW-индекс pgvector для `vector` (до
  2 000).
- Скорость на CPU из первоисточников мы не нашли. Наша оценка: вопрос —
  десятки миллисекунд; индексация — от единиц до десятков фрагментов в
  секунду на 16 ядер. Нужен замер.

**Предложение.** ML замеряет 2–3 кандидата на золотом наборе против
`text-embeddings-v2`: bge-m3 или USER-bge-m3, Giga-Embeddings-480M,
USER2-base. Если не хуже — переезжаем: основной путь — своя модель на
CPU, запасной — та же модель через API провайдера (или наоборот).

### 2.5. Качество ML как часть мониторинга

- Ночной прогон золотого набора на основной и запасной модели (RISKS
  №23).
- Алерт на смену `llm_model_version`.
- Доли по дням: отказы, общие ответы, 👎, ответы в деградации.
- После смены эмбеддингов — следить за распределением
  `best_vector_distance`: если оно сдвинулось, порог устарел.

## 3. Хостинг

### 3.1. Что нам нужно от провайдера

1. Управляемая PostgreSQL с pgvector, репликой в другом ЦОД,
   автопереключением и восстановлением на момент времени (PITR).
2. Несколько зон доступности в одном регионе: ВМ приложения и
   мониторинга — в разных.
3. Аттестация по 152-ФЗ (УЗ-1) — клиенты-компании о ней спросят.
4. S3 для бэкапов.
5. GPU и российский инференс открытых моделей — для §2.3 и §2.4.
6. Провайдер не продаёт конкурирующего корпоративного ассистента.
7. Цена.

### 3.3. Timeweb подробнее (его и планировали)

- **Зоны.** «Мы постепенно отказываемся от концепции зон доступности.
  Для новых пользователей… будет предлагаться одна общая зона»
  ([Timeweb](https://timeweb.cloud/docs/zony-dostupnosti)).
- **Бэкапы базы.** «Снимок состояния базы данных на уровне файловой
  системы» — ежедневно, еженедельно или ежемесячно. Восстановить можно
  только на момент снимка. RPO — до суток, как у нашего `pg_dump` сейчас.
- **SLA.**
  - Доступность «от 99,8 % по итогам года» для российской части —
    это 0,2 % × 8 760 ч = **17,5 ч простоя в год** без нарушения SLA.
  - Компенсация — стоимость суток, если простой ≥ 6 ч или было ≥ 6
    сбоев за сутки.
  - Совокупная ответственность — не больше месячного платежа.
- **Инциденты.** Амстердам — около 46 ч простоя в мае–июне 2026 (по
  посту пользователя на Хабре со ссылкой на канал статуса Timeweb). Это
  вне РФ и не первоисточник.
- **Плюсы.** Цена втрое ниже; есть pgvector, Patroni с автопереключением
  внутри зоны, Valkey, УЗ-1.

## 4. Уровни отказоустойчивости системы

| Уровень | Что это | RPO / RTO (оценка) | Реалистичная доступность |
|---|---|---|---|
| **L0 — сейчас** | одна ВМ, `pg_dump` раз в сутки, один поставщик ML, без деградации | 24 ч / часы | < 99,5 % |
| **L1 — на пилот (предлагаем)** | ВМ приложения + управляемая база HA с PITR (H3) + бэкапы у второго провайдера + мониторинг на отдельной ВМ + деградация ML + запасная модель | минуты / до часа | 99,5 % |
| **L2 — позже** | две ВМ приложения в разных зонах за балансировщиком, управляемый Redis, эмбеддинги у себя | минуты / минуты | 99,9 % |

**Почему запасная модель важна в этой арифметике.** Числа
иллюстративные; предполагается, что отказы независимы.

- Звенья стоят последовательно: ВМ 99,95 % × база 99,95 % × провайдер
  модели 99,5 % (SLA MWS; SLA Яндекса мы не нашли) ≈ **99,40 %**.
  Слабейшее звено — ML.
- Два провайдера модели параллельно: 1 − 0,005 × 0,005 = 99,9975 %.
  Вся цепочка тогда ≈ 0,9995 × 0,9995 × 0,999975 ≈ **99,90 %**.

Вывод: при одной ВМ быстрее всего доступность поднимает не второй
сервер, а запасной путь для ML.

## 5. Что ещё

1. **Резервная копия `.env`.**
   - DEPLOY §8 считает единственным состоянием PostgreSQL. Но ключи
     `CONNECTOR_SECRETS_KEYS` лежат только в `.env` на сервере, а их
     потеря — это «все подключения останавливаются с
     `credentials_unreadable`» (DEPLOY §9).
   - Нужна зашифрованная копия `.env` вне хоста: менеджер паролей
     команды или S3 у другого провайдера, доступ — у двух человек.
2. **Бэкапы у второго провайдера.** Защищают от отказа провайдера
   целиком (блокировка аккаунта, инцидент на всей площадке). S3 стоит
   1–2,6 ₽ за ГБ в месяц. Раз в квартал — не только восстановить дамп
   (это уже есть в DEPLOY §8), но и **поднять систему с нуля** в другой
   зоне по инструкции, засекая время. Это и есть наш реальный RTO.
3. **Деньги — тоже точка отказа.** Кончился баланс у облака, у Yandex AI
   Studio или у SMS-сервиса — отказ без единой ошибки в коде. Нужны
   уведомления о балансе и лимиты расходов у каждого провайдера плюс
   алерт в мониторинге.
4. **Нагрузочный тест до пилота.**
   - Потолок ответов: 10 одновременных генераций при ~2 с на ответ
     (0,8–2,3 с на прогоне 28.09) ≈ 5 ответов в секунду ≈ 18 тыс. в
     час. Для пилота с запасом.
   - Узкое место — общая квота эмбеддингов 10 запросов/с при загрузке
     большой папки. Проверить k6 или Locust.
5. **Учения** на стенде, с проверкой, что алерты пришли, а деградация
   сработала:
   - остановить Redis;
   - закрыть выход к Yandex (`iptables`);
   - убить воркер;
   - заполнить диск.
6. **Выкатка без простоя.** `docker compose up -d --build` пересоздаёт
   `api`.
   - Минимум: собирать образ до остановки (`build`, затем `up -d`).
   - Позже: два контейнера `api` за nginx по очереди.
7. **SLA в договорах** — не выше того, что даёт архитектура: 99,5 % на
   L1. Страница статуса и шаблон сообщения клиенту об инциденте — до
   первого инцидента, а не после.
8. **Переносимость.** Compose, скрипты развёртывания и бэкапы в
   стандартных форматах (`pg_dump`, WAL-G) позволяют переехать к другому
   провайдеру за дни. Это страховка на случай, если любой поставщик
   станет конкурентом.

## 6. Предложение по шагам

1. **Неделя работы в коде, поставщики не меняются.**
   - `x-data-logging-enabled: false` во всех запросах к Яндексу.
   - Таймауты по этапам и предохранитель (§2.1).
   - Частичный ответ вместо 502 (§2.2).
   - Загрузка документов без потерь: фрагменты сразу, векторы позже,
     без `FAILED` при ошибке провайдера.
   - Резервная копия `.env`; бэкапы у второго провайдера.
2. **1–2 недели вместе с ML.**
   - Замер запасной модели на золотом наборе (gpt-oss-120b или
     Qwen3.6-35B-A3B у MWS или Selectel) и `FallbackGateway`.
   - Замер 2–3 открытых моделей эмбеддингов.
3. **Хостинг до пилота.**
   - H3 (Selectel ru-6).
   - Если бюджет критичен — H2 (Timeweb + своя PostgreSQL с WAL-G в
     S3 другого провайдера).
   - H1 — только как временный вариант с явным принятием RPO 24 ч.
   - Мониторинг — вариант B из `MONITORING-RESEARCH.md`.
4. **По итогам замера** — перевод эмбеддингов на открытую модель: у
   себя плюс та же модель у провайдера в запасе.

## 7. Что осталось непроверенным

- **Цены.** Цены Selectel, Cloud.ru, VK и MWS за ВМ и базу — наш расчёт
  из тарифов, единицы в прайс-API Selectel не подтверждены. Для Timeweb
  не проверено, считается ли реплика полным узлом.
- **SLA.** Selectel — по странице услуги, юридический документ не
  читали. SLA Yandex AI Studio, GigaChat и Cloud.ru Foundation Models не
  нашли.
- **Timeweb.** Мульти-зонный кластер управляемой базы не нашли — это
  вывод из отсутствия, а не прямое утверждение. Российское размещение
  моделей в AI Gateway — по вторичным источникам.
- **Лимит Cloud.ru.** Источники расходятся: 20 запросов в секунду на
  ключ против 20 параллельных запросов на организацию.
- **Эмбеддинги.**
  - Действует ли `x-data-logging-enabled` на эмбеддинги — документация
    прямо не говорит.
  - Скорость открытых эмбеддингов на CPU — только наша оценка.
  - Совпадают ли векторы одной модели у разных поставщиков настолько,
    чтобы порог не сдвинулся (fp16, fp32, int8), — нужен замер.
  - Баллы бенчмарков — с карточек моделей, версии разные. Яндекса в
    ruMTEB нет.
- **Объёмы.** 55 тыс. вопросов в месяц на пилоте и ≈ 3 500 + 500
  токенов на вопрос — предположения.
- **Инциденты.** Selectel в 2026 году — по агрегатору статусов
  ([seo-recipes](https://seo-recipes.ru/hosting/incidents/2026/selectel.html)):
  деградация сетевых дисков в ru-7b 31.08–05.09, сеть ru-3/ru-9 —
  2 ч 25 мин 01–02.09. Timeweb, Амстердам — по посту пользователя.
- **УЗ-1 у MWS** для управляемой базы.
