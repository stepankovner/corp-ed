# Архитектура corp-ed

Карта системы на 6 сентября 2026. Описывает то, что реально существует в коде,
а не то, что запланировано. Пробелы и слабые места — в `RISKS.md`.

---

## 1. Общая форма

Слоистая архитектура (layered) с однонаправленной зависимостью сверху вниз:

```
api  →  services  →  repositories  →  domain
```

Плюс два элемента, которые в эту цепочку не входят:

- **`core`** — сквозная инфраструктура. К нему обращаются все слои, он не
  передаёт данные по конвейеру, а предоставляет услуги: конфиг, подключение
  к БД, безопасность, иерархия исключений, логирование, tenant-контекст.
- **`llm`** — адаптер к внешней системе, стоит на том же уровне, что
  `repositories`. Оба переводят с языка внешней системы (PostgreSQL,
  Yandex Cloud) на язык домена.

Правило, по которому проверяется целостность: **импорт вверх по цепочке —
протечка слоя.** `repositories` не знает про `services`, `domain` не знает
про `sqlalchemy` и `httpx`.

## 2. Слои

### 2.1. `api` — граница с клиентом

- `api/v1/endpoints/auth.py` — регистрация, логин, `GET /auth/me`
- `api/v1/endpoints/users.py` — операции с пользователями
- `api/v1/dependencies.py` — композиционный корень: здесь собираются
  репозитории, сервисы и гейтвей и раздаются через `Depends`

Единственный слой, знающий про HTTP. Валидация входящих данных — Pydantic-схемы
на границе. Исходящие ошибки в HTTP-коды превращает не этот слой,
а обработчики исключений (см. 3.4).

### 2.2. `services` — бизнес-логика

- `AuthService` — регистрация тенанта и пользователя, проверка учётных данных,
  выпуск токена
- `UserService` — операции над пользователями

Сервисы принимают зависимости в конструктор и не создают их внутри. Это
условие тестируемости: если тест не пишется — виновата зависимость, созданная
внутри.

### 2.3. `repositories` — доступ к данным

- `UserRepository`
- `TenantRepository`

Работают с `AsyncSession`, отдают наверх ORM-объекты. Сессия создаётся на
запрос через `get_session`.

### 2.4. `domain` — модели предметной области

| Сущность | Назначение |
|---|---|
| `Tenant` | компания-клиент, корень всех данных |
| `User` | человек в компании; уникальность по паре `tenant_id + email` |
| `UserRole` | роль пользователя (енум) |
| `Brief` | заполненная руководителем анкета, вход для генерации |
| `Program` | программа адаптации; `intern_id` nullable, `content: str` — заглушка |
| `ProgramStatus` | стадия жизни программы (енум) |
| `Material` | материал отдела, источник для FAQ |
| `Track` | направление; енум, не таблица |

У всех сущностей есть `tenant_id` — это несущая конструкция изоляции.

## 3. `core` — сквозная инфраструктура

### 3.1. Конфигурация

- `Settings` — общие настройки приложения, читаются из `.env`
- `LLMSettings` — отдельный класс для Yandex Cloud (`YC_FOLDER_ID`, `YC_API_KEY`)

`LLMSettings` **не создаётся на уровне модуля**: экземпляр собирается лениво
в `get_llm_settings()` под `@lru_cache`. Иначе импорт модуля требовал бы
наличия кредов, и падали бы тесты и alembic.

Принцип: конфиг читают там, где создают объекты, а не там, где их описывают.

### 3.2. База данных

`get_session` — асинхронная сессия на запрос, отдаётся через `Depends`.
Стек: SQLAlchemy 2.x в async-режиме, драйвер asyncpg, PostgreSQL 16.

### 3.3. Безопасность и аутентификация

- Пароли — passlib с argon2
- Токены — PyJWT; в payload лежат `sub` (id пользователя) и `tenant_id`
- `decode_access_token` — проверка подписи и срока жизни

Поток аутентификации:

1. `get_current_user` декодирует токен, при неудаче — `NotAuthenticatedError`
2. Достаёт `sub` и `tenant_id`, приводит к UUID
3. **Ставит `tenant_id` в контекст из подписанного токена**, а не из заголовка
4. Загружает пользователя, проверяет `is_active`

`require_role(*roles)` — фабрика зависимостей: возвращает зависимость,
пропускающую только перечисленные роли, иначе `PermissionError` (403).

Заглушка `X-Tenant-ID` удалена: тенант подменить нельзя, он внутри подписи.

### 3.4. Исключения

Иерархия доменных исключений с общим корнем `DomainError`:

```
DomainError
├── ConflictError
├── NotFoundError
├── PermissionError
├── InvalidCredentialsError
└── NotAuthenticatedError
```

Направление конверсии: исключения рождаются внутри системы, летят вверх и
превращаются в HTTP-ответы централизованными обработчиками, зарегистрированными
в `main.py`. Обработчик `DomainError` стоит запасным вариантом на случай
незарегистрированного потомка.

`NotAuthenticatedError` отдаёт 401 с обязательным заголовком
`WWW-Authenticate: Bearer`.

### 3.5. Логирование и трассировка

`structlog` + `RequestIDMiddleware`: каждому запросу присваивается идентификатор,
который попадает во все записи лога этого запроса.

### 3.6. Мультитенантность

Три части:

- `current_tenant` — контекстная переменная, ставится в `get_current_user`
- `TenantMixin` — добавляет `tenant_id` моделям; порядок наследования
  `TenantMixin, Base`, не наоборот
- Хук `do_orm_execute` — перехватывает ORM-запросы и подмешивает фильтр
  через `with_loader_criteria`

**Границы применимости хука.** Он висит на ORM-исполнении и покрывает только
SELECT. Мимо проходят:

- INSERT, UPDATE, DELETE — `tenant_id` проставляется вручную
- Raw SQL и Core-запросы — фильтр не навешивается вообще

Практическое следствие: изоляция на чтении автоматическая, на записи —
договорная. Векторный поиск в pgvector пойдёт сырым SQL и потребует явной
фильтрации.

Без тенанта в контексте запросы падают (default deny).

## 4. Слой `llm`

Провайдеро-независимый гейтвей. Пять модулей:

### `types.py` — доменные типы

`Role`, `FinishReason`, `Message`, `Usage`, `Completion`. Все — frozen
dataclass'ы и StrEnum. Внешних зависимостей нет.

`Completion` несёт не только текст, но и `finish_reason`, `usage`,
`model_version`, `model` и `latency_ms` — всё, что нужно для учёта и отладки.

### `gateway.py` — контракт

`LLMGateway` — абстрактный класс с единственным методом `generate`.
Контракт не импортирует `httpx`: импорт инфраструктуры в контракт был бы
индикатором протечки.

### `errors.py` — классификация ошибок

`LLMError(DomainError)` с флагом `retryable`. Функция `classify` превращает
HTTP-ответ провайдера в доменную ошибку или `None` при успехе.

Ретраебельность определяется статус-кодом (`RETRYABLE_STATUSES`) и не зависит
от формы тела. Тело ответа — данные извне без гарантий формы, поэтому:
непарсящийся JSON и не-объект на любом уровне не выпускают чужих исключений
наружу, а дают `LLMError` с обрезанным фрагментом тела в сообщении.

### `retry.py` — политика повторов

`call_with_retry` принимает колбэк, возвращающий ответ. Экспоненциальный
backoff с jitter. Транспортные ошибки httpx считаются ретраебельными,
классификация остальных — через `classify`. N попыток дают N−1 пауз.

Три механизма повтора различаются и не смешиваются: ретрай (вход тот же),
repair-петля (вход плюс ошибка валидации), исправление входа (обрезка,
разбиение). Здесь реализован только первый.

### `yandex.py` — адаптер

`YandexAdapter(LLMGateway)`. Собирает payload для Yandex Foundation Models,
вызывает через `call_with_retry`, парсит ответ в `Completion`.

Параметры конструктора: HTTP-клиент, `folder_id`, `api_key`, модель, политика
ретраев, таймаут чтения. Модель — параметр конструктора, а не переменная
окружения: она зависит от задачи, а не от окружения.

Латентность меряется внутри одной попытки через замыкание, а не оборачиванием
всего `call_with_retry` — иначе в неё попали бы паузы между попытками.

Неизвестный статус завершения даёт `LLMError`, а не молчаливое допущение.

### `fake.py`

Пустой. `FakeAdapter` будет написан, когда появится первый сервис,
зависящий от `LLMGateway` — до этого его нечем проверить использованием.

## 5. Жизненный цикл приложения

`main.py` собирает приложение:

- `lifespan` создаёт один `httpx.AsyncClient` при старте, кладёт в
  `app.state.http_client`, закрывает при остановке
- Роутеры подключаются с префиксом `/api/v1`
- Регистрируются обработчики исключений
- Добавляется `RequestIDMiddleware`

**Почему один клиент на приложение.** Клиент держит пул соединений; создание
на каждый запрос теряет keep-alive и переустанавливает TLS. Владение ресурсом
принадлежит тому, кто его создал, — поэтому создаёт и закрывает `lifespan`,
а адаптеры получают готовый клиент аргументом конструктора.

Цена выбора `app.state`: контейнер не типизирован, mypy видит `Any`.
Обращение к нему локализовано в одной функции `get_http_client`.

Цепочка зависимостей гейтвея:

```
get_llm_settings  ─┐
                   ├─→  get_llm_gateway  →  LLMGateway
get_http_client   ─┘
```

`get_llm_gateway` объявляет типом возврата **контракт**, а не `YandexAdapter`:
зависимость декларирует контракт, а не реализацию.

## 6. Миграции

Alembic, цепочка ревизий, `alembic upgrade head`.

`alembic heads` читает файлы, `alembic current` читает БД — быстрый способ
отличить «цепочка цела» от «не достучался до базы».

PostgreSQL Enum: `sa.Enum` игнорирует `create_type=False`. Рабочее решение —
`postgresql.ENUM` из `sqlalchemy.dialects` с явным `.create(checkfirst=True)`
в начале `upgrade()` и `create_type=False` во всех колонках.

## 7. Тесты

`pytest` + `pytest-asyncio`, `asyncio_mode = "auto"`.

Режим `auto` выбран вместо `strict` осознанно: цена `strict` — async-тест без
декоратора собирается, показывается зелёным и не выполняется. Молчаливо
зелёный тест хуже, чем неявность механизма.

Существующее покрытие: `tests/llm/test_errors.py` — классификация ошибок,
включая ответ с непарсящимся телом.

mypy на `tests/` не смотрит (`files = ["src"]`) — решение отложено сознательно
до появления заметного объёма тестов.

## 8. Стек

**Приложение:** FastAPI, SQLAlchemy 2.x (async), asyncpg, PostgreSQL 16,
Pydantic v2 + pydantic-settings, PyJWT, passlib[argon2], structlog, httpx,
uvicorn.

**Разработка:** uv, ruff, mypy strict, pre-commit, Alembic, pytest,
pytest-asyncio, Docker Compose, GitHub Actions.

**Внешние сервисы:** Yandex Cloud Foundation Models (YandexGPT) — выбран
из-за требований 152-ФЗ к размещению данных.

**Планируется:** pgvector, Redis, Celery.

## 9. Чего в системе нет

Раздел существует, чтобы карта не читалась как описание готового продукта.

- Гейтвей не подключён ни к одной ручке — потребителя `LLMGateway` нет
- Нет сервиса генерации программ
- Нет RAG/FAQ: ни ингеста, ни чанков, ни векторного поиска
- Нет учёта usage
- Нет фронтенда
- Нет деплоя: `compose.prod` не существует
- `Program.content` — строка-заглушка, структура ждёт согласования

Единственный сквозной пользовательский сценарий на данный момент —
аутентификация.
