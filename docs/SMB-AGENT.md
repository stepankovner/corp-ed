# Агент сетевых папок (SMB): устройство и протокол

Решение владельца продукта 15.10 (`DECISIONS.md`): делать сейчас, вместе
с остальными коннекторами. Сетевые папки — самый частый способ хранить
документы (57 % компаний, `CONNECTORS-RESEARCH.md`), но до них нельзя
дотянуться из интернета: файловый сервер стоит внутри сети клиента.
Поэтому здесь всё наоборот по сравнению с другими коннекторами: не kronto
ходит в систему, а **агент в сети клиента приходит в kronto**.

Вид `smb_agent`, только «Корпоративный», скрыт до живой проверки у
пилота (`CONNECTOR_PREVIEW_KINDS`).

## 1. Кто что делает

| Часть | Где | Что делает |
|---|---|---|
| Агент (`agent/`, образ Docker) | сеть клиента, рядом с файловым сервером | обходит папки по SMB 2/3, читает права NTFS (дескрипторы безопасности), переводит SID в почты через LDAP контроллера домена, отправляет в kronto изменённые файлы и права |
| Сервер (`/api/v1/agent/...`) | kronto | принимает документы и права агента тем же конвейером, что и у других коннекторов (извлечение текста в песочнице, материалы, очередь индексации), удаляет исчезнувшее после полного обхода |

Агент ходит только наружу, по HTTPS на 443: входящих портов в сети
клиента не нужно. Пароль к файловому серверу и к LDAP остаются у клиента
— в kronto их нет.

## 2. Права: как папка становится списком почт

Для каждого файла агент берёт эффективный дескриптор безопасности
(с унаследованными ACE) и считает, **кто может читать** (право
`FILE_READ_DATA`, включая `GENERIC_READ`, `GENERIC_ALL`):

1. ACE разрешения и запрета по SID пользователей и групп.
2. Группы раскрываются через LDAP транзитивно (правило
   `LDAP_MATCHING_RULE_IN_CHAIN`, `member:1.2.840.113556.1.4.1941:`),
   почта — атрибут `mail` (если пуст — `userPrincipalName`, если задано
   в настройке агента).
3. Запрет побеждает разрешение (так же решает Windows для явных и
   унаследованных ACE одного уровня; порядок «явные раньше
   унаследованных» учитывается).
4. Широкие SID — `Everyone` (S-1-1-0), `Authenticated Users` (S-1-5-11),
   `Domain Users` (…-513) — раскрываются в **явный список** почт всех
   включённых пользователей домена, а не в «видно всем»: в kronto
   компании могут быть люди не из домена.
5. Отключённые учётки (`userAccountControl` с битом 2) не попадают.
6. Что не удалось однозначно вычислить (SID чужого домена, условные
   ACE, учётка без почты) — пропускается: документ виден только тем, у
   кого право доказано. Агент пишет счётчики пропусков в отчёт запуска.

**Чего агент не видит.** Права на сам общий ресурс (share permissions)
читаются только через RPC администратора — агент их не читает и
считает, что ресурс открыт на чтение всем, кто есть в NTFS-правах (так
обычно и настраивают: «Everyone — чтение» на ресурсе, ограничения — в
NTFS). Если на ресурсе стоят ограничения уже, чем в NTFS, админ задаёт в
агенте `share_readers` — группу, с которой пересекается каждый список.

**Чем проверено.** Стенд — Samba в роли контроллера домена AD в Docker
(`tests/live/smb/`): настоящие SMB 3, дескрипторы безопасности NTFS
(через `vfs_acl_xattr`), LDAP с группами и почтами. Это те же протоколы,
что у Windows Server, но **не Windows Server**: поведение реального
сервера с GPO, DFS и вложенными доверием доменами на стенде не
проверено — это часть живой проверки у первого клиента.

## 3. Протокол агент → kronto

Аутентификация — ключ агента в заголовке
`Authorization: Bearer kag_<tenant>_<connector>_<секрет>`. Ключ выпускает
администратор компании (в карточке подключения — «Выпустить ключ
агента», либо `cli agent-token`); в kronto хранится только SHA-256
секрета. Перевыпуск ключа отзывает старый. Ключ даёт доступ только к ручкам ниже и только к своему
подключению.

Базовый путь — `/api/v1/agent`.

### 3.1. `GET /state?after=<external_id>&limit=1000`

Что уже есть в kronto: `{"documents": [{"external_id", "version"}],
"next": "<external_id>" | null}`. По нему агент решает, какие файлы
отправлять заново.

### 3.2. `POST /runs` → `{"run_id": "<uuid>", "started_at": "<iso>"}`

Начать обход. Один открытый обход на подключение: новый закрывает
прежний незавершённый (как упавший, без удаления).

### 3.3. `PUT /documents` (multipart)

Часть `meta` (JSON):

```json
{
  "run_id": "…",
  "external_id": "<путь UNC в нижнем регистре; длиннее 512 — sha256:<хеш пути>>",
  "version": "<mtime_ns>-<size> или хеш",
  "title": "Положение о командировках",
  "path": "\\\\fs01\\docs\\Кадры\\Положение о командировках.docx",
  "filename": "Положение о командировках.docx",
  "modified_at": "2026-10-15T09:00:00Z",
  "allowed_emails": ["a@corp.ru", "b@corp.ru"]
}
```

Часть `file` — содержимое. Ответ — `{"status": "added" | "updated" |
"unchanged", "material_id"}`. Тот же конвейер, что у коннекторов: формат,
лимиты размера, песочница; неподдерживаемый формат — `415`, слишком
большой — `413` (агент считает и пропускает).

### 3.4. `POST /access` (JSON, до 500 документов за раз)

Файл не менялся, права могли: `{"run_id", "documents": [{"external_id",
"allowed_emails"}]}` → `{"updated": n, "unknown": [external_id, …]}`.
Неизвестный external_id — агент отправит файл через `PUT /documents`.

### 3.5. `POST /runs/{run_id}/finish`

`{"complete": true, "stats": {...}}`. Только при `complete: true` сервер
удаляет материалы этого подключения, которых обход не коснулся
(`synced_at` раньше начала обхода): прерванный обход — не повод удалять.
Статистика пишется в журнал запусков подключения (тот же, что у других
коннекторов).

Все ручки отвечают `401` на неверный ключ, `403` — подключение
остановлено или вид скрыт у компании, `429` — лимит (агент ждёт
`Retry-After`).

## 4. Видимость в kronto

- Документ всегда `RESTRICTED`: видят сотрудники kronto, чьи почты есть в
  `allowed_emails`. Почта, которой нет среди сотрудников компании,
  пропускается (как у коннекторов режима organization).
- Расписание сервера агентское подключение не запускает: обход делает
  агент (по умолчанию раз в час, настраивается).
- Остановить подключение — как любое другое: агент получит `403` и
  перестанет отправлять.
