# Свой runner GitHub Actions

**Runner** — программа GitHub, которая берёт задания Actions и выполняет
их на своей машине. Наш — отдельная ВМ в Timeweb Cloud: на ней идут все
workflow (CI, Security, Deploy, Stage resume), когда задана переменная
репозитория `RUNS_ON`.

**Зачем.**

- 02.10 кончились минуты Actions: у приватного репозитория на тарифе
  Free — 2 000 минут в месяц, задания перестали стартовать (`WORKLOG.md`,
  02.10). Минуты своего runner GitHub не считает.
- Решение Б владельца (03.10) — свой runner на отдельной ВМ. Заодно
  автовозобновление стенда раз в 10 минут (`STAGE.md` §4.8) ничего не
  стоит.
- Переключение — без правки workflow: `RUNS_ON` задана — задания идут
  на наш runner, удалена — снова на машины GitHub.

Скрипт настройки — `deploy/ci-runner/setup.sh`.

---

## 1. Сервер

**Timeweb Cloud, Cloud-80: 4 vCPU, 8 ГБ RAM, 80 ГБ NVMe, Ubuntu 24.04,
публичный IPv4, Новосибирск — ≈ 2 300 ₽/мес.** Москва и Петербург 03.10
были распроданы. Для runner расстояние не важно: к GitHub он ходит сам,
к нему подключаемся только мы по SSH.

- **На ВМ только runner.** Данных стенда и клиентов здесь нет. Секреты
  (ключ выкатки, токен GHCR) лежат на диске только на время задания
  Deploy (§4).
- **Два экземпляра**, `kronto-ci-1` и `kronto-ci-2`, — два задания
  одновременно, по ~2 ядра на задание, как у машины GitHub для
  приватного репозитория. Swap 4 ГБ — запас на случай, когда сойдутся
  два тяжёлых задания (CodeQL, сборка образа).

## 2. Как устроено

```
GitHub ◄── runner сам забирает задания (HTTPS, исходящие) ── ВМ Timeweb
                                                              ├─ kronto-ci-1, kronto-ci-2: службы systemd, пользователь runner
                                                              └─ Docker: сервисы заданий (postgres, redis), сборка образов, Trivy
```

У каждого задания в `ci.yaml`, `security.yaml`, `deploy.yaml` и
`stage-resume.yaml`:

```yaml
runs-on: ${{ fromJSON(vars.RUNS_ON || '"ubuntu-24.04"') }}
```

`RUNS_ON` = `["self-hosted","kronto"]` — задание ждёт runner с меткой
`kronto`; переменной нет — `ubuntu-24.04`, как раньше.

**Чем наш runner отличается от машины GitHub:**

| Машина GitHub | Наш runner | Что сделано |
|---|---|---|
| `sudo` без пароля: `playwright install --with-deps` сам ставит библиотеки Chromium | у пользователя `runner` sudo нет | библиотеки ставит `setup.sh` (список Playwright 1.63 для Ubuntu 24.04); на своём runner e2e ставит только браузер (`runner.environment`) |
| в образе есть `git`, `psql`, `python3`, `jq`, `zstd`, компилятор | чистая Ubuntu | ставит `setup.sh` |
| пояс UTC, `LANG=C.UTF-8` | у ВМ может быть местный пояс | `setup.sh`: UTC; `LANG` — в `.env` runner |
| одноразовая машина на одно задание | два задания сразу, Docker и домашний каталог общие и переживают задание | ниже |

**Общая машина — что поменялось в workflow** (на машинах GitHub всё
работает так же):

- **Порты сервисов** (`postgres`, `redis`) на хосте — случайные:
  `ports: [5432]`, адрес — `job.services.postgres.ports['5432']`. С
  `5432:5432` второе задание с базой на той же машине не стартует, а в
  одном прогоне CI их три (checks, e2e, migrations). Вариант «задания с
  базой по одному через concurrency» отброшен: второй экземпляр
  простаивал бы, а в группе concurrency ждущее задание отменяется, как
  только приходит следующее.
- **e2e:** порты API и фронта — свободные (шаг Ports), метрики воркера
  (9101) выключены.
- **Образы** в заданиях image — с номером прогона (`ci-<run_id>`,
  `scan-<run_id>`) и удаляются в конце; контейнер web — на случайном
  порту и тоже удаляется. Иначе параллельный прогон подменил бы
  проверяемый образ.
- **Ключ выкатки и логин GHCR** — в `RUNNER_TEMP` (runner очищает его в
  начале и в конце задания), а не в `~/.ssh` и `~/.docker`.
- **Кэш Trivy** — свой у каждого экземпляра: два сканирования с общим
  кэшем не уживаются.
- **Docker публикует порты в обход ufw** — в `/etc/docker/daemon.json`
  `"ip": "127.0.0.1"`: порты сервисов видны только с самой ВМ.
- **Мусор Docker** — `kronto-ci-clean` из cron: раз в неделю — всё
  неиспользуемое старше недели; каждые 15 минут, если диск занят больше
  80 %, — старше суток, не хватило — старше часа. Runner удаляет
  контейнеры сервисов без их томов, поэтому тома тоже чистятся.

## 3. Первый запуск

Порядок: 1 → 2 → 3 → 4 → 5. Токен (шаг 3) живёт час — брать его прямо
перед шагом 4.

### 3.1. ВМ в Timeweb Cloud

Панель меняется — если поле называется иначе, ищите по смыслу.

1. `timeweb.cloud` → **Облачные серверы** → **Создать**.
2. ОС — **Ubuntu 24.04**; локация — **Новосибирск**; конфигурация —
   **Cloud-80** (4 vCPU, 8 ГБ, 80 ГБ NVMe); публичный IPv4.
3. **SSH-ключ** — ваш открытый личный ключ, тот же, что для стенда
   (`id_ed25519.pub`, `STAGE.md` §4.1). Без ключа `setup.sh` оставит
   вход по паролю и предупредит.
4. Создать, скопировать IPv4. Проверка: `ssh root@<IP>`.

### 3.2. Скрипт на сервер

Репозиторий приватный: с сервера по ссылке скрипт не скачать. Пока PR
#57 не влит, файл — в ветке `claude/vibrant-mccarthy-jfc11y` (в команде
`gh` ниже — `ref=` этой ветки вместо `main`).

- Из клона репозитория на своём компьютере:
  ```bash
  scp deploy/ci-runner/setup.sh root@<IP>:/root/setup.sh
  ```
- Без клона: GitHub → `deploy/ci-runner/setup.sh` → кнопка **Download raw
  file**, затем `scp ~/Downloads/setup.sh root@<IP>:/root/setup.sh`.
- Через GitHub CLI:
  ```bash
  gh api -H "Accept: application/vnd.github.raw" \
      "repos/stepankovner/corp-ed/contents/deploy/ci-runner/setup.sh?ref=main" > setup.sh
  scp setup.sh root@<IP>:/root/setup.sh
  ```

### 3.3. Токен регистрации

GitHub → репозиторий → **Settings** → **Actions** → **Runners** → **New
self-hosted runner** → Linux, x64. Команды со страницы выполнять не
нужно — всё делает `setup.sh`. Нужен только токен: строка после
`--token` в команде `./config.sh --url … --token AXXXX…`.

- Живёт **1 час**, подходит для обоих экземпляров.
- **Не присылать в чат и не сохранять в файл.** Он нужен один раз:
  дальше runner входит своим ключом (`.credentials` в каталоге
  экземпляра).

### 3.4. Запуск (один раз, под root)

На сервере:

```bash
ssh root@<IP>
bash /root/setup.sh
# «токен регистрации (ввод скрыт):» — вставить токен, Enter
```

Или со своего компьютера, не заходя на сервер (macOS, Linux):

```bash
read -rs TOKEN        # вставить токен, Enter: на экране и в истории его нет
printf '%s\n' "$TOKEN" | ssh root@<IP> bash /root/setup.sh; unset TOKEN
```

Токен — только через stdin: в аргументах или переменной окружения он
попал бы в историю shell и в `ps`.

Скрипт работает 5–10 минут. Что он делает:

- ставит Docker с buildx и compose (из репозитория Docker; недоступен —
  из архива Ubuntu), git, psql, python3, jq, zstd, компилятор,
  библиотеки Chromium для Playwright и зависимости самого runner;
- автообновления безопасности, пояс UTC, журнал не больше 1 ГБ, swap
  4 ГБ;
- файрвол — снаружи только 22; SSH — только по ключу, с постквантовым
  обменом первым (как `bootstrap.sh` стенда);
- пользователь `runner` в группе `docker`, без sudo;
- `actions/runner` 2.337.0 (SHA-256 архива сверяется), экземпляры
  `kronto-ci-1` и `kronto-ci-2` в `/home/runner/actions-runner-N`, метка
  `kronto`, службы systemd;
- чистку Docker (`/etc/cron.d/kronto-ci`).

Повторный запуск безопасен: настроенные экземпляры он не трогает, и
токен тогда не нужен. Число экземпляров — переменная `RUNNERS` в начале
команды (по умолчанию 2; на 8 ГБ больше не ставить). Не скачиваются
образы с Docker Hub — добавить в начало команды
`REGISTRY_MIRROR=https://mirror.gcr.io`.

### 3.5. Включить и проверить

1. GitHub → Settings → Actions → **Runners**: `kronto-ci-1` и
   `kronto-ci-2` в статусе **Idle**, метки `self-hosted`, `Linux`,
   `X64`, `kronto`.
2. Settings → **Secrets and variables** → **Actions** → вкладка
   **Variables** → **New repository variable**: имя `RUNS_ON`, значение
   ровно `["self-hosted","kronto"]` — с квадратными скобками и кавычками,
   это JSON. Не JSON — workflow не стартуют с ошибкой `fromJSON`.
3. **Проверка:** Actions → **CI** → последний прогон → **Re-run all
   jobs**. В логе задания, шаг **Set up job**, — `Runner name:
   'kronto-ci-1'` (или `-2`); на странице Runners экземпляр — **Active**.
   Все задания зелёные, как на машинах GitHub.
4. **Выкатка:** Actions → **Deploy** → **Run workflow** → `main` — три
   зелёных шага (`STAGE.md` §4.7).
5. Теперь можно включить автовозобновление стенда раз в 10 минут
   (`STAGE.md` §4.8).

### 3.6. Откат

Удалить переменную `RUNS_ON` (Settings → Secrets and variables → Actions
→ Variables). Следующие запуски снова идут на машины GitHub и тратят
минуты; задания, которые уже ждут наш runner, — отменить и запустить
заново. ВМ можно оставить (runner простаивает) или удалить: сначала
Settings → Actions → Runners → экземпляр → **Remove**, затем сервер в
Timeweb.

## 4. Безопасность

- **Отдельная ВМ.** Задания идут под `runner` в группе `docker`, а это
  фактически root: код из workflow может на этой машине всё. Поэтому на
  ней нет ничего, кроме runner, — ни данных стенда, ни ключей от других
  серверов.
- **Только приватный репозиторий.** Код со стороны на runner не
  попадает: PR из форков приватного репозитория workflow не запускают,
  пока это не включено в Settings → Actions → General. Если репозиторий
  станет публичным — сначала удалить `RUNS_ON` и runner: в публичном
  любой PR выполнил бы свой код на нашей машине (GitHub советует свои
  runner только для приватных).
- **Секреты — только на время задания.** `STAGE_SSH_KEY` и логин GHCR
  лежат в `RUNNER_TEMP` и стираются runner в конце задания;
  `GITHUB_TOKEN` истекает сам. Пароль Selectel (Stage resume) — только
  в окружении шага.
- **Токен регистрации** — на час и один раз; в чат не присылать.
- **Снаружи — только SSH по ключу.** Порты Docker — только на 127.0.0.1;
  runner сам ходит к GitHub, входящих не принимает.
- **Обновления:** безопасности Ubuntu ставятся сами, runner обновляется
  сам.

## 5. Обслуживание

- **Состояние:** `systemctl status 'actions.runner.*'`; логи —
  `journalctl -u 'actions.runner.*' -f` и
  `/home/runner/actions-runner-N/_diag/`.
- **Диск:** `df -h /`, `docker system df`. Чистка идёт сама; вручную —
  `kronto-ci-clean weekly`, её журнал — `journalctl -t kronto-ci-clean`.
- **Docker** из репозитория Docker автообновления не трогают. Раз в
  месяц, когда оба экземпляра Idle: `apt-get update && apt-get upgrade
  -y`; есть `/var/run/reboot-required` — `reboot` (службы runner
  поднимутся сами).
- **Runner** обновляется сам: GitHub не даёт заданий слишком старой
  версии. Версия и SHA-256 в `setup.sh` — только для первой установки;
  при пересоздании ВМ взять свежий релиз и его SHA-256 из раздела
  «SHA-256 Checksums» описания релиза.
- **Playwright обновился** и e2e падает с `Host system is missing
  dependencies` — дописать пакеты из сообщения в `PLAYWRIGHT_DEPS` в
  `setup.sh` и запустить его ещё раз.
- **Изменился `setup.sh`** — запустить ещё раз, токен не нужен.
- **ВМ пересоздали** — новый токен и `setup.sh`: `--replace` заменит
  экземпляры с теми же именами.

## 6. Что проверено

**03.10, в среде сессии:**

- `actionlint` 1.7.12 с shellcheck — все четыре workflow; `bash -n` и
  `shellcheck` 0.11 — `setup.sh` и `kronto-ci-clean`.
- **Задания CI на одной машине одновременно**, как на runner с двумя
  экземплярами: сервисы на случайных портах 127.0.0.1, шаги — из
  `ci.yaml`. Два e2e сразу — по 10 из 10 Playwright; два migrations и
  checks сразу — 1 529 тестов, покрытие 91 %. Smoke-тест образа web —
  случайный порт, контейнер и образ удаляются.
- **`setup.sh` в контейнере Ubuntu 24.04** без systemd (`systemctl`,
  `timedatectl` и включение swap — заглушки): пакеты ставятся (Docker —
  из архива Ubuntu: download.docker.com из песочницы недоступен), ufw —
  только 22, sshd принимает настройку, пояс — UTC, `config.sh` проходит
  проверку зависимостей и берёт токен из окружения (в журнале runner —
  `***`); регистрация остановлена на первом запросе к GitHub. С
  имитацией зарегистрированных экземпляров — `svc.sh install runner` и
  повторные запуски без токена и без изменений. Логика
  `kronto-ci-clean` — на поддельных `docker` и `df`.
- **Docker:** отпечаток ключа `9DC8 5822 9FC7 DD38 854A E2D8 8D81 803C
  0EBF CD88` извлекается из настоящего ключа; пакеты обоих источников
  есть для noble; `daemon.json` проходит `dockerd --validate`; с
  `"ip": "127.0.0.1"` порт сервиса публикуется только на 127.0.0.1.
- **Архив runner 2.337.0** скачан с github.com, SHA-256 посчитан по
  нему. Страница релиза из песочницы недоступна — сверить с разделом
  «SHA-256 Checksums» на github.com/actions/runner/releases/tag/v2.337.0.

**Не проверено — нужна ВМ и настройки GitHub:**

- регистрация и службы systemd на настоящей ВМ; Docker из
  download.docker.com;
- задания GitHub на нашем runner: CodeQL, gitleaks, Trivy, сборка образов
  (в песочнице сборке недоступны npm и Alpine), выкатка;
- доступ из Timeweb к GitHub, ghcr, Docker Hub, npm, PyPI и CDN
  Playwright;
- память, когда сходятся два тяжёлых задания (CodeQL и сборка образа).
