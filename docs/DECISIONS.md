## 2026-09-04 — Один HTTP-клиент на приложение

**Контекст.** Адаптер к Яндексу держит пул соединений. Нужны разные политики
ретраев и таймаутов для FAQ и генерации программ.

**Решение.** Один `httpx.AsyncClient` создаётся в `lifespan`, живёт в
`app.state`. Адаптеры получают его в конструктор и не владеют им.

**Альтернативы.**
- Адаптер сам создаёт клиент — проще, но при двух политиках получаем два пула
- Новый клиент на каждый запрос — теряется переиспользование соединений

**Цена.** Ответственность за закрытие уехала в `lifespan`. Заголовок с ключом
переехал из клиента в каждый запрос. Конструктор адаптера вырос до семи
аргументов.

**Статус.** Действует.

## 2026-09-07 - Backoff с jitter

**Контекст.** Экспоненциальный `backoff` с `jitter` в `call_with_retry`. При написании тестов выяснилось, что `base_delay=0` не обнуляет паузу

**Решение.** Оставить аддитивный `jitter`, зафиксировать дефект.

**Альтернативы.**
- Пропорциональный множитель - придётся переписать ассерт `sleeps[0] < sleeps[1]` — диапазоны начнут перекрываться

**Цена.** Разброс теряет долю с ростом номера попытки, механизм рассинхронизации слабеет там, где нужнее всего. `base_delay` не управляет паузой полностью.

## 2026-09-07 - Откуда в тестовой базе берутся таблицы

**Контекст.** База создана, но она пустая. Перед тестами в ней должны появиться tenants, users, briefs, programs, materials.

## 2026-09-07 - Как откатывается состояние между тестами

**Контекст.** Тестируемый код вызывает `commit`. Обычная транзакция завершится, данные запишутся по-настоящему, и откатывать станет нечего. Грязь останется в базе.

**Решение.** Очистка через `TRUNCATE ... CASCADE` перед каждым тестом.

**Альтернативы.**
- Вложенная транзакция с `SAVEPOINT`. Механизм неявный, требует обработчика событий.

**Цена.** `TRUNCATE` медленнее отката, но станет заметен только на сотнях тестов.

**Статус.** Действует


## 2026-09-07 - Как в тестах бедт устанавливаться `current_tenant`

**Контекст.** `current_tenant` — контекстная переменная. Хук `do_orm_execute` без неё режет все `SELECT-ы (default deny)`. Значит любой тест, читающий из базы, упадёт, пока тенант не установлен.

(«без тенанта ничего не видно») написать нельзя, придётся его обходить.
- Каждый тест ставит сам — явно, но в каждом тесте появятся две служебные строки.

## 2026-09-08 - Как отлавливать невалидный `tenant_id`

**Контекст.** Изоляция автоматическая на чтении, ручная на записи; забытый или неверный `tenant_id` не
отлавливается ничем

**Решение.** Хук `before_flush`, гибрид подстановки и валидации: не указан → подставить из контекста;
указан свой → пропустить; указан чужой → отказать; пустой контекст и не указан → отказать доменной ошибкой.
Для `session.dirty` — запретить изменение `tenant_id` у существующих записей

**Альтернативы.**
- Чистая подстановка без проверки — молча перезаписывает намерение программиста.
- Базовый репозиторий — не ловит запись мимо него, остаётся договорённостью, а не механизмом.

**Цена.** Второй неявный хук в проекте; raw SQL по-прежнему проходит мимо, для pgvector нужна отдельная
явная фильтрация.

**Статус.** Действует


## 2026-09-09 — Кто владеет транзакцией

**Контекст.** `UserRepository.create` делал `commit` внутри себя. Пока
операция одна, это работает. Но сервис генерации программы делает
несколько записей подряд, а позже добавится строка учёта usage — при
коммите внутри репозитория они уйдут разными транзакциями, и падение
между ними оставит систему в половинчатом состоянии.

**Решение.** Репозитории делают `add` + `flush` + `refresh`, но не
коммитят. `commit` вызывает сервис — он знает границы бизнес-операции.

**Альтернативы.**
- Коммит в репозитории — как было. Каждый метод самодостаточен, но
  атомарность между операциями недостижима.
- Коммит в зависимости `get_session`: фиксировать при успешном
  завершении запроса, откатывать при исключении. Никто не пишет
  `commit` вообще — но это третий неявный механизм в проекте, а два
  уже в списке рисков.

**Цена.** Сервисы обязаны помнить про коммит. Забытый `commit` = молча
потерянные данные, и поймать это можно только тестом.

**Следствия.** `UserService` получил `AsyncSession` в конструктор.
`AuthService` не тронут — `login` только читает.

**Статус.** Действует


## 2026-09-09 — Что возвращает ручка генерации

**Контекст.** `POST /programs/generate` может вернуть программу целиком
или только идентификатор со статусом.

станет отдавать `202`, клиент пойдёт опрашивать `GET /programs/{id}`,
форма ответа не изменится. `GET /programs/{id}` нужен в любом случае —
руководитель открывает программу и позже, не только сразу.

## 2026-09-10 — Что делать с оборванной генерацией

**Контекст.** `Completion` несёт `finish_reason`. Модель может упереться
в `max_tokens` и вернуть обрубок с кодом 200. Без проверки обрубок
сохраняется как готовая программа — молчаливая порча данных.

**Решение.** Проверять `finish_reason` сразу после вызова. Если не
`COMPLETED` — писать предупреждение в лог с `brief_id`, причиной и
числом выходных токенов. Программа сохраняется как обычно, статус не
меняется.

**Альтернативы.**
- Падать с ошибкой — результат теряется, а генерация уже стоила денег
  и секунд.
- Помечать особым статусом — в `ProgramStatus` только `DRAFT` и
  `APPROVED`, третий заводить ради MVP не стали.

**Цена.** Руководитель может открыть программу и увидеть обрыв на
середине. Смягчается тем, что программа в любом случае проходит его
review до показа стажёру.

**Следствия.** Временное решение. Когда появится многочастная
генерация — три вызова с догенерацией оборванной части, — логика
переедет в оркестратор, а из сервиса уйдёт.

**Статус.** Действует, пересмотреть с многочастной генерацией


## 2026-09-25 — Как влить ML-стек

**Контекст.** ML-код пришёл стеком веток: `ml/preprocess-split` →
`ml/retrieval-utils` → `ml/eval` → `ml/prompt-v2` → … → `ml/alice-compare`.
PR #3–#6 открыты по первым четырём, пункты handoff BH-15…BH-23 (Flash,

**Решение.** Влить вершину стека `ml/alice-compare` одним merge-коммитом

**Альтернативы.**

## 2026-09-25 — Где лежит название документа для выдержки

## 2026-09-25 — Что хранит `chunks.content` и по чему считается эмбеддинг

**Контекст.** Нарезка v2 отдаёт два представления: `embed_text` (крошки +
текст без разметки) и `llm_text` (крошки + Markdown).

**Решение.** `content` = `llm_text`, новая колонка `embed_text`, новая
колонка `heading_path text[]`. Эмбеддинг — только по `embed_text`.
`materials.content` хранит Markdown ДО `preprocess`: ингест каждый раз
прогоняет предобработку заново.

**Альтернативы.**
- Отдельная колонка `llm_text`, `content` — мёртвая до удаления.
- `heading_path jsonb` — гибче, но в Python ручная валидация, и для
  списка строк гибкость не нужна.
- Хранить результат `preprocess` — ингест быстрее на миллисекунды, но
  исправление предобработки у ML требует повторной загрузки файлов.

**Цена.** `embed_text` почти дублирует `content` — ×2 к тексту чанков.
Он же понадобится для `tsvector` гибридного поиска (BH-12), так что
дубль не пропадёт.

**Статус.** Действует


## 2026-09-25 — Тестовая схема пересоздаётся на каждый прогон
