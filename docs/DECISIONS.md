## 2026-09-04 — Один HTTP-клиент на приложение

**Контекст.** Адаптер к Яндексу держит пул соединений. Нужны разные политики

**Цена.** Ответственность за закрытие уехала в `lifespan`. Заголовок с ключом
переехал из клиента в каждый запрос. Конструктор адаптера вырос до семи
аргументов.

**Статус.** Действует.

## 2026-09-08 - Как отлавливать невалидный `tenant_id`

**Контекст.** Изоляция автоматическая на чтении, ручная на записи; забытый или неверный `tenant_id` не

**Решение.** Хук `before_flush`, гибрид подстановки и валидации: не указан → подставить из контекста;

**Альтернативы.**

- Базовый репозиторий — не ловит запись мимо него, остаётся договорённостью, а не механизмом.

**Цена.** Второй неявный хук в проекте; raw SQL по-прежнему проходит мимо, для pgvector нужна отдельная

## 2026-09-09 — Кто владеет транзакцией

**Контекст.** `UserRepository.create` делал `commit` внутри себя. Пока
операция одна, это работает. Но сервис генерации программы делает
несколько записей подряд, а позже добавится строка учёта usage — при
коммите внутри репозитория они уйдут разными транзакциями, и падение
между ними оставит систему в половинчатом состоянии.

**Решение.** Репозитории делают `add` + `flush` + `refresh`, но не
коммитят. `commit` вызывает сервис — он знает границы бизнес-операции.

**Альтернативы.**
- Коммит в репозитории — как было. Каждый метод самодостаточен, но
  атомарность между операциями недостижима.
- Коммит в зависимости `get_session`: фиксировать при успешном
  завершении запроса, откатывать при исключении. Никто не пишет
  `commit` вообще — но это третий неявный механизм в проекте, а два
  уже в списке рисков.

**Цена.** Сервисы обязаны помнить про коммит. Забытый `commit` = молча
потерянные данные, и поймать это можно только тестом.

**Следствия.** `UserService` получил `AsyncSession` в конструктор.
`AuthService` не тронут — `login` только читает.

**Статус.** Действует

## 2026-09-25 — Короткий access-токен и ротация refresh-токена

**Контекст.** Access-токен жил 8 часов, отозвать его было нельзя: ни
смена пароля, ни блокировка не действовали до истечения срока. Выхода
не было вовсе. В токене не было `iss`, `aud`, `jti`, `nbf` — сервер не
отличил бы свой токен от токена другого сервиса с тем же ключом.

**Решение.**
- Access — JWT на 15 минут с `iss`, `aud`, `iat`, `nbf`, `exp`, `jti`,
  `typ` и `ver`; при проверке все обязательны, алгоритм — только HS256.
- `users.token_version` (`ver` в токене): смена пароля, роли,
  блокировка, «выйти везде» увеличивают её — старые access-токены
  отвергаются сразу, без чёрного списка.
- Refresh — случайные 256 бит, в базе только sha256. При каждом
  обмене выдаётся новый, старый помечается использованным. Повторное
  предъявление использованного — признак кражи: отзывается вся цепочка
  (`family_id`), RFC 9700 §4.14.2.
- Роль из токена для прав не используется — только из базы.

**Альтернативы.**
- Чёрный список `jti` — точечный отзыв, но запрос в хранилище на
  каждый вызов API и рост списка; `ver` решает то же одним полем.
- Refresh как JWT — не отзывается без хранилища, то есть хранилище всё
  равно нужно.
- Refresh в httpOnly-cookie — XSS не украдёт его из JS, но нужны CSRF-
  защита и `allow_credentials` в CORS. Отложено до появления фронтенда
  на своём домене; тогда — `SameSite=Strict`, путь `/api/v1/auth`.
- Льготное окно при гонке двух вкладок — удобнее, но окно — это ровно
  то время, когда украденный токен работает.

**Цена.** Два запроса к базе на каждый вызов API (тенант и пользователь).
Две вкладки, одновременно обновляющие токен, разлогинят друг друга:
вторая предъявит уже использованный токен. Фронту — обновлять токен из
одного места.

**Статус.** Действует *28.09:* refresh — в httpOnly-cookie `kronto_refresh`, запись «Refresh-токен в httpOnly-cookie».

## 2026-09-25 — HTTP-периметр: заголовки, ошибки, лимиты, документация

**Контекст.** Ответы уходили без заголовков безопасности, 422 возвращал
присланные данные (включая пароль из `/auth/login`), непойманное
исключение давало текстовый 500 без request_id, размер тела не
ограничивался, `/docs` и `/openapi.json` были открыты везде.

**Решение.**
- `SecurityHeadersMiddleware` (чистый ASGI): nosniff, `X-Frame-Options:
  DENY`, CSP `default-src 'none'`, `no-referrer`, `Cache-Control:
  no-store`; HSTS только в production.
- `BodySizeLimitMiddleware`: 1 МиБ для JSON, 25 МиБ для загрузки;
  проверяет и `Content-Length`, и реально прочитанные байты. Исключение
  при превышении не бросает — FastAPI превратил бы его в 400 — а сам
  отвечает 413 и отдаёт приложению `http.disconnect`.
- `RequestIDMiddleware` ловит непойманные исключения: наружу — JSON
  с request_id, трассировка — в лог. Входящий `X-Request-ID` не
  принимается (подделка записей лога).
- 422 — только `loc`, `msg`, `type`. Ошибки изоляции (нет тенанта,
  чужой `tenant_id`) — общий 500 без слова «tenant».
- `/docs`, `/redoc`, `/openapi.json` — только вне production.
- CORS — явный список origin'ов, без credentials, методы и заголовки
  перечислены. `TrustedHostMiddleware`. В production `*` в хостах и
  CORS — ошибка старта.
- Логи: процессор `redact_sensitive` заменяет значения полей с
  password/token/secret/authorization на `[REDACTED]`.
- Проверка базы в `lifespan` (RISKS №6).

**Альтернативы.**
- Заголовки на reverse proxy — правильно дублировать, но тогда API без
  прокси (локально, в тестах) их не отдаёт, и тестом это не закрыть.
- Обработчик `Exception` у FastAPI — вызывается снаружи всех middleware,
  ответ ушёл бы без заголовков и request_id.
- Лимит тела только на nginx — тот же довод, плюс chunked-тела.

**Цена.** Swagger UI в разработке работает без CSP. Настройки периметра
вынесены в `HttpSettings` с дефолтами — `main.py` читает их при импорте.

**Статус.** Действует


## 2026-09-25 — Ограничение частоты: где хранить счётчики и что делать, если хранилище лежит

**Контекст.** Ни вход, ни вопросы к ассистенту не ограничивались:
пароль перебирался без помех, а каждый `/faq/ask` — это деньги за LLM
и эмбеддинг (OWASP API4:2023, ASVS 6.3.1).

**Решение.**
- Контракт `RateLimiter` и две реализации: `RedisRateLimiter`
  (production, счётчики общие для всех воркеров и экземпляров) и
  `InMemoryRateLimiter` (разработка, тесты). Фиксированное окно:
  INCR + EXPIRE одним Lua-скриптом.
- Вход: 30 попыток на IP за 15 минут и 10 НЕУДАЧНЫХ на пару
  «компания + почта» — в том числе несуществующую, чтобы блокировка
  не выдавала наличие учётки. Успешный вход обнуляет счётчик.
- Обновление токена — 60 в минуту на IP, смена пароля — 5 за 15 минут
  на пользователя, вопросы — 30 в минуту на пользователя.
- Redis лежит: вход, refresh, смена пароля — **fail-closed** (503);
  вопросы, поиск, загрузка — **fail-open** с ошибкой в логе.
- IP берётся из `request.client`; за прокси его подставляет uvicorn
  (`--proxy-headers --forwarded-allow-ips=<адрес прокси>`), а не наш
  разбор `X-Forwarded-For`, который подделывается.

**Альтернативы.**
- Счётчики в Postgres — без нового сервиса, но запись в базу на каждую
  попытку входа и вопрос; Redis всё равно нужен для квоты эмбеддингов.
- Скользящее окно / токен-бакет — точнее на стыке окон, сложнее; для
  защиты от перебора важен порядок величины.
- Капча после N неудач — нужен фронтенд и внешний сервис; позже.
- Всё fail-open — перебор паролей открыт на время сбоя Redis;
  всё fail-closed — сбой счётчика кладёт весь продукт.

**Цена.** Злоумышленник, знающий почту и код компании, может на 15
минут заблокировать вход конкретному сотруднику (10 неверных паролей).
Это известная плата за защиту от распределённого перебора. Redis стал
обязательной зависимостью production.

**Статус.** Действует


## 2026-09-25 — Журнал аудита и неизменяемость на уровне базы

**Контекст.** Действия с безопасностью (входы, смена ролей и паролей,
блокировки, заведение компаний) оставляли след только в текстовом логе
приложения: его ротирует хостинг, и его может почистить любой с
доступом к серверу. Для расследования инцидента и для аудитора нужен
журнал, который не переписывается задним числом (ASVS 16.x).

**Решение.**
- Таблица `audit_events`: кто, что, над чем, когда, IP, request_id,
  детали в JSONB. Не `TenantMixin`: неудачный вход с неверным кодом
  компании тоже пишется — с `tenant_id = NULL`.
- Запись — в той же транзакции, что и действие: нет действия без
  записи и записи без действия. Неудачный вход коммитит только запись.
- Триггер в базе: UPDATE запрещён (кроме обнуления ссылки при
  `ON DELETE SET NULL`), DELETE — только для записей старше 365 дней.
  Действует для любой роли, включая владельца таблицы.
- Список событий закрытый (`AuditAction`): опечатка в строке события —
  событие, которое никто не найдёт.
- IP и request_id передаются в сервисы через `ContextVar`, который
  ставит middleware; сервисы по-прежнему не знают про HTTP.
- `GET /api/v1/audit` — только ADMIN и только своя компания.
- SQL триггера — в `core/db_policies.py`: его выполняют и миграция, и
  тестовая фикстура после `create_all`. Так тесты проверяют настоящее
  поведение базы, а не только кода.

**Альтернативы.**
- Только структурированные логи во внешнюю систему (ELK, Loki) —
  лучше для поиска, но нужен ещё один сервис; журнал в базе не
  исключает этого, а дополняет.
- Запрет прав UPDATE/DELETE у роли приложения — обходится владельцем
  таблицы; триггер работает для всех, кроме суперпользователя.
- Перейти в тестах с `create_all` на миграции — пересмотр решения от
  07.09; общий модуль правил даёт то же покрытие дешевле.

**Цена.** В журнале хранится почта при неудачном входе — это
персональные данные; срок хранения год, и это нужно отразить в
политике обработки ПДн. Суперпользователь PostgreSQL может отключить
триггер — защита от него организационная (доступ к серверу базы).

**Статус.** Действует


## 2026-09-25 — Row-Level Security в PostgreSQL

**Контекст.** Изоляция компаний держалась только на коде: ORM-хуки и
явные фильтры в колоночных запросах. Любой забытый `WHERE tenant_id` в
сыром SQL — утечка между компаниями, которую ничто не поймает
(RISKS №1). В досье (14) RLS — в списке «не сделано».

**Решение.**
- Политика `tenant_isolation` на `users`, `materials`, `chunks`:
  `USING` и `WITH CHECK` сравнивают `tenant_id` с параметром сессии
  `app.tenant_id`. `FORCE ROW LEVEL SECURITY` — и для владельца таблицы.
- Параметр ставит приложение: `set_config(..., is_local => true)` в
  `after_begin`, перед каждым запросом через Session (`do_orm_execute`)
  и перед flush, если контекст сменился. Значение живёт до конца
  транзакции и не переезжает с соединением пула в чужой запрос.
- Нет тенанта — `NULLIF(...)::uuid` даёт NULL, строк ноль (default deny).
- На старте приложение проверяет свою роль: SUPERUSER или BYPASSRLS в
  production — ошибка старта (RLS для них молча не действует).
- Роли: владелец схемы гоняет миграции (`MIGRATIONS_DATABASE_URL`),
  приложение — `corp_ed_app` с правами только на данные
  (`deploy/postgres/10-app-role.sh`).
- Тесты работают под ролью без привилегий (`SET ROLE` на каждом
  соединении), иначе RLS в них не действует и тесты ничего не доказывают.
  Отдельный набор проверяет изоляцию сырым SQL, мимо ORM.
- Тест падает, если появилась тенант-модель без политики.

**Альтернативы.**
- Только ORM-хуки — один рубеж; сырой SQL и колоночные запросы мимо.
- Схема на тенанта — сильнее, но миграции ×N и пул соединений на схему.
- `SET` вместо `set_config(..., true)` — значение переживает
  транзакцию и достаётся следующему запросу на том же соединении.

**Цена.** Один лишний `SELECT set_config` на транзакцию. Две роли в
базе и два URL подключения при деплое. Таблицы, которые ищутся до того,
как тенант известен (`tenants`, `refresh_tokens`, `audit_events`), под RLS
не входят — их защищает код.

**Статус.** Действует


## 2026-09-25 — Нет ответа в документах: общий ответ со строгой пометкой (Р1)

**Контекст.** Досье (3.1) требовало отказа, если ответа во внутренних
данных нет, и первая версия FAQ v2 так и делала (`NOT_FOUND_ANSWER` без
вызова модели). Решение продукта от 25.09: ответ выдаётся, но со
строгой пометкой, что он не основан на документах компании. У ML это
режим Р1 «общий ответ с пометкой»; функции `build_general_messages` и
`ensure_general_prefix` готовы, замер 25.09 на 25 вопросах вне корпуса:
пометка 25/25, выдача общих сведений за правила компании 0/25,
~0,03 ₽ за ответ.

**Решение.**
- Два случая «в документах нет»: (а) ни одна выдержка не прошла порог;
  (б) выдержки нашлись, но модель по ним отказала. В обоих — второй
  промпт без единой выдержки, ответ из общих знаний.
- Пометка двойная и не зависит от модели: первая строка «В документах
  компании ответа нет. Общая информация:» ставится `ensure_general_prefix`
  (даже если модель её потеряла), и поле `origin: "general_knowledge"`
  в ответе API — фронт показывает плашку по полю, не разбирая текст.
- `sources` у общего ответа всегда пуст, `answer_given = false`: для
  журнала ответов и отчёта о пробелах это вопрос без ответа в базе.
- Отказ модели по выдержкам (случай б) клиенту не показывается.

**Альтернативы.**
- Строгий отказ (было) — честно, но сотрудник упирается в тупик на
  типовых вопросах (кадровые, IT), которые документы не покрывают.
- Только случай (а), как в замере ML — меньше вызовов LLM, но на
  отказе модели по близким выдержкам сотрудник снова получает тупик.
- Строгий режим настройкой компании (рекомендация ML) — нужен тем, кому
  нельзя ничего сверх документов; не сделан до первого такого клиента.

**Цена.** В случае (б) — два вызова LLM на вопрос. Случай (б) ML не
замерял: проверить на золотом наборе, что общий ответ не противоречит
частично найденным документам. Ответ модели «из общих знаний» остаётся
ответом модели — пометка снимает с него статус «правила компании», но
не гарантирует правильность.

**Статус.** Действует. Отменяет строгий отказ из решения по FAQ v2 и
позицию досье 3.1 в части «отказывается отвечать». Дополнено: текст
пометки сменил ML (`faq-v2.4`), строгий режим стал настройкой компании —
см. «Р1 по BH-24» ниже.

## 2026-09-25 — Фоновый ингест: очередь в Postgres, темп эмбеддингов в Redis

**Контекст.** Ингест был синхронным (~0,7 с на чанк): документ на 300
чанков держал HTTP-запрос минуты, а длина материала была урезана до
20 000 символов ради этого. Квота эмбеддингов — 10 запросов в секунду
на каталог, общая для вопросов и ингеста; параллельный ингест без
ограничителя сразу получает 429 (BH-4). После каждой смены нарезки или
модели нужна переиндексация всего (BH-6), и ML просит её раньше
перехода на `vector(768)`.

**Решение.**
- Очередь — таблица `ingest_jobs`, воркер `python -m corp_ed.worker`
  берёт задачи `FOR UPDATE SKIP LOCKED`. Задача ставится в той же
  транзакции, что и материал. Частичный уникальный индекс — не больше
  одной активной задачи на материал. Повторы временных сбоев —
  30 с × 2^n, до 5 попыток; упавший воркер — задачу подбирает другой
  через 15 минут.
- `ingest_jobs` не под RLS: воркер выбирает задачу до того, как знает
  тенанта. Содержимое читается уже в `tenant_scope` задачи, в свежей
  сессии на каждую задачу.
- Статус материала: PENDING → PROCESSING → READY / FAILED; причина —
  кодом (`embedding_provider_error`), текст ошибки — только в лог.
  PROCESSING коммитится до эмбеддингов, замена чанков и READY — одним
  коммитом после: при сбое старые чанки остаются.
- Создание материала сразу ставит его в очередь; `POST /ingest` —
  202 и идемпотентная постановка на переиндексацию.
- Темп эмбеддингов — слоты в Redis (Lua + `TIME` сервера Redis), общие
  для API и воркера. Вопросы и ингест — разные ключи и доли квоты
  (3 и 6 в секунду): сотрудник не ждёт, пока воркер съест квоту.
  Слот берёт каждая попытка, включая повтор после 429. Redis лежит —
  fail-open, лишний 429 обработает ретрай.
- `python -m corp_ed.cli reindex (--code X | --all) [--dry-run]` ставит
  все материалы в ту же очередь, компания за компанией в своём
  `tenant_scope`.
- `MaterialService` (API) и `IngestService` (воркер) разделены: API
  эмбеддингов документов больше не считает.

**Альтернативы.**
- `BackgroundTasks` FastAPI — ноль инфраструктуры, но задача умирает с
  процессом и не повторяется.
- arq / Celery на Redis — готовые повторы и мониторинг, но постановка в
  очередь не входит в транзакцию базы: материал без задачи или задача
  без материала становятся возможны.
- Темп в памяти процесса — работает с одним воркером; API и воркер —
  уже два процесса с общей квотой.

**Цена.** Воркер — отдельный процесс для деплоя. Опрос очереди раз в
2 с при пустой очереди. Если материал поменяли, пока задача на него уже
выполняется, новая не встанет до её окончания (частичный индекс).

**Статус.** Действует. Уточняет решение от 17.09 «ингест отдельной
ручкой»: ручка осталась, но для повторной индексации; первая ставится
автоматически при создании.


## 2026-09-25 — text-embeddings-v2 768: одна поставка и ловушка RLS в миграциях

**Контекст.** ML (25.09): `text-embeddings-v2` ищет заметно лучше
`text-search` (MRR +0,25 на dev, p = 0,0001), размерность 768 лучше 256
(+0,048, p = 0,003). Колонка была `vector(256)`, в двух местах было
зашито 256 (проверка в адаптере, фейковый эмбеддер). Порог отказа у v2
другой — 0,51 вместо 0,65. ML просит одну поставку: модель, колонка,
переингест, порог (BH-16…BH-18).

**Решение.**
- `EMBEDDING_DIM = 768` — одна константа схемы в `core/config.py`;
  колонка, адаптер и фейковый эмбеддер берут её оттуда. Настройки
  `EMBEDDING_MODEL` / `EMBEDDING_DIM`: несовпадение размерности со
  схемой — ошибка старта с подсказкой «нужна миграция и переиндексация».
- В `chunks.model` пишется `семейство-вид@размерность`
  (`text-embeddings-v2-doc@768`) — видно, какие векторы пересчитывать.
- Миграция: `TRUNCATE chunks`, колонка → `vector(768)`, все материалы
  в очередь ингеста. Воркер пересчитает всё без отдельного запуска
  reindex. Порог 0,51 — в той же поставке.
- **Ловушка:** таблицы под `FORCE ROW LEVEL SECURITY`, а владелец схемы
  в production — не суперпользователь. `DELETE FROM chunks` в миграции
  удалил бы ноль строк, а выборка материалов вернула бы пустоту.
  Поэтому `TRUNCATE` (RLS на него не действует) и `NO FORCE` на время
  транзакции миграции для выборки материалов. Проверено прогоном под
  ролью-владельцем без SUPERUSER и с данными.

**Альтернативы.**
- Новая колонка `embedding_v2`, заполнение в фоне, переключение поиска
  — без окна пустого поиска, но две миграции и два пути поиска; на
  pre-MVP без клиентов окно ничего не стоит.
- 256 без миграции — отвергнуто ML: MRR на 0,05 ниже.

**Цена.** До окончания переингеста поиск пуст — сотрудники получают
общие ответы с пометкой. Каждая будущая миграция с данными
тенант-таблиц должна помнить про FORCE (записано в `db_policies.py`).

**Статус.** Действует *30.09:* порог 0,59 (BH-31, ML-4); финал — holdout 11–12.10.


## 2026-09-25 — Загрузка файлов: проверки, песочница, что хранится

**Контекст.** Досье (3.3): pre-MVP — ответы по загруженным docx, PDF с
текстовым слоем, txt, md; неподдерживаемое отклоняется при загрузке с
понятным сообщением. ML выбрал библиотеки (BH-2): mammoth + markdownify
для docx, pymupdf4llm для PDF, страницы через `\f`. Файл присылает
клиент — это враждебный вход, а MuPDF — библиотека на C.

**Решение.**
- `POST /api/v1/materials/upload` (multipart, ADMIN): файл + `title`.
  Название обязательно — ML просит человеческое, а не имя файла.
- Формат — по расширению, **подтверждённому сигнатурой**: `%PDF-`,
  zip с `word/document.xml`; бинарник, переименованный в .txt, — отказ.
  Content-Type от клиента не используется.
- До парсера — проверка docx на zip-бомбу: распакованный объём,
  число файлов, коэффициент сжатия.
- Разбор — в дочернем процессе (`python -I -m
  corp_ed.ingest.extract_worker`): пустое окружение (без `SECRET_KEY`,
  ключа Яндекса и строки базы), `RLIMIT_AS` 1,5 ГБ, `RLIMIT_CPU` 60 с,
  запрет записи файлов и core dump, таймаут 90 с с `kill`. Наружу —
  только Markdown или код ошибки из закрытого списка.
- Отказы — `415` (формат) или `422` с `code` и текстом для человека;
  подробности парсера — только в лог.
- Хранится извлечённый Markdown (до `preprocess`), имя файла без пути,
  формат, размер и sha256. **Исходный файл не хранится.** Повтор того же
  файла в той же компании — `409` с id существующего материала.
- Транзакция во время разбора не открыта: дедупликация — после.
- Переименование ставит материал на переиндексацию (название — в
  крошках каждого чанка); удаление убирает чанки каскадом сразу.

**Альтернативы.**
- Разбор в процессе API — быстрее на ~1 с (запуск интерпретатора), но
  уязвимость парсера исполнялась бы рядом с секретами, а PDF-бомба
  занимала бы воркер API.
- Контейнер-песочница (gVisor, отдельный сервис) — сильнее изоляция,
  но ещё один сервис; rlimit + пустое окружение закрывают основное.
- Хранить исходники (в базе или в Object Storage) — можно переизвлечь
  после улучшения конвертера, но это ещё одна копия персональных
  данных клиента; переиндексация и так берёт текст из базы.
- markitdown для PDF — ноль заголовков (замер ML).

**Цена.** ~1 с накладных расходов на каждый файл. Улучшение извлечения
(не предобработки) не применится к уже загруженным файлам без повторной
загрузки. Starlette складывает части multipart больше 1 МБ во временный
файл на диске API — он удаляется после запроса. pymupdf и pymupdf4llm —
AGPL-3.0 (решение команды; риск — в RISKS.md).

**Статус.** Действует *01.10:* форматов семь — ещё .xlsx, .pptx, .doc (запись 01.10); лимит CPU с 26.09 — таймаут × ядер.


## 2026-09-25 — Журнал ответов, оценки, отладка поиска, сроки хранения

**Контекст.** Без версии промпта и модели рядом с ответом нельзя

- `debug=true` у `/faq/ask` вместо `/faq/search` — меньше кода, но

**Цена.** Строка журнала на каждый вопрос (вектор 768 — ~3 КБ). Purge

## 2026-09-25 — Пул кредитов компании: расход по журналу, остановка до вызовов

**Контекст.** Досье (10.2): один пул на компанию, один тип кредита,
персональных лимитов нет, жёсткая остановка при исчерпании, уведомления
на 80 % и 100 %. Числа — предложение, не утверждены: 1 кредит ≈ 2 000
токенов, 420 кредитов на место в месяц. Бэкенд должен считать расход и
не пускать обращения сверх пула; счетов и оплаты в MVP нет.

**Решение.**
- `tenants.seats` (CHECK > 0) задаёт команда: `cli create-tenant
  --seats N` (обязательный) и `cli set-seats` (с событием в аудите
  «было → стало»). Пул = места × `BILLING_CREDITS_PER_SEAT`; смена мест
  действует сразу, без пропорции по дням.
- Период — календарный месяц по `BILLING_TIMEZONE` (Москва): вопрос в
  00:30 1-го числа по Москве списывается с нового пула, хотя по UTC это
  ещё прошлый месяц. Пакет `tzdata` в зависимостях — чтобы пояс не
  зависел от образа ОС.
- Расход — `SUM(qa_log.credits)` с начала месяца по индексу
  `(tenant_id, created_at)`. Отдельного счётчика нет: журнал и есть
  книга расхода, расходиться им не с чем.
- Проверка — **первым шагом** `FaqService.answer`, до эмбеддинга и
  модели: исчерпанный пул не стоит ни копейки. Ответ — HTTP 402 с
  `code: credits_exhausted`: фронту нужен отдельный экран, повтор
  запроса до следующего месяца не поможет. Администратор тоже
  останавливается — пул общий.
- Останавливаем, когда потрачено всё (`used ≥ pool`), а не «когда не
  хватит на следующий»: стоимость ответа заранее неизвестна, последний
  вопрос может уйти в небольшой минус.
- Пороги 80 % и 100 % — события `credits.warning` и `credits.exhausted`
  в журнале аудита (его видит админ, `GET /audit`) и warning в логе для
  команды. Одно событие на порог за месяц. Условие — «порог достигнут
  и события в этом месяце ещё нет», а не «перейдён этим вопросом»: два
  параллельных вопроса, перешедшие порог вместе, иначе потеряли бы
  событие. Событие пишется в транзакции ответа.
- `GET /usage` (ADMIN): период, места, пул, потрачено, осталось.
  Компания — только из токена.
- `/faq/search` кредиты не списывает: это отладка без LLM, только
  эмбеддинг вопроса, и она ограничена лимитом частоты.

**Альтернативы.**
- Счётчик в Redis или в `tenants` — быстрее, но второй источник правды:
  после сбоя между записями счётчик и журнал расходятся, а спор о
  списании решается только по журналу.
- Блокировка на компанию (`SELECT … FOR UPDATE` по tenant или advisory
  lock) — точная остановка без перерасхода, но транзакция держится всё
  время ответа модели (секунды), и вопросы одной компании идут по
  одному. Резервирование кредита до вызова с доначислением после —
  точнее, но сложнее, а выигрыш — несколько кредитов на границе.
- Уведомление письмом — нет почтового канала в MVP; событие аудита —
  то, что админ увидит уже сейчас, а письмо добавится потребителем
  этих же событий.
- Помесячные строки «баланса» — нужны для счетов, в MVP счетов нет.

**Цена.** Без блокировки параллельные вопросы на границе перерасходуют
пул на число одновременных вопросов компании (для 30 мест — десятки
кредитов из 12 600, < 0,5 %). Один лишний SUM на каждый вопрос (индекс,
~12 тыс. строк в месяц на компанию). Сократить места ниже потраченного —
остановить компанию до конца месяца: это осознанно, решает команда.

**Статус.** Действует. Числа (420 и 2 000) — пересмотреть, когда
команда утвердит тарифы (досье 10.2). *29.09–30.09:* 1 кредит = 4 000 токенов (BH-30, `BILLING_TOKENS_PER_CREDIT`); 420 на место подтверждено тарифами 30.09 (запись «Тарифы…»). *09.10:* остановку снимает и купленный пакет кредитов (запись «Пакеты кредитов…»).

## 2026-09-25 — Гибридный поиск (M1, BH-12): под флагом, порог по вектору

**Контекст.** ML (`docs/ml-report.md`, A7): гибрид «вектор + полнотекст»
через RRF поднимает Hit@5 на +0,21 на серебряном наборе (p = 0,0001) и
+0,22 на демо-вопросах (p = 0,12 — мало вопросов). Сквозной прогон на
демо: F1 отказа тот же (0,957), верных 20/24 против 21/24 у вектора.
Решение о включении — по золотому набору (задача ML 2.3). Функции
`to_fulltext_query` и `rrf_merge` — ML, контракт — BH-12.

**Решение.**
- `chunks.fts tsvector GENERATED ALWAYS AS (to_tsvector('russian',
  embed_text)) STORED` + GIN-индекс. Колонку считает база из того же
  текста, что у эмбеддинга: ветки видят одно и то же, и забыть обновить
  её при переингесте нельзя. В ORM — `deferred`, в Python не грузится.
- `ChunkRepository.search_fulltext`: `websearch_to_tsquery('russian',
  :q)`, `ts_rank_cd`, явный фильтр тенанта на `chunks` и `materials`
  (колоночный select, хук изоляции его не видит; RLS — третье кольцо).
  `:q` — `to_fulltext_query(question)`: только слова через `or`, минус и
  кавычки вопроса не становятся операторами; значение — bind-параметр.
  Конфигурация `'russian'` — константа в коде, не параметр. Запрос
  заодно считает векторное расстояние найденных чанков.
- `RAG_RETRIEVER=vector|hybrid` (без дефолта, как остальные `RAG_*` —
  переключает ML по замеру), `RAG_FULLTEXT_WEIGHT` (старт 0,5), k = 60 —
  константа ML. Глубина каждой ветки — 50, как в замерах ML.
- Порог в `hybrid` — **на лучшем векторном кандидате**: прошёл — в
  промпт идёт вся слитая выдача (и чанки, найденные только по словам);
  не прошёл — ответа в документах нет, даже если полнотекст нашёл точное
  совпадение. Так замерял ML; скор RRF зависит только от рангов, порог
  по нему бессмыслен. В `vector` — как было: порог на каждой выдержке.
- Полнотекстовая ветка работает **в обоих режимах**: в `vector` — одна
  строка, только сигнал. Её ранг пишется в `qa_log.best_fulltext_score`:
  без него `classify_miss` не отличит «в базе этого нет» (gap) от
  «точное совпадение было, вектор промахнулся» (retrieval_miss).
- `/faq/search` принимает `retriever` (сравнить способы на живой базе,
  не меняя настройку) и отдаёт `fulltext_rank` у каждой выдержки.

**Альтернативы.**
- Включить `hybrid` по умолчанию — Hit@5 выше, но сквозной прогон не
  лучше, а подбор идёт на синтетике; решение за ML по золотому набору.
- Полнотекст по `content` (Markdown) — разметка и таблицы шумят в
  лексемах; `embed_text` — чистый текст с крошками, его же видит
  эмбеддер.
- Отдельная поисковая система (OpenSearch/Elastic, BM25) — точнее
  ранжирование, но ещё один сервис с данными клиентов, своей изоляцией
  тенантов и своими уязвимостями; `ts_rank_cd` для MVP хватает.
- `plainto_tsquery` — соединяет слова через И, ветка почти всегда пуста
  (разбор ML в `domain/fulltext.py`).
- Порог и на чанках полнотекстовой ветки (расстояние мы знаем) —
  отсекло бы то, ради чего гибрид нужен: точные совпадения по словам,
  которые вектор ставит далеко. Открытый вопрос ML 2.3.

**Цена.** Второй запрос к базе на каждый вопрос (GIN-индекс, в `vector` —
LIMIT 1). ADD COLUMN STORED переписал `chunks` под блокировкой при
миграции. В `hybrid` чанк, найденный только по словам, может уйти в
промпт с большим векторным расстоянием — так и замерено, но это
предмет проверки на золотом наборе.

**Статус.** Действует; `RAG_RETRIEVER=vector` до решения ML.


## 2026-09-25 — Словарь сокращений компании (M5, BH-14)

**Контекст.** Вектор плохо находит документ, когда сотрудник пишет
сокращение, а документ — полную форму («ДМС» ↔ «добровольное
медицинское страхование»). ML сделал `expand_query(question, glossary)`
(`domain/query.py`): дописать к вопросу расшифровки найденных терминов
перед эмбеддингом и полнотекстом. Словарь свой у каждой компании.

**Решение.**
- Таблица `glossary_terms (tenant_id, term, expansion)` под RLS с FORCE,
  уникальность `(tenant_id, lower(term))` — «ДМС» и «дмс» один термин,
  как и в `expand_query`. Гонка двух одинаковых терминов — 409, не 500.
- CRUD `/api/v1/glossary` — только ADMIN; каждое изменение в аудите
  (с прежним значением у правки); лимит частоты на компанию; не больше
  500 терминов (каждый проверяется на каждом вопросе).
- Термин 2–64 символа, расшифровка 2–256, одна строка без управляющих
  символов; лишние поля (`tenant_id`) — 422, как везде.
- Расшифровка идёт **только в поиск** (эмбеддинг и полнотекст). В промпт
  модели уходит исходный вопрос сотрудника. В журнал — тоже исходный
  (после `mask_pii`), вектор — тот, что ушёл в поиск (BH-20). В лог —
  только факт расширения, без текста.
- Выборка словаря — колоночный select с явным фильтром тенанта.
- Флага нет: пустой словарь ничего не меняет, поведение включает админ.
- `test_rls.py` теперь проверяет по каталогу базы, что у каждой таблицы
  из `TENANT_TABLES` включены RLS и FORCE и есть политика.

**Альтернативы.**
- Расширенный вопрос и в промпт — модель лучше поняла бы сокращение,
  но текст, который пишет админ компании, становится частью запроса к
  модели (prompt injection через словарь) и меняет вопрос сотрудника.
  Выдержки с полной формой модель и так видит.
- Словарь из документов автоматически (LLM извлекает сокращения) —
  дороже и ошибается; ML предлагает сравнить с multi-query (M6) на eval.
- Замена сокращения вместо дописывания — в документах бывает и то и
  другое (разбор ML в `domain/query.py`).

**Цена.** Лишний запрос словаря на каждый вопрос (обычно десятки строк).
Расшифровка меняет вектор вопроса: плохая расшифровка ухудшит поиск —
ответственность админа компании, изменения видны в аудите.

**Статус.** Действует.


## 2026-09-25 — Отчёт о пробелах (BH-21…23): ночная пересборка

**Контекст.** Досье: админ компании должен видеть, чего не хватает в
документах. ML сделал чистые функции (`domain/gaps.py`: `classify_miss`,
`cluster_questions`, `cluster_priority`, `mask_pii`; `prompts/gaps.py`:
подпись gaps-v1) и оценил их на синтетике: gap + отказ модели —
precision 0,88, recall 0,64; порог кластеров 0,6 — чистота 0,83.
Бэкенду — таблицы, ночная задача и API.

**Решение.**
- `python -m corp_ed.cli gaps --all` раз в сутки, после `purge`. По
  каждой активной компании в её `tenant_scope`: классы всех вопросов
  окна (30 дней) → `qa_log.miss_kind`; вопросы `gap` и `model_refusal`
  одной модели эмбеддингов (новейшей в окне), не больше 2 000 → кластеры
  по уже сохранённым векторам → приоритет → подпись → запись.
- **Кластеризация — только внутри компании**: векторы разных компаний не
  попадают в одну матрицу (цикл по компаниям, тест с одинаковыми
  векторами у двух компаний).
- Пересборка каждую ночь, но **id, статус и подпись переживают её**:
  новый кластер узнаёт вчерашний по общим вопросам (жадно, от больших
  пересечений). Статус узнанного кластера при записи не трогается —
  если админ сменил его, пока шла подпись, его решение важнее.
- Подпись моделью — только новым кластерам и кластерам со старой версией
  промпта; строгий JSON (`response_format`, для нативного API —
  `jsonSchema`). Модель вызывается вне транзакции. Сбой модели — не сбой
  отчёта: временное название из самого свежего вопроса, подпись —
  следующей ночью. Не больше 50 подписей за ночь на компанию. Текст
  модели — одна строка, без управляющих символов, в пределах поля.
- Пороги полнотекста (`GAPS_STRONG_FULLTEXT`/`GAPS_EMPTY_FULLTEXT`) ML
  просит подобрать на живых логах (`ts_rank_cd`, не доля слов, как в
  замере). Пока не заданы — полнотекст в классификации не участвует.
  `GAPS_CLUSTER_DISTANCE` и `GAPS_HALF_LIFE_DAYS` — значения ML, без
  дефолтов, как `RAG_*`.
- В отчёт — группы от двух вопросов; `retrieval_miss`, `unclear`,
  `off_topic` — внутренний мониторинг, клиенту не показываются (BH-23).
- `gap_clusters` и `gap_cluster_questions` — тенант-таблицы под RLS;
  состав ссылается на `qa_log` с ON DELETE CASCADE: срок хранения
  журнала сильнее отчёта.
- `GET /api/v1/gaps` (ADMIN): важное сверху, фильтр по статусу, до 100;
  примеры вопросов — повторно через `mask_pii`. `PATCH /api/v1/gaps/{id}`
  — статус, с событием аудита. Компания — только из токена.
- Второй одновременный запуск отказывает: транзакционная
  advisory-блокировка (иначе двойной расход LLM и гонка записи).
- Подпись кластеров кредиты компании не списывает: это работа системы
  для админа (~0,05 ₽ за кластер), а не обращение сотрудника.
- Сборка LLM-адаптера вынесена в `llm/factory.py` — её используют и API,
  и ночная задача.

**Альтернативы.**
- Дописывать новые вопросы к кластерам по близости к центроиду (id
  стабильны без сопоставления) — больше кода, и кластеры «дрейфуют»:
  ошибка ранней ночи не исправляется пересборкой.
- Подписывать все кластеры каждую ночь — название прыгает, LLM дороже.
- Кластеризовать онлайн при ответе — задержка ответа сотруднику ради
  отчёта, который смотрят раз в неделю.
- Воркер очереди вместо cron — отчёт раз в сутки, очередь ему не нужна.

**Цена.** Кластеризация ML — O(n³): 2 000 вопросов ~9 с на компанию,
отсюда потолок. Пересечение для сопоставления может «склеить» статус с
заметно изменившимся кластером; для этого есть аудит. Пока пороги
полнотекста не заданы, часть `retrieval_miss` попадёт в отчёт как
`gap` (precision ниже 0,88).

**Статус.** Действует. Пороги полнотекста и 0,6 — уточнить на живых
логах (ML).


## 2026-09-25 — Конвейер безопасности в CI, образ без root, compose как в бою

**Контекст.** Цель проекта — пройти внешнюю проверку безопасности. CI
до этого гонял линтер, типы и тесты; уязвимости в зависимостях, секреты
в истории, состав образа и настройки контейнера никто не проверял.
Первый же прогон `pip-audit` нашёл 7 известных CVE в боевых
зависимостях (`anyio`, `pydantic-settings`, `starlette` — в том числе
DoS через url-encoded форму, PYSEC-2026-249).

**Решение.**
- `ci.yaml`: токен только на чтение (`permissions: contents: read`),
  отмена устаревших прогонов; Redis в сервисах — без `TEST_REDIS_URL`
  тесты Redis-реализаций пропускались бы молча; порог покрытия 85 %
  (`fail_under` в pyproject — страховка от коммитов без тестов, не цель);
  ruff с правилами `S` (bandit) — пять находок в `src` разобраны и
  помечены `noqa` с причиной (имена событий и типов токенов — не пароли;
  джиттер backoff — не криптография).
- Отдельный job миграций на пустой базе **под владельцем схемы без
  SUPERUSER**: `upgrade head → check → downgrade base → upgrade head`.
  Под суперпользователем FORCE RLS не действует, и миграция, которая
  у него проходит, у настоящего владельца может молча не увидеть ни
  одной строки (ловушка из решения по v2@768). Там же проверяется
  скрипт роли приложения: данные читает, `CREATE TABLE` не может, ни
  SUPERUSER, ни BYPASSRLS.
- Job образа: сборка, запуск не под root, импорт приложения, CLI и
  alembic на месте, `resource` для песочницы парсера доступен.
- `security.yaml` — по push, PR и **раз в неделю** (новые CVE
  появляются без изменения кода): `pip-audit` по боевым зависимостям
  из `uv.lock` (без dev-группы, `--no-deps`: список полный и
  закреплён); `gitleaks` по всей истории; CodeQL `security-extended`;
  Trivy по образу (HIGH/CRITICAL с исправлением — красная сборка; без
  исправления — в отчёт) и по Dockerfile/compose; SBOM CycloneDX
  артефактом на 90 дней — для сертификации и разбора инцидентов.
- Dependabot: `uv`, GitHub Actions, Docker — еженедельно, minor/patch
  группой.
- Dockerfile: uv закреплён по версии (совпадает с CI и разработкой);
  `apt-get upgrade` в runtime-слое; отдельный системный пользователь
  без shell и домашней папки, код и окружение — только на чтение;
  `alembic.ini` и `migrations/` в образе, alembic — в основных
  зависимостях (закрывает RISKS №3); HEALTHCHECK на `/health` без
  базы и Redis; `--proxy-headers` (адрес клиента для лимитов и аудита
  — из `X-Forwarded-For`, но только от `FORWARDED_ALLOW_IPS`),
  `--no-server-header`.
- compose: базовый файл — боевая форма (без публикации портов базы и
  Redis, без `--reload`, приложение под `corp_ed_app`, миграции
  одноразовым контейнером под владельцем схемы, `worker` отдельным
  сервисом, Redis с паролем и без диска); `compose.override.yaml` —
  разработка, подхватывается автоматически.

**Альтернативы.**
- Закреплять actions по SHA, а не по тегу — надёжнее против подмены
  тега, но в этой среде SHA проверить нельзя; теги + Dependabot для
  actions, переход на SHA — отдельным шагом (RISKS).
- Закреплять базовый образ по digest — то же: digest нужно снять с
  реестра; Trivy и Dependabot (docker) закрывают риск устаревшего
  образа, digest — следующий шаг.
- Distroless вместо `python:slim` — меньше поверхность, но нет
  `apt`-обновлений, сложнее отладка; slim с `apt-get upgrade` и
  еженедельным Trivy — достаточно для MVP.
- Планировщик (`purge`, `gaps`) внутри compose отдельным сервисом —
  ещё один образ; пока cron на хосте (DEPLOY.md).

**Цена.** Прогон дольше на несколько минут (CodeQL, сборка образа).
Красная сборка из-за CVE в зависимости, которую мы не трогали, — это
намеренно: исправление в тот же день, а не когда заметят.

**Статус.** Действует. *01.10:* с 30.09 репозиторий приватный — CodeQL без GitHub Code Security не работает, оба задания красные; решение владельца — RISKS №13.


## 2026-09-25 — Фильтр содержимого провайдера — отказ, а не сбой (BH-25)

**Контекст.** Ревью ML по ветке бэкенда (handoff v1.2): `content_filter`
от Flash разбирался как неизвестная причина завершения → `LLMError` →
502 «сервис недоступен». В замерах ML — 2 из 1 808 ответов, оба на
законные вопросы (списки, связанные с терроризмом, как основание для
отказа в гранте). Сотрудник повторит и получит то же; строки в `qa_log`
нет — вопрос исчезает из отчёта о пробелах. Там же BH-26: `/latest`
меняет модель без предупреждения, а в журнале только алиас.

**Решение.**
- `FinishReason.FILTERED`; оба адаптера переводят в него `content_filter`
  / `ALTERNATIVE_STATUS_CONTENT_FILTER`. Неизвестные причины — по-прежнему
  `LLMError`.
- `FaqService`: отфильтрованный ответ — `NOT_FOUND_ANSWER`, `origin=none`,
  `sources=[]`, **без второго вызова** (общий промпт на тот же вопрос
  отфильтруется так же), строка в `qa_log` как обычно, кредит за
  сделанный вызов списан. Текст модели («Я не могу обсуждать…») клиенту
  не уходит: он без пометки и без источников.
- `qa_log.llm_model_version` и `diagnostics.model_version` — из поля
  `model` ответа провайдера, отдельной колонкой (URI длиннее 64
  символов, конкатенация с алиасом не влезла бы).

**Альтернативы.** Отдать текст модели как общий ответ с пометкой —
это не общие знания, а отказ провайдера, пометка была бы ложью.
Считать `content_filter` ошибкой и не списывать кредит — вызов был,
и вопрос должен остаться в журнале для отчёта.

**Цена.** Ещё одна причина `origin=none`, неотличимая от строгого
режима по ответу API; в журнале и логе (`faq_content_filtered`) они
различимы.

**Статус.** Действует.


## 2026-09-25 — Коннекторы к источникам документов: дизайн MVP (код не написан)

**Контекст.** Досье: pre-MVP — ответы по загруженным файлам (сделано);
MVP — «ответы по подключённым внутренним источникам; первые адаптеры»
(3.3). Коннекторы считаются **по источникам**, не по типам: два диска —
два коннектора; в базовом тарифе пять на компанию, подключаются на
компанию (10.3). Четыре способа получить документы: загрузка файлов,
синхронизация папки или диска, обход портала, адаптер по API (10.5).
Предложенный ML/продуктом порядок, не утверждён (вопрос 18.1):
Битрикс24 (диск и база знаний) → Яндекс Диск и Вики → Confluence
Server/DC → Google Диск или сетевая папка. Боты в Telegram/MAX/чате
Битрикс24 — канал, а не источник; 1С и amoCRM — структурированные
данные, другая задача. Позиционирование (12.2) обещает «несколько
систем разных вендоров, **права доступа**, ссылки на документы».
Данные не должны уходить за пределы РФ (17.1). Ориентир трудоёмкости
(Forrester): 80 ч на проверку готового коннектора, 172 ч на свой.

Что уже есть и на что опираемся: конвейер файла (`detect_format` →
песочница → `Material` → `IngestJob` → воркер), дедупликация по sha256 в
пределах компании, переиндексация из текста (оригинал не нужен), RLS на
всех тенантских таблицах, аудит, лимиты на компанию.

**Решение (предложение).**

*Термины.* Коннектор — одно настроенное подключение одной компании к
одному источнику (портал, диск, пространство). Адаптер — код для типа
системы. Один адаптер обслуживает много коннекторов.

*Данные* (все таблицы тенантские, под RLS с FORCE):
- `connectors`: `kind` (`bitrix24_disk`, `bitrix24_kb`, `yandex_disk`,
  `yandex_wiki`, `confluence`), `name`, `config` JSONB — **несекретное**
  (адрес портала, корневая папка, пространство, маски), `credentials`
  — секреты **шифрованные** (см. безопасность), `status`
  (`active | paused | error`), `sync_interval_minutes`, `last_sync_at`,
  `last_error_code`, `created_by`.
- `connector_sync_runs`: журнал запусков — начало/конец, статус,
  счётчики (просмотрено / добавлено / обновлено / удалено / с ошибкой),
  код ошибки. Хранится 90 дней (`purge`), нужен админу и разбору сбоев.
- `connector_sync_jobs`: очередь воркера по образцу `ingest_jobs`
  (`FOR UPDATE SKIP LOCKED`, попытки, `run_after`); отдельная таблица,
  не обобщение `ingest_jobs`: другой payload и другая семантика повтора.
- `materials` получает `connector_id` (FK), `external_id` (стабильный
  id в источнике), `source_url` (ссылка на документ — обещание 12.2,
  фронт показывает её в источниках ответа), `external_version` (etag /
  дата изменения / ревизия), `synced_at`. Уникальность
  `(connector_id, external_id)`. Индекс `(tenant_id, source_sha256)`
  остаётся уникальным **только для ручных загрузок**
  (`WHERE connector_id IS NULL`): один и тот же файл на двух дисках — два
  документа с разными ссылками. sha256 у коннекторов — признак «не
  изменился», не ключ.

*Права доступа — главный выбор.* MVP: **видимость на компанию**. Граница
того, что попадает в базу, — учётная запись только для чтения, которую
клиент выдаёт коннектору: что она видит, то видят все сотрудники
компании. Это честно описывается на созвоне подключения (10.1) и в
интерфейсе. Зеркалирование прав источника (12.2) — следующий этап:
таблица `material_access (material_id, principal)` с принципалами,
которые адаптер забирает из системы (Битрикс24 и Confluence отдают
права, Яндекс Диск — только через общий доступ), сопоставление
принципалов с `users` по почте, и условие `EXISTS` в поиске чанков.
Схема MVP этому не мешает; ничего под будущие права заранее не
добавляется, кроме требования к адаптерам отдавать `RemoteDocument`
с полем `path`, из которого права выводятся позже.

*Синхронизация.* Воркер получает планировщик: раз в минуту ставит в
`connector_sync_jobs` коннекторы, у которых `last_sync_at + interval`
прошёл (по умолчанию 60 мин; «синхронизировать сейчас» — ручка с
лимитом частоты). Один запуск, в `tenant_scope` компании:
1. `adapter.check()` — учётные данные живы; нет → `status=error`, код
   ошибки, событие аудита, письмо позже (канала нет, как у кредитов);
2. `adapter.list()` — постраничный обход; неподдерживаемые форматы и
   файлы больше лимита пропускаются с записью в счётчик;
3. сравнение с базой по `(connector_id, external_id)`: новый или
   изменился (`external_version`, затем sha256) → `adapter.fetch()`
   (лимит размера и времени) → **тот же** `detect_format` и
   `extract_isolated`, что у загрузки → материал создан/обновлён →
   `IngestJob.enqueue`; не изменился → пропуск; исчез из источника →
   материал удалён (чанки каскадом);
4. бюджет запуска: не больше N документов (200) и T минут; остаток —
   следующим запуском по курсору. Индексация и так асинхронна.
Ошибка одного документа не роняет запуск (`status_error` у материала);
ошибка авторизации останавливает коннектор до вмешательства админа.
Переиндексация по-прежнему из текста: источник для неё не нужен.

*Адаптеры* — только ввод-вывод через `httpx`, без базы и без знания о
компании; интерфейс:
`check()`, `list() -> AsyncIterator[RemoteDocument]`
(`external_id, title, path, url, version, size, modified_at, kind:
file | page`), `fetch(doc) -> bytes | Markdown`. Страницы (вики, база
знаний, Confluence) приходят HTML → очистка (скрипты, стили, формы) →
`markdownify`; файлы — байтами в конвейер загрузки.
1. **Битрикс24, диск и база знаний.** Авторизация — входящий вебхук с
   правами `disk` и `landing` (создаёт админ портала за минуту; OAuth-
   приложение в Marketplace — позже, когда подключений станет много).
   Диск: `disk.storage.getlist` → `disk.folder.getchildren` рекурсивно →
   `disk.file.get` (`DOWNLOAD_URL`). База знаний — сайты типа KNOWLEDGE
   (`landing.site.getlist` → `landing.landing.getlist` → содержимое
   блоков); **как именно получить текст страницы через REST — проверить
   на тестовом портале первым делом**, это главный технический риск
   адаптера. Лимит API ~2 запроса/с на портал — ограничитель на
   коннектор, метод `batch` для списков. Коробочный Битрикс24 — свой
   домен, те же методы, та же проверка адреса (см. SSRF).
2. **Яндекс Диск** (REST `cloud-api.yandex.net`, OAuth-токен служебного
   пользователя, `resources` с `modified`, `resources/download`) и
   **Яндекс Вики** (B2B API организации Яндекс 360, страницы в YFM).
   Доступность Wiki API на тарифе клиента — проверить.
3. **Confluence Server/DC**: `/rest/api/content` по пространству с
   `body.storage`, `version`, `ancestors`; авторизация PAT (DC 7.9+) или
   логин/пароль служебной учётки; вложения docx/pdf — в файловый
   конвейер. Cloud-версия — другая авторизация и адреса, вне MVP.
4. После MVP: Google Диск, сетевая папка (нужен агент в сети клиента —
   другая архитектура: push с их стороны в наш API).

*API (ADMIN).* `GET /connectors/kinds` (каталог адаптеров и их полей —
для формы на фронте), `GET/POST /connectors`, `GET/PATCH/DELETE
/connectors/{id}`, `PUT /connectors/{id}/credentials` (только запись;
в ответах — `has_credentials` и последние 4 символа), `POST
/connectors/{id}/test` (проверка учётных данных без загрузки), `POST
/connectors/{id}/sync` (лимит частоты), `GET /connectors/{id}/runs`.
Материалы отдают `connector_id` и `source_url`. Шестой коннектор — 409
с кодом `connector_limit` (10.3; лимит — настройка тарифа компании,
пока константа 5).

*Безопасность* (цель — тот же пентест):
- Секреты источников шифруются в базе (`cryptography`, Fernet с
  ротацией через `MultiFernet`; ключ `CONNECTOR_SECRETS_KEY` в
  окружении, в production обязателен). Расшифровка — только в воркере
  на время запуска; API секреты не возвращает; в логи не попадают
  (redaction по ключам плюс запрет логировать `config`).
- **SSRF.** Адрес портала/Confluence задаёт админ клиента — это
  URL от пользователя. Правила: только `https`; имя резолвится, и
  каждый адрес проверяется — не loopback, не RFC 1918, не link-local
  (169.254.0.0/16 — метаданные облака), не ULA IPv6; редиректы не
  следуются автоматически; подключение — к проверенному адресу
  (защита от DNS rebinding). Одна функция `validate_outbound_url` для
  всех адаптеров, с тестами на каждый класс адресов. Egress воркера в
  проде — только к нужным хостам (DEPLOY).
- Скачанное — враждебный ввод, как файл от админа: те же сигнатуры,
  zip-бомба, песочница, лимиты; HTML страниц — очистка до Markdown без
  внешних загрузок. Инструкции в документах — данные (промпт, BH-24).
- Минимальные права учётной записи источника — инструкция на каждый
  адаптер (`docs/CONNECTORS.md`): что выдать, что не выдавать.
- Изоляция: новые таблицы под RLS; адаптер не знает `tenant_id`;
  запуск — в `tenant_scope`; лимиты на компанию: число коннекторов,
  документов за запуск, объём за сутки.
- Аудит: создание/изменение/пауза/удаление коннектора, смена учётных
  данных, ручной запуск, остановка по ошибке авторизации.
- Юрконтур (17.1): данные **втягиваются** в РФ; чтение из системы за
  рубежом (Confluence Cloud, Google) — существующая практика клиента,
  но наши запросы туда — вопрос к юристу; поэтому такие источники
  после MVP.

*Проверка на каждом этапе.* Каждый адаптер получает поддельный сервер
(`httpx.MockTransport` с записанными ответами) и контрактные тесты;
плюс живая проверка `cli connector-check` против тестового портала —
для неё нужны тестовые учётки от команды; ответ живой системы
записывается (без секретов) и становится фикстурой. Этап не считается
закрытым без: тестов, зелёного CI, живой проверки на стенде и записи в
`WORKLOG.md`.

**Альтернативы.**
- Зеркалировать права с первого дня — обещание 12.2, но нужны
  сопоставление личностей (почта в источнике ↔ наш пользователь), ACL
  API у каждой системы (разные, у Яндекс Диска почти нет) и фильтр в
  поиске; ×2–3 к сроку каждого адаптера. Рекомендация: MVP на
  служебной учётке, права — следующий этап, схема готова.
- Push-модель (скрипт клиента шлёт файлы в наш API) — без адаптеров,
  но клиенту нужно что-то запускать у себя; оставить как способ для
  сетевых папок после MVP.
- Платформа интеграций (n8n/Albato) — данные клиента через третью
  сторону (152-ФЗ), зависимость и цена; нет.
- Один обобщённый `jobs` вместо второй очереди — меньше таблиц, но
  миграция живой `ingest_jobs` и смешение семантик; нет.
- Хранить оригиналы файлов коннекторов — не нужно: переиндексация идёт
  из текста, повторная загрузка только при изменении в источнике.
- Диск и база знаний одного портала как один коннектор с галочками —
  проще клиенту, но противоречит правилу 10.3 «по источникам»; решение
  за продуктом (влияет на тариф).

**Цена.** Новая зависимость `cryptography` и ключ шифрования в
окружении (ротация — процедура в DEPLOY). Воркер получает исходящий
доступ к системам клиентов — поверхность SSRF, закрытая проверкой
адресов и egress-политикой. Дубликаты одного файла из двух источников
— два документа в поиске. Задержка появления документа — до интервала
синхронизации. Главный риск сроков — REST базы знаний Битрикс24: если
текст страниц через API не достаётся, останется диск, а база знаний —
через выгрузку. Реалистичная оценка: ядро (таблицы, очередь, API,
шифрование, SSRF, тесты) — 2–3 дня; каждый адаптер — 2–5 дней при
наличии тестового портала.

**Статус.** Предложение; код не написан. Нужны решения команды:
(1) порядок адаптеров (18.1); (2) права в MVP — граница служебной
учётки, зеркалирование позже; (3) Битрикс24 — вебхук, OAuth позже;
(4) диск и база знаний одного портала — один или два коннектора;
(5) интервал синхронизации 60 мин по умолчанию; (6) удаление
коннектора удаляет его документы. И доступ к тестовым порталам:
Битрикс24 (бесплатный тариф достаточен), организация Яндекс 360,
Confluence Server/DC.

Решено: (2) права **зеркалируются в MVP**; (3) Битрикс24 — **OAuth-
приложение**, не вебхук. Открыто: (1) порядок адаптеров и (4) счёт

Что меняется в дизайне из-за зеркалирования прав:
- Исследование показало, что REST Битрикс24 **не отдаёт права на
  файлы и папки диска** (есть только назначение прав), права базы
  знаний читаются только для текущего пользователя и на уровне сайта;
  Яндекс Диск и Вики читаются от имени пользователя. Confluence отдаёт
  ограничения и группы. Значит, один способ на все системы невозможен.
- Коннектор получает **режим**: `organization` (админ подключает,
  ACL выгружаются, личности сопоставляются по почте — Confluence) или
  `per_user` (приложение ставит админ, авторизует каждый сотрудник;
  видимость = «документ есть в листинге сотрудника» — Битрикс24,
  Яндекс). OAuth-приложение — как раз механизм второго режима.
- Новые таблицы: `connector_user_grants` (токены сотрудников,
  шифрованные, обновление по refresh) и `material_access
  (material_id, user_id)`; поиск чанков фильтрует по ней через
  `EXISTS`, ручные загрузки остаются видимыми компании. Содержимое
  скачивается один раз, видимость пересчитывается отдельно листингами
  без скачивания.
- Появляется сценарий сотрудника «подключить мои источники» и
  уведомление о неподключённом источнике.
- Рекомендация по счёту (обоснование — в исследовании, § 4): коннектор =
  одно подключение к одной системе с модулями внутри; правило «два
  диска — два коннектора» сохраняется как «два подключения». Ни один
  из ориентиров (Алиса AI, Coworker, Glean, Microsoft) не тарифицирует
  число коннекторов — считают пользователей, кредиты или объём индекса.
- Оценка сроков: ядро 4–5 дней, адаптер Битрикс24 5–8 дней при наличии
  тестового портала.

**Реализация этапа 1 (25.09, ночь) — где код разошёлся с текстом выше
и почему.**
- Бюджет запуска считается по **работе** (скачанные + упавшие
  документы), а не по просмотренным: иначе источник с 200+
  неизменными документами никогда не дошёл бы до новых.
- Удаление исчезнувших документов — только после **полного** листинга
  (бюджет не исчерпан, источник не упал): обрезанный листинг — не
  доказательство, что документа нет.
- В режиме `per_user` документ удаляется, когда его не листит ни один
  активный грант (RISKS №28); права сотрудника отзываются по его
  полному листингу.
- В ответах коннектора нет «последних 4 символов» секрета — только
  `credentials_set_at`: четыре символа токена ничего не дают админу и
  что-то дают атакующему.
- `POST /connectors/{id}/test` возвращает `ok` и код, а не бросает
  ошибку: проверка — это вопрос, а не сбой.
- `materials.visibility` вместо строки `material_access` «на всех»
  (см. решения выше); `connectors.modules` — массив, без таблицы.
- Переход коннектора из `error` в `active` — только новыми учётными
  данными (`PUT .../credentials`), не `PATCH status`: иначе админ
  «чинил» бы остановку, не меняя причину.
- Тариф: потолок подключений — `CONNECTOR_MAX_PER_TENANT` (20),
  код 409 `connector_limit` сохранён как технический.
- Адаптеров в каталоге пока нет (`default_registry()` пуст): фронт
  получит их с этапами 2–4. Ядро проверено поддельным адаптером с тем
  же интерфейсом.
- Ключ шифрования: `CONNECTOR_SECRETS_KEYS` (список), `cli
  rotate-connector-secrets`; в `production` — обязателен на старте.

**Реализация этапа 2 (25.09, ночь) — Битрикс24, где код уточняет
дизайн.**
- Вид `bitrix24` — режим `per_user` с OAuth: у спецификации вида
  появились `app_credential_fields` (секрет приложения, задаёт админ
  через тот же `PUT .../credentials`) и `user_auth = oauth`
  (`credential_fields` пусты, `PUT .../mine` отвечает 422
  `oauth_required`). Каталог отдаёт `oauth_callback_url` из
  `CONNECTOR_OAUTH_CALLBACK_URL` — админ вписывает его в карточку
  локального приложения на портале.
- `state` OAuth — подписанный JWT с отдельным `typ`, привязанный к
  сотруднику, компании и подключению, срок 10 минут (RISKS №33).
  Обратный вызов публичный, ограничен по IP; ошибка — редирект на фронт
  с кодом и событие аудита `connector.oauth_failed`, не 4xx: браузеру
  сотрудника некуда «упасть». Параметры `domain`, `member_id`,
  `server_domain` от портала не используются — адрес портала только из
  настроек подключения (иначе редирект мог бы увести обмен на чужой
  хост). Сразу после обмена токен проверяется `profile`: сотрудник
  узнаёт о проблеме на месте, а грант получает `external_user_id`.
- Продление токена — по ответу `expired_token`, один повтор, как
  велит документация («не обновлять по расписанию»); новая пара
  сохраняется в грант через `refreshed_credentials` при **любом**
  исходе запуска (старый refresh уже недействителен).
- `AdapterConfigError` — третий класс ошибок адаптера: проблема
  подключения (секрет отвергнут, нет scope, REST недоступен на
  тарифе), а не сотрудника. Останавливает коннектор с кодом, гранты
  не трогает: после исправления настроек сотрудникам не нужно
  авторизоваться заново. Альтернатива — гасить гранты по одному —
  превращала бы ошибку админа в работу для всей компании.
- Модули: `disk` (общий диск и диски групп), `disk_personal` («Мой

  GROUP). Личный диск — отдельный модуль, а не поле формы: у полей
  формы нет типа «да/нет», а список модулей — как раз выбор «что
  читать».
- Редиректы REST не следуются: 301/302 — смена адреса портала, повтор

## 2026-09-26 — Живая проверка Битрикс24: исходящие запросы за прокси, бюджет CPU песочницы, живой тест

**Контекст.** Сеть окружения открыта, тестовый портал доступен. Первый
запуск `connector-check` упал: `OutboundClient` закрепляет IP (защита от
DNS rebinding) и шлёт CONNECT к IP через egress-прокси среды, который
пропускает только по имени. Второй PDF портала (85 страниц) песочница
убила по лимиту 60 с CPU и назвала «повреждённым». Стенд с API и OAuth
без входа в портал не собрать.

**Решение 1 — режим `via_proxy`.** `CONNECTOR_OUTBOUND_VIA_PROXY=true`:
запрос уходит по имени, проверка адреса (https, публичный IP, без
учётных данных в URL) остаётся, закрепление делегируется политике
прокси. Альтернативы: снять `HTTPS_PROXY` для процесса (запрещено
политикой среды, и прокси перевыпускает TLS — прямой выход отвечает
403); резолвить внутри прокси особыми заголовками (нестандартно).
Боевой стенд за корпоративным прокси столкнётся с тем же, поэтому это
настройка, не костыль (RISKS №39).

**Решение 2 — бюджет CPU песочницы = таймаут × ядер.** Разбор PDF
многопоточный: `pymupdf4llm` 1.28 включает модель разметки
`pymupdf-layout` на onnxruntime, которая занимает все ядра. Фиксированный
лимит CPU меньше таймаута по стене, умноженного на ядра, убивает
честный документ раньше таймаута. Лимит передаётся дочернему процессу
из `sandbox.py` (`cpu_budget`), убийство по лимиту (SIGXCPU/SIGKILL)
отдаётся как `timeout`, не `corrupted`. Альтернативы: поднять константу
(на другом числе ядер снова разойдётся); ограничить потоки onnxruntime
(настройки в `pymupdf-layout` нет, один поток удлиняет стену вдвое);
выключить модель (`use_layout(False)`: ×5 дешевле при том же объёме
текста — решение о качестве за командой, RISKS №40).

**Решение 3 — живая проверка как тест.** `tests/live/test_bitrix24_live.py`
запускает `ConnectorSyncService` против настоящего портала с настоящей
песочницей и пропускается без `BITRIX24_TEST_*`. Вебхук кладётся в
грант сотрудника напрямую — обход OAuth только для стенда (через API
такой грант не создать). Повторяемая проверка вместо ручного протокола;
в CI переменных нет — тест пропущен.

**Следствия.** `.env.example` и `DEPLOY.md` §9a — флаг и когда его
включать; `redact` маскирует код вебхука в пути (`/rest/{user}/{code}/`)
— живая запись показала его в `DOWNLOAD_URL`; записи портала лежат в
`tests/connectors/fixtures/bitrix24/live/`.

## 2026-09-28 — Фронтенд MVP: React + TypeScript + Vite, дизайн лендинга, один origin

**Контекст.** Бэкенд MVP готов, интерфейса нет. Лендинг krontoai.ru
(репозиторий demo-kronto) — статичный HTML с ванильным JS: для демо
хватало, для приложения с входом, ролями, формами по спецификациям
коннекторов и опросом статусов — нет. Дизайн лендинга утверждён и
остаётся; после MVP домен переключается на этот репозиторий.

**Решение — стек.** React 19 + TypeScript (strict) + Vite 8, маршруты —
React Router 7, данные — TanStack Query 5, клиент API — `openapi-fetch`
с типами из `openapi-typescript`: схема берётся у бэкенда
(`python -m corp_ed.openapi`), CI падает, если сгенерированные типы
разошлись со схемой. Стили — CSS Modules на токенах лендинга
(`tokens.css`, шрифты Onest и JetBrains Mono, OFL); паттерны окна чата,
ссылок-источников, панели фрагмента и форм перенесены из `sections.css`.
Markdown ответов — `react-markdown` + `remark-gfm` без сырого HTML и
картинок; маркеры `[n]` превращает в кнопки свой плагин remark.
Альтернативы: Next.js (SSR не нужен — всё за входом, лишний сервер в
выкладке); компонентная библиотека (Mantine/MUI — пришлось бы
перекрашивать под лендинг и тащить чужой визуальный язык); Tailwind
(токены уже есть в CSS-переменных, переписывать разметку лендинга в
классы — работа без выигрыша).

**Решение — выкладка.** Статика — отдельный контейнер `web` (nginx без
root, CSP `script-src 'self'`), внешний прокси ведёт `/api` в API, всё
остальное — в `web`. Один origin: без CORS, токен не уходит на другой
домен, а `web` не встаёт в цепочку `X-Forwarded-For` к API.

**Решение — сессия.** Пара access/refresh в `localStorage` одним
ключом: вкладки видят пару, которую получила любая из них. Бэкенд
ротирует refresh и при повторном предъявлении отзывает цепочку, поэтому
обновление идёт под межвкладочной блокировкой (Web Locks) и внутри неё
вкладка сначала перечитывает хранилище. Цена — токен доступен скрипту
страницы (RISKS №44); перенос refresh в httpOnly-cookie — после MVP.
*Заменено 28.09: refresh в httpOnly-cookie — запись «Refresh-токен в
httpOnly-cookie».*

**Решение — dev-режим как стенд e2e.** `LLM_PROVIDER=fake` (ответ из
первой выдержки, эмбеддинги «мешок слов») даёт фронту настоящий API без
ключей Yandex Cloud; e2e в CI (Playwright) идут против API, воркера и
собранного фронта с этим провайдером. Порог расстояния для «мешка слов»
— 0,8 вместо 0,51.

**Следствия.** `frontend/` (README там же), задания `frontend` и `e2e`
в CI, образ `web` в задании `image`; `DEPLOY.md` §1, §5, §11;
`deploy/nginx/kronto.conf`.


## 2026-09-28 — Ответ, когда в документах ответа нет: отказ по умолчанию, источник общего ответа заменяемый

**Контекст.** Досье 3.1 обещает честный отказ, код с 25.09 по умолчанию
давал общий ответ с пометкой (Р1). Вопросы команде Q1–Q4 и ответы
владельца продукта (28.09):
1. Режим новой компании — **отказ**, пока продукт не решит иначе; код
   должен быть готов к расширению и переделке.
2. Общий ответ — **из знаний модели**, поиск в интернете — после MVP;
   тоже готово к замене.
3. В общий ответ — **«Уточните у руководителя или в профильном
   отделе»**.
4. Режим переключает **команда** (`cli set-not-found-mode`); интерфейс
   для админа компании — после MVP при необходимости.

**Решение.**
- `DEFAULT_NOT_FOUND_MODE = NotFoundMode.STRICT` (`domain/types.py`) —
  одно место для ORM, CLI (`create-tenant --not-found-mode`),
  `TenantService.provision` и `FaqService`. Миграция `eaaa2fcbfb12`
  меняет только `server_default`: режим уже заведённых компаний выбирали
  при подключении, его не трогаем (стендов с клиентами нет).
- Источник общего ответа — протокол `GeneralAnswerSource`
  (`services/general_answer.py`): метод `generate(question) → Completion`
  и имя для журнала. Реализация одна — `ModelKnowledgeSource` (промпт ML
  `build_general_messages`, без выдержек). Выбор источника — в
  `get_faq_service` (`api/v1/dependencies.py`); `FaqService` источник не
  знает.
- Пометка в начале и совет в конце — `finalize_general_answer` поверх
  любого источника, **кодом, а не промптом**: модель может потерять
  строку, код — нет (тот же приём, что `ensure_general_prefix`). Совет —
  последним абзацем, `GENERAL_ANSWER_ADVICE`; повторно не дописывается.

- Переключение режима — как было: `cli set-not-found-mode` с событием
  аудита; ручки API для этого нет.

**Как расширять.**
- *Поиск в интернете:* класс с тем же `generate` (поиск → выдержки →
  модель) и выбор в `get_faq_service` по настройке. Если ответу нужны

- *Новый режим* (например, «общий ответ только на общие вопросы»):
  значение в `NotFoundMode`, CHECK `ck_tenants_not_found_mode`
  миграцией, ветка в `FaqService._not_found`.
- *Режим в интерфейсе админа:* ручка `PATCH /tenant/settings` с ролью
  `ADMIN` и тем же `TenantService.set_not_found_mode` (аудит уже есть).

**Альтернативы.**
- Совет в промпте (правило модели) — новая версия промпта ML и замер,
  а маленькая модель теряет обязательные строки (ровно поэтому есть
  `ensure_general_prefix`).
- Перевести в `strict` и существующие компании — клиентов на стендах
  нет, а режим, выбранный при подключении, меняет команда явно.
- Настройка окружения для источника общего ответа сейчас — при одной
  реализации это переключатель без второго положения.

**Цена.** Модуль на 60 строк и параметр `FaqService`. Правило 4 промпта
ML («посоветуй уточнить у ответственных сотрудников») может дать второй

## 2026-09-28 — Временный пароль администратора задаёт оператор, CLI его не печатает

**Контекст.** CodeQL (high, RISKS №42): `cli create-tenant` печатал
сгенерированный временный пароль администратора. Владелец продукта:
«делай как безопаснее и правильнее».

**Решение.** `TenantService.provision(admin_password=…)` — пароль от
оператора, проверка той же политикой, что у пользователей
(`validate_password`, с почтой администратора), `must_change_password`
как было. CLI берёт пароль скрытым вводом дважды (`getpass`) или
первой строкой stdin с `--admin-password-stdin` (как `docker login
--password-stdin`); без терминала и без флага — понятная ошибка, а не
зависание. В выводе, истории терминала и журналах пароля нет.

**Альтернативы.**
- Отклонить алерт как by design — секрет остаётся в выводе терминала и
  прокрутке; проще, но не безопаснее.
- Писать пароль в файл 600 — при `docker compose run --rm` файл внутри
  контейнера исчезает; для CodeQL это хранение секрета открытым текстом.
- Ссылка-приглашение с одноразовым токеном — правильнее всего, но нужна
  почта или другой канал доставки, которого в MVP нет.

**Цена.** Оператор придумывает пароль (удобнее — менеджер паролей
команды). Сотрудникам компании временные пароли по-прежнему выдаёт
админ в интерфейсе (показываются один раз) — это ответ API, не вывод
программы, и CodeQL его не отмечает.

**Статус.** Действует.


## 2026-09-28 — Ссылки-приглашения в компанию

**Контекст.** Досье не говорит, как сотрудники получают учётки; админ
заводил их по одному с временным паролем — на 60 мест это около часа и
пароли в мессенджерах. Владелец продукта: «ссылка-приглашение, которую
можно отправить не обязательно почтой, например в Телеграм; перейдя по
ней, пользователь сразу регистрируется и уже внутри компании, либо
появится плашка „присоединиться к команде“ и он нажмёт „да“».

**Решение.**

## 2026-09-28 — Refresh-токен в httpOnly-cookie

**Контекст.** RISKS №44: пара токенов в `localStorage`, XSS уносит
сессию на 14 дней. Владелец продукта 28.09: закрыть до пилота.

**Решение.**
- Ручки, открывающие сессию (вход, смена пароля, присоединение по
  ссылке, обновление), кладут refresh в cookie `kronto_refresh`:
  `HttpOnly`, `SameSite=Strict`, `Path=/api/v1/auth`, `Max-Age` = срок
  refresh, `Secure` в production. В теле — только access и срок.
- `/auth/refresh` и `/auth/logout` читают cookie; тела у них нет. Выход
  и «выйти везде» стирают cookie. Если `Origin` есть, его хост должен
  совпасть с `Host` (или origin — из `CORS_ALLOWED_ORIGINS`), иначе 403:
  второй рубеж CSRF для браузеров без `SameSite`. Схема не сравнивается:
  за прокси она зависит от доверия к `X-Forwarded-Proto`, и ошибка в его
  настройке не должна разлогинивать всех.
- Фронт: access — в памяти вкладки; после перезагрузки вкладка вызывает
  refresh (cookie приложит браузер), пока он идёт — экран загрузки. В
  `localStorage` — признак «здесь входили» без токенов: без него каждый
  анонимный посетитель слал бы пустой refresh. Обновления под
  межвкладочной блокировкой (Web Locks): cookie общая, и вторая вкладка
  отправляет refresh уже с новой. Вход и выход вкладка сообщает другим
  через `BroadcastChannel`: они сбрасывают данные и, после чужого входа,
  восстанавливают сессию заново.
- Клиенты не из браузера (`corp_ed.stand`, eval ML) берут только access
  из тела; `Origin` они не шлют, проверка их пропускает.

**Альтернативы.** Всё в cookie, включая access (нужен CSRF-токен на
всех ручках, а не на двух); BFF-прокси с сессией на сервере (новый
компонент); `sessionStorage` (та же XSS, плюс вход в каждой вкладке).

**Проверено.** Тесты API (атрибуты cookie, `Secure` в production,
ротация, повтор, чужой `Origin` → 403, выход стирает cookie), Vitest
(восстановление, выход из соседней вкладки, токенов нет в хранилище),
e2e (перезагрузка, атрибуты cookie в браузере), боевой прогон по HTTPS.

**Статус.** Действует.

## 2026-10-01 — Реранкер на контракте ML (BH-32), память диалога включена везде

**Контекст.** 01.10 ML влил в `main` правило реранжирования

## 2026-10-04 — Наша панель: команда заводится только с сервера (этап 8)

**Решение.** «Наша панель» (ТЗ §9) открыта учёткам из `staff_members`.

которая добавила бы человека в команду, нет. Украденная сессия или ошибка

где оператор отвечает за проверку личности. Свою компанию команда из
панели не приостанавливает — токен этой компании перестал бы работать.

**Журнал.** Действия из панели пишутся в журнал компании с
`details.staff_account_id`: у команды нет членства в чужой компании, а
пустой автор («сделала команда из CLI») не отличал бы людей.

**Статус.** Действует.

## 2026-10-04 — Уведомления и поддержка: что куда уходит (этап 9)

**Поддержка.** По ТЗ §8 «Написать в поддержку» — сообщение в
Telegram-бот команды. Но бот у нас «без персональных данных» (DEPLOY.md,
RISKS №50: сервер Telegram за рубежом, текст человека может содержать что
угодно). Поэтому обращение хранится в нашей базе и читается в нашей
панели («Обращения»), а в Telegram уходит только «обращение №…, тема,
код компании». Отвечает команда письмом на почту учётки.

**Недельная сводка — в воркере, не в cron.** Cron на стенде ставит только
первичная настройка сервера (`bootstrap.sh`), выкатка его не обновляет —
новая задача потребовала бы ручного шага на сервере. Воркер обновляется
с каждой выкаткой; раз в неделю на компанию — по отметке `digest.sent` в
журнале, так что перезапуск или второй воркер второй сводки не пришлют.
Неделя без вопросов — без письма: пустое еженедельное письмо учит его не
открывать.

**Письма по умолчанию включены.** Строки настроек нет — администратор
получает всё: остановленное подключение и исчерпанный лимит важнее
лишнего письма. Колокольчик приходит всегда, настройки — только про
почту. Сотруднику письма — только о безопасности (ТЗ §8).

**Статус.** Действует.

## 2026-10-04 — Сайт на одном домене: готовый HTML, песочница, индексация (этап 10)

**Контекст.** ТЗ §1: один домен krontoai.ru, гость видит главную, а не
вход; публичные страницы — готовым HTML для поисковиков; демо с переходом
в песочницу. ТЗ §11: установка на телефон, юридические заготовки.

**Решение.**

- **Предрендер своими силами, без SSR-сервера.** После `vite build`
  вторая сборка `--ssr` рисует страницы сайта (`site/prerender.tsx`), а
  `tools/prerender.mjs` кладёт их в `dist/<адрес>/index.html` с
  заголовком, описанием, каноническим адресом и og-тегами. Рисуются те же
  маршруты, что видит гость в браузере: главная и «Помощь» — через
  `handle.guest` маршрутов приложения в `RequireAuth`. В браузере
  приложение не «оживляет» готовый HTML (hydrate), а рисует поверх
  (`createRoot`): у вошедшего на `/` другое содержимое, и сверять разметку
  не с чем. Чтобы у него не мигал сайт, скрипт в `<head>` по признаку
  входа ставит `data-session`, и готовый HTML скрыт до отрисовки

## 2026-10-04 — «Выйти» действует сразу; прежний пароль не вернуть

**Контекст.** Проверка стенда (`STAGE-TESTING.md`, раздел 6) нашла две
вещи для этапа безопасности. После «Выйти» и «Завершить» в списке
сеансов access-токен этого входа работал до своего срока (до 15 минут):
отзывалась только цепочка refresh-токенов. После сброса пароля (по
ссылке или командой из CLI) можно было поставить прежний — тот, который
и сбрасывали, потому что его мог узнать кто-то ещё.

**Решение.**
- В access-токене — `sid`, сеанс: `family_id` цепочки refresh-токенов
  входа. На каждом запросе — поиск отозванной записи этой цепочки (по
  индексу `family_id`, одна строка); нашлась — 401. Отдельного чёрного
  списка нет: признак — те же отозванные refresh-токены. «Выйти»
  закрывает сеанс из токена, а не только из cookie.
- Отозванные refresh-токены не удаляются раньше, чем истекут access-токены;
  сейчас их не удаляет ничто, кроме удаления учётки.
- `accounts.previous_password_hashes` — хеши трёх прежних паролей. Смена,
  сброс по ссылке и временный пароль из CLI сверяют новый пароль с
  текущим и ими. Пересчёт хеша при входе (тот же пароль) историю не
  трогает. Отказ — после второго фактора: «пароль уже был» говорит о
  прежних паролях.

**Альтернативы.** Чёрный список `jti` в Redis до истечения токена:
отдельное хранилище и отказ при недоступном Redis — а база и так
читается на каждом запросе (учётка, версия). Access на 5 минут вместо
15: окно меньше, но не ноль, и обновлений втрое больше. Сверка только с
текущим паролем при сбросе: не закрывает «временный от команды → прежний».
Периодическую смену пароля не вводим (ASVS, NIST SP 800-63B): история
срабатывает, только когда пароль меняют сами.

**Последствия.** Переход в другую компанию тоже закрывает прежнюю
цепочку — старый токен перестаёт действовать сразу; фронт уже заменяет
токен и при 401 один раз обновляет его. Выкатка: токены без `sid`
отклоняются — открытые вкладки один раз обновят токен по cookie.
Кто уже завладел учёткой, может проверить догадку о прежнем пароле
сменой пароля — не больше 5 попыток за 15 минут и только пока догадка в
истории.

**Статус.** Действует.

## 2026-10-04 — Копия бэкапа вне сервера: age и объектное хранилище

**Контекст.** `DEPLOY.md` §8 требует хранить дамп не меньше 30 дней вне
хоста, зашифрованным; до первого клиента это обязательно. На стенде
дамп лежит только на самом сервере.

**Решение.** `deploy/stage/offsite.sh` — на стенде и на бою.
- Дамп шифруется `age` открытым ключом владельца. Закрытый ключ
  создаётся на компьютере владельца и хранится в менеджере паролей; на
  сервер, в чат и в репозиторий он не попадает. Ни хранилище, ни тот, у
  кого окажется ключ от бакета, копию не прочтут.
- Отправка — `rclone` (S3, объектное хранилище Selectel), настройки — в
  `/etc/kronto/offsite.env` (root:deploy, 640); `age` и `rclone` — пакеты
  Ubuntu.
- Сверка: копия скачивается обратно, sha256 шифротекста сравнивается с
  отправленным (ETag не годится: при составной загрузке это не MD5
  файла). Расшифровку и подъём — раз в квартал владелец своим ключом.
- Ключу сервера — чтение и запись в один бакет, без удаления: срок
  хранения задаёт правило бакета (30 дней). Тот, кто завладеет
  сервером, не сотрёт старые копии; перезапись закрывает
  версионирование бакета, если оно есть. Для хранилища без правил —
  `OFFSITE_KEEP_DAYS`, тогда ключу нужно и удаление.
- Ночью — после проверки восстановления (`backup.sh`); не ушло — неудача
  задачи `backup`, тревога. После выкатки — строка в проверке стенда;
  не настроено — `--`, проверку не роняет.

**Альтернативы.** Шифрование `rclone crypt` или ключом на сервере:
проверка расшифровки шла бы автоматически, но ключ лежал бы рядом с
базой, а с потерей сервера терялся бы и он. GPG — тяжелее в настройке,
пользы для одного получателя нет. Копия на второй сервер по SSH —
второй сервер нужно держать и защищать.

**Статус.** Код готов; включается, когда владелец заведёт ключ и бакет
(`STAGE.md` §4.11). На бою — обязательно до первого клиента.

## 2026-10-04 — Ответ не держит базу, пока пишет модель; перегрузка — «busy»

**Альтернативы.** Отдел только от администратора — проще, но против ТЗ

администратором — строже (закрывает и случай «папку открыли отделу, куда
уже записались сами»), но это новая заявка и экран; по решению владельца.
Запрет «поделиться» диалогом с закрытыми документами — сотрудник не
понял бы, почему нельзя.

отдела администратором (следующая запись). Скрытие ответа в общей

## 2026-10-06 — Отдел открывает закрытые папки после подтверждения администратором

**Контекст.** Запрет «в отдел с закрытой папкой записывает только
администратор» (запись выше) не закрывал случай: люди сами выбрали
обычный отдел, а потом администратор открыл ему закрытую папку — они
получали доступ. Владелец 06.10 выбрал вариант Б: выбор сотрудника
вступает в силу для закрытых папок после подтверждения.

**Решение.** У членства — признак «отдел подтверждён»
(`users.department_confirmed`). Закрытая папка открыта человеку, только
если его отдел совпадает с отделом папки **и** подтверждён;
администраторам — все папки, как раньше.
- Отдел, назначенный администратором (коллеге или себе), подтверждён
  сразу. Выбранный самим сотрудником — сразу виден в профиле и
  справочнике (ТЗ §4 не меняется), но ждёт подтверждения. Тот же отдел,
  что уже стоит, ничего не меняет; снять отдел — сразу.
- В «Сотрудниках» — блок «Ждут подтверждения отдела»: «Подтвердить»,
  «Отклонить» (отдел снимается). `POST /users/{id}/department/confirm`
  и `…/reject`, в журнал; человеку — колокольчик, без письма (ТЗ §8).
- Администраторам — уведомление, только если выбранному отделу уже
  открыта закрытая папка (колокольчик; письмо — по настройке «заявки»).
  Выбор обычного отдела не шумит: человек просто в списке ждущих.
- В списке отделов — сколько людей ждут подтверждения; окно закрытой
  папки показывает это администратору.
- Миграция: у всех, кто уже в отделе, отдел — неподтверждённый.
  Администраторы подтверждают заново; на стенде — только тестовые
  данные, сквозная проверка переводит сотрудника в отдел от имени
  администратора.

Порядок работы — как в этапе «чёрного ящика»: сначала ТЗ и контракт API
(коммит без логики), потом тесты отдельного агента, видевшего только
ТЗ, схему API и описание обвязки, потом код.

**Альтернативы.** Две колонки «отдел» и «заявка на отдел» — отдел не
виден в справочнике до подтверждения, против ТЗ §4. Уведомлять
администраторов о каждом выборе отдела — при подключении компании это
десятки писем без действия. Отдел только от администратора — против ТЗ.

**Статус.** В коде.


## 2026-10-06 — Прошлые отказы не показываются модели ответа

ML (`prompts/dialogue.py`, `prompts/faq.py`) не менялись; ML-инженеру —

промпт ML, и он уже так написан, а модель всё равно повторяла отказ.
Сбрасывать историю при смене прав — права меняются и без события в
диалоге (файл загрузили, папку открыли).

**Статус.** Действует.

## 2026-10-07 — Права проверяются в момент действия, а не по прежнему состоянию

**Контекст.** Внутреннее ревью кода 06–07.10 (отчёт — у владельца, в
репозиторий не кладётся). Общий вывод: правила доступа должны
одинаково работать у соседних действий и пересчитываться при каждом
показе, а не опираться на то, что было верно раньше.

**Решение.**
- **Второй фактор.** Подключить приложение или ключ доступа — только с
  паролем, как и отключить. У всех действий «подтвердите паролем»
  (второй фактор, резервные коды, удаление ключа и учётки, смена почты)
  общий счётчик попыток на учётку: 10 за 15 минут. Команда kronto может
  снять второй фактор с сервера: `cli reset-second-factor --email …`
  (приложение, ключи, резервные коды, доверенные устройства, все сеансы).
- **Подключение коннектора по OAuth** завершается только в том браузере,
  что его начал: httpOnly-cookie на путь обратного вызова, в state — её
  отпечаток. Новое подключение в том же браузере заменяет прежнее.
- **Подтверждение отдела** — с `department_id`, который видел
  администратор; сотрудник успел сменить отдел — 409 (ТЗ §7).
- **Свои диалоги после снятия доступа.** Ответ по документу, к которому
  у сотрудника больше нет доступа (документ есть, но не виден), в своём
  диалоге показывается как «нет доступа», как по общей ссылке, и не идёт
  в историю для модели — ни в чате, ни в памяти `/faq/ask` (в Redis
  теперь хранятся и документы ответа). Удалённый документ так не
  скрывается: это не снятие прав.
- **Почта.** Незаверенная регистрация адрес не держит и при смене почты
  и откате «это не я» (как уже при повторной регистрации): заглушка
  удаляется, адрес переходит учётке, доказавшей владение. Коды входа на
  почту — один счётчик на адрес (5 в час) для нового входа и «прислать
  ещё раз».
- **Завершить сеанс** из списка сеансов забывает и «запомненные»
  устройства, как «выйти везде».
- **Песочница сайта** отвечает только в компании, где кроме её учётки
  никого нет; `cli demo setup` отказывается от кода компании с людьми.
  Скрытое поле формы проверяется до общего суточного лимита.
- **Общая ссылка на диалог** только читает (не меняет диалог автора) и
  ограничена по частоте.

**Альтернативы.** Подтверждать новый фактор действующим фактором вместо
пароля — у первого фактора его нет. Привязать доверенное устройство к
сеансу — нужна миграция, а выигрыш мал: завершают сеанс редко и обычно
из-за подозрения. Для памяти `/faq/ask` — сбрасывать её при смене прав:
права меняются без события в диалоге (папку закрыли, человека убрали из
отдела).

**Статус.** Действует.

## 2026-10-07 — Разбор файлов, внешние запросы, деплой и логи (часть 2 ревью)

**Контекст.** Вторая часть исправлений по внутреннему ревью 06–07.10
(первая — запись выше).

**Решение.**
- **Office XML** (xlsx, pptx и все части docx до mammoth) разбирается
  `defusedxml` с запретом DTD: любой DTD отклоняется парсером — в любом
  месте пролога и в любой кодировке (`corrupted`). Байтовая проверка
  первых 4 КБ убрана. Зависимость `defusedxml` (PSF-2.0).
- **Zip-контейнеры:** число записей считается до того, как `zipfile`
  строит каталог (запись EOCD/ZIP64 и подсчёт сигнатур записей —
  `zipfile` объявленному числу не верит); размеры и степень сжатия —
  проверка по объявленным значениям, best-effort; настоящий потолок —
  память и таймаут песочницы. Ответ песочницы — не больше ~12 МБ.
- **Внешние запросы к системам клиентов:** тело ответа API читается
  потоково, потолок 20 МиБ (`response_too_large`); при редиректе на
  другой хост не уходят ни учётные заголовки, ни параметры, ни тело;
  идентификаторы в путях API кодируются одним сегментом; коды ошибок
  источников приводятся к `[a-z0-9_]{1,64}`; адреса NAT64 и
  IPv4-совместимые IPv6 отвергаются явно. Группа Confluence, имя
  которой сервер не принимает (400), пропускается, как недоступная.
- **Логи:** значения параметров SQL не попадают ни в текст ошибок
  (`hide_parameters`, в том числе у миграций), ни в лог; поля с почтой,
  телефонами и адресатами скрываются; ошибка модели пишется статусом и
  классом, без текста провайдера. В боевом режиме `MAIL_BACKEND`
  `console`/`memory` запрещены — воркер не стартует.
- **Настройки подключений** читают общую `ENVIRONMENT` (раньше —
  `CONNECTOR_ENVIRONMENT`, и боевые проверки ключей и https не
  включались).
- **nginx на хосте:** HSTS на каждом ответе по HTTPS, неизвестное имя —
  444/отказ TLS, `/metrics`, `/docs`, `/openapi.json` — 404,
  `proxy_read_timeout` для `/api` — 210 с. Действует после повторного
  `bootstrap.sh` на сервере.
- **Деплой:** `deploy.sh` останавливается, если в `.env` не
  `ENVIRONMENT=production` или API отдаёт `/openapi.json` не 404;
  значения из `.env.example` переносятся без `sed`; скрипты стенда пишут
  логи и дампы с правами только владельца.
- **CI:** PR из другого репозитория (форка) всегда идёт на машины GitHub.
- **Фронтенд:** переход после входа — только на свой путь; ссылки и
  адреса с сервера — только http(s); карты кода не связаны со сборкой;
  `X-Frame-Options: DENY`; панель источника возвращает фокус; песочница
  объявляет только готовность ответа.
- **Подсказки «частых вопросов»** считаются по документам, видимым
  смотрящему; **чистка** удаляет истёкшие refresh-токены (через 30 дней
  после срока), шаги входа, ссылки из писем и доверенные устройства.
- **Подсчёты по компании** называют компанию в запросе сами: в
  `count()` без сущности фильтр сессии не срабатывает.

**Отложено.** Картинки в песочницу (RISKS №59), сеть и файлы песочницы
(№60) — сделано 09.10, запись «Решения владельца по итогам ревью».

**Статус.** Действует.

## 2026-10-09 — Данные после ухода и расторжения, два согласия, юридические страницы

**Контекст.** Проекты юридических документов (оферта, соглашение,
политика, согласия, возвраты, cookies — проверит юрист) обещают то,
чего код не делал: уход из компании и удаление учётки только помечали

ст. 9 152-ФЗ).

**Решение.**
- **Ушёл из компании или удалил учётку** — через 30 дней ночной `cli
  purge` удаляет его диалоги целиком, уведомления, токены подключений и

  обрабатывать снова; повторное вступление его сбрасывает). Телефон,
  Telegram и фото — в учётке и уходят вместе с ней сразу.
- **Удаление данных компании** — `cli delete-tenant` и кнопка в панели:

  песочница и не своя. Остаются обезличенные заказы, начисления и
  списания кредитов (бухгалтерия), журнал аудита до своего срока (его
  удалить раньше не даёт триггер базы), учётки людей; строка компании —
  обезличенный след с `data_deleted_at`. Токены сотрудников отзываются у
  провайдеров после commit (best-effort).
- **Два согласия при регистрации** — отдельные неотмеченные галочки:
  соглашение (`terms_accepted_at`, `terms_version`,
  `REGISTRATION_TERMS_VERSION`) и согласие на обработку ПДн
  (`consented_at`, `consent_policy_version`). Заявка на созвон ссылается
  на текст согласия на созвон (`/consent-call`).
- **Уведомления команде в Telegram** называют компанию коротким id
  (8 символов UUID), а не кодом: код — транслитерация названия, у
  ИП это фамилия. Тот же id — рядом с компанией в панели.
- **Юридические страницы** — тексты проектов с плашкой «Проект —
  проверяется юристом»; реквизиты — одна константа (`documents.ts`),
  версии сайта и сервера сверяет тест. Новые страницы: оферта, возвраты,
  cookies, согласие на созвон.
- **Тексты сайта о Yandex Cloud** — только проверяемое: запросы с
  отключённым журналированием данных у провайдера
  (`x-data-logging-enabled: false`), не для обучения моделей.

**Открыто.** Комментарий администратора к заявке на тариф по-прежнему
уходит в Telegram (команде негде его прочесть иначе) — решить; токены

описаны оплата картой и доплата за места — до их включения не снимать
плашку «Проект».

**Статус.** В `main`.


## 2026-10-09 — Оплата через Точку: подписка счётом или картой, вебхук банка, акты

**Контекст.** ИП открыт, счёт — в Точке (решения владельца 09.10: УСН
6 % без НДС; В5а — Точка; В6в — и карта, и счёт, год и квартал со
скидкой; В7 — PDF-акт, ЭДО позже; В8а — места добавляются сразу с
пропорциональной доплатой, сокращаются со следующего периода; А4 —
пакеты по счёту, карта следом). Исследование — в истории сессии
(сравнение банков и эквайринга).

**Решение.**
- **Всё за флагом** `PAYMENTS_PROVIDER` (`none` по умолчанию): без банка
  работает прежний путь — счёт выставляет команда, оплату отмечает в
  панели. Код провайдера — за протоколом (`services/payments/`), Точка —
  первая реализация.
- **Подписка**: тариф × места × период (месяц; квартал −5 %, год −10 %,
  `PAYMENTS_DISCOUNT_*`). Счётом юрлицу — любой период; картой — только
  помесячно, подписка Точки «по графику» с чеком. Период начинается в
  день оплаты первого счёта. Счёт на продление — за 5 дней до конца
  периода, напоминание в день окончания, через 7 дней — `overdue`,
  одно сообщение команде и уведомление администраторам; **компания не
  блокируется** автоматически. Приостановленной компании счета на
  продление и просрочка не идут (сверка с банком и акты — идут).
- **Счета**: через API банка (PDF — банка, при сбое — свой шаблон с
  суммой прописью); номер сквозной по всем компаниям (`KR-00042`), он же
  в назначении платежа — по нему вебхук находит счёт.
- **Зачисление по вебхуку**: тело — JWT, подпись RS256 публичным ключом
  банка (`alg` закреплён); перевод засчитывается после сверки суммы и
  ИНН и повторного запроса статуса счёта в банке; оплата по ссылке —
  только `APPROVED` с проверкой операции в банке; повтор доставки и
  повторный платёж гасятся уникальными ключами. Не сошлось — ручной
  разбор в панели («Оплата»). Потерянный вебхук ловит сверка раз в 15
  минут.
- **Карта**: пакеты и доплаты — разовая ссылка с чеком (`usn_income`,
  без НДС, `full_prepayment`, `service`). Сумма автосписания в середине
  периода не меняется (фискализация `Charge Subscription` не
  подтверждена): доплата за места — разовой ссылкой; изменилась сумма к
  продлению — график отменяется, администратору — новая ссылка.
- **Места**: добавление при оплаченном периоде — сразу, доплата
  пропорционально оставшимся дням (сегодня считается) по всем
  оплаченным периодам; сокращение — `next_seats`, с начала следующего
  оплаченного периода.
- **Акты**: раз в месяц — по счетам, оплаченным в прошедшем месяце (год
  вперёд — один акт в месяц оплаты). С реквизитами — акт создаёт банк и
  шлёт на почту для документов; иначе — свой PDF, администраторам —
  колокольчик и письмо со ссылкой. Письма об оплате подчиняются
  настройке писем «Кредиты».
- **Реквизиты покупателя** — в настройках компании (ИНН с контрольными
  цифрами, КПП — не у ИП); реквизиты продавца — только в
  `BILLING_SELLER_*`, не в коде.
- **Сертификат Минцифры** (сервер банка подписан им) — в образе,
  отпечаток сверяется при сборке; доверяет ему только клиент банка.
- **Таблицы под RLS** — реквизиты, подписки, счета, акты;
  `invoice_refs` (только идентификаторы) и `payment_events` (разбирает
  команда) — без RLS: вебхук приходит без компании, компания ищется по
  номеру счёта.
- **Сообщения команде** — короткий id компании, сумма и код причины,
  без реквизитов и назначения.
- **Удаление данных компании после расторжения**: счета, акты, номера
  счетов и платежи из банка остаются (бухгалтерия, 5 лет; заметка
  команды к платежу стирается), реквизиты и подписка удаляются.
  Автосписание по карте сначала отменяется в банке; банк не ответил или
  не подключён — данные не удаляются (`card_cancel_failed`,
  `card_subscription_active`).

**Подтвердить владельцу.** Сквозная нумерация счетов; акт по дате
оплаты, а не по оказанию услуги; отдельная настройка писем для актов
(сейчас — общая с «Кредитами»); карта только помесячно.

**Открыто.** Вопросы к Точке до включения: чек на `Charge
Subscription`, смена суммы подписки без повторного ввода карты, ставка
СБП и MCC, вебхук на каждое плановое списание, отдельный `Order[]` на
каждое списание (RISKS №73), создание акта без привязки к счёту. Доход
2025 против порога НДС 20 млн ₽ — если выше, с 2026 года меняются чеки,
счета и акты.

**Статус.** В `main`.

## 2026-10-09 — PDF, DOCX и PPTX — до 100 МБ

**Контекст.** Лимит файла был 25 МБ для всех форматов — при ручной
загрузке и в коннекторах. Для текстовых документов это тысячи страниц, но
презентации и PDF с фотографиями часто весят десятки мегабайт, хотя текста
в них килобайты: картинки мы не читаем (OCR нет). Такие файлы
отклонялись целиком, а коннектор молча пропускал их с диска клиента.

**Решение (владелец продукта, 09.10).**
- pdf, docx и pptx — до 100 МБ (`MAX_LARGE_UPLOAD_BYTES`,
  `CONNECTOR_MAX_LARGE_DOCUMENT_BYTES`); xlsx, doc, txt, md, вложения к
  вопросу, аватар и логотип — по-прежнему 25 МБ.
- Лимит выбирается по расширению (`ingest.extract.max_file_bytes`);
  формат дальше подтверждается содержимым, поэтому `.txt`, названный
  `.pdf`, получит большой лимит, но не пройдёт сигнатуру, а zip под видом
  docx/pptx — проверки контейнера (200 МБ после распаковки, 5 000
  записей, степень сжатия).
- Потолок тела: middleware — 100 МБ только на `/materials/upload`,
  nginx — `client_max_body_size 101m` только в `location =
  /api/v1/materials/upload`; остальные ручки — как были.
- Больших загрузок в одном процессе API одновременно не больше
  `MAX_CONCURRENT_LARGE_UPLOADS` (2), остальные ждут: файл целиком лежит в
  памяти, пока идёт разбор, и копируется в процесс разбора (контейнер API
  — 2 ГБ).
- Коннектор скачивает до 100 МБ при любом формате (`download_limit_bytes`)
  и проверяет лимит формата после скачивания.

**Проверено.** Песочница разбора на синтетических файлах с картинками:
pptx 124 МБ — 0,9 с, PDF 150 МБ — 1,6 с, docx 112 МБ — 1,4 с; текст
извлечён полностью, память и CPU песочницы (1,5 ГБ, 90 с) не задеты.

**Альтернативы.** Один лимит 100 МБ для всех форматов — большой xlsx или
txt — это реально много текста и эмбеддингов, а не картинки; отдельная
загрузка по частям — сложнее, не нужна при 100 МБ.

**Цена.** До 2 × 100 МБ файла в памяти API на процесс; ожидание очереди
при одновременной загрузке больших файлов разными администраторами.
Коннектор может скачать большой xlsx и только потом отказать.

**Статус.** В ветке, не в `main`. На сервере — повторный `bootstrap.sh`
(новое правило nginx).
