## 1. Коротко

- Ассистент отвечает сотруднику **по документам его компании**. У каждого
  утверждения стоит ссылка `[n]` на выдержку, из которой оно взято.
- Если ответа в документах нет, ассистент отвечает из общих знаний, но
  первой строкой **прямо пишет «В документах компании ответа нет»**. Это
  режим по умолчанию (решение Артёма 29.09); строгий отказ — настройка
  компании. В продукте — с 30.09 (BH-29).
- Ассистент **понимает уточняющие вопросы** («а для УМНИК?»): переписывает
  их в самостоятельные по истории диалога. В продукте с 30.09 (BH-28),
  3 пары по замеру ML.
- Документ перед поиском **чистится и режется на фрагменты по смыслу**: по
  разделам и предложениям, а не по числу символов. Каждый фрагмент знает,
  из какого он раздела.
- Модели выбраны замерами. Ответы даёт **Alice AI LLM Flash**, поиск идёт
  по эмбеддингам **text-embeddings-v2 размерности 768**. Эта пара вдвое
  дешевле и заметно точнее прежней.
- Есть **отчёт о пробелах**: система находит темы, по которым сотрудники
  спрашивают, а документов нет, и группирует такие вопросы.
- Есть **стенд оценки качества (eval)**. Любое изменение можно измерить и
  проверить, что разница не случайна.
- **Настройки проверены на золотом наборе** (25.09, проверен людьми):
  крошки с названием документа, фрагменты 400/50, 5 фрагментов в ответ,
  порог 0.51 (с 30.09 — 0.59), только векторный поиск. Из шести опробованных улучшений
  подтвердилось одно (крошки), остальное — шум или хуже; в продукте
  менять ничего не нужно. Финал — на отложенной половине набора 11–12.10.
- **30.09:** вопросы по таблицам находятся (13 из 13), но три отсекает
  порог 0.51 — с 30.09 порог **0.59** (решение Артёма, 5.13).
  Облегчённый реранкер даёт тот же прирост поиска, что тяжёлый, за 1,8 с
  вместо 20 с — в MVP за флагом, по умолчанию выключен (Артём 01.10,
  BH-32; 5.12).
- **01.10:** форматы .xlsx, .pptx и .doc приняты ML и встроены (BH-33…35)
  (5.15). Сноски стоят на месте ссылки, верхний индекс, набранный
  вручную, больше не портит числа. Память диалога: история из 3 реплик
  (5.16). Финальный прогон на закрытых вопросах — по протоколу,
  записанному заранее.

## 2. Что умеет система

Как проходят документ и вопрос. Колонка «Где» показывает, кто делает шаг:
ML написал функцию, бэкенд встроил её в сервис. Статус — на 01.10; всё
встроенное — в `main` (PR #15 влит 29.09).

### 2.1. Загрузка документа

| Шаг | Что происходит | Где | Статус |
|---|---|---|---|
| Приём файла | docx, PDF с текстовым слоем, txt, md. Файл разбирается в изолированном процессе без доступа к ключам. Плюс .xlsx, .pptx, .doc — разбор ML | бэкенд | ✅ в `main`, новые форматы — с 01.10 (BH-33…35, флаг `INGEST_EXTRA_FORMATS`) |
| Файл → Markdown | docx: mammoth + markdownify. PDF: pymupdf4llm, страницы разделены символом `\f`. .xlsx, .pptx, .doc — свой разбор ML без сторонних библиотек (`ingest/xlsx.py`, `pptx.py`, `doc.py`) | бэкенд, библиотеки и разбор новых форматов — ML | ✅; верхний индекс у .docx — ⏳ BH-36 |
| Очистка текста | колонтитулы и номера страниц, оглавление, таблицы → строки «ключ: значение», сноски — на место ссылки, верхний индекс, ссылки, мусорные символы (11 шагов) | ML: `ingest/preprocess.py` | ✅ |
| Нарезка | разделы по заголовкам → предложения → фрагменты по 400 токенов с перекрытием 50. У фрагмента есть «хлебные крошки»: «Документ > Раздел > Подраздел» | ML: `domain/split.py` | ✅ |
| Эмбеддинги | text-embeddings-v2, размерность 768, фоновая очередь с ограничением частоты | бэкенд | ✅ |

## 4. Метрики: что это и что они значат для нас

### Поиск — находит ли система нужный фрагмент

- **Hit@K** — доля вопросов, у которых правильный фрагмент попал в первые
  K результатов. Для нас главное **Hit@5**: модель видит 5 фрагментов.
  Если нужного среди них нет, модель ответит «ответа нет» или ошибётся.
- **MRR** (mean reciprocal rank) — насколько высоко стоит правильный
  фрагмент. Первое место — 1, второе — 0.5, третье — 0.33, не нашёлся —
  0; среднее по вопросам. Растёт MRR → правильный фрагмент чаще первый →
  модели проще.
- **Правильный фрагмент** — из нужного документа и содержит цитату-
  доказательство (`evidence`). Если цитаты нет — фрагмент из нужного
  раздела.

### Отказ — не выдумывает ли система

Ответ на вопрос вне документов — это выдумка или общее знание, выданное за
документ. Отказ на вопрос по документам — ответ, который потерян.

- **Precision отказа** — из всех отказов доля правильных (ответа в
  документах действительно нет). Низкая → ассистент зря говорит «не
  нашёл», сотрудник уходит без ответа.
- **Recall отказа** — из всех вопросов вне документов доля тех, где
  ассистент отказал. Низкий → **выдумки**, самое опасное для доверия.
- **F1 отказа** — одно число из двух предыдущих. Цель ≥ 0.9, сейчас 0.983.
- **Ложных ответов вне корпуса** — сколько вопросов вне документов модель
  «ответила по документам». Цель — 0. Сейчас 1 из 32 «близких» вопросов:
  это подмена программы, см. раздел 6.
- Общий ответ с пометкой считается отказом: он не из документов.

### Ответ — правильно ли

- **Правильность** — человек (или откалиброванный судья) ставит 2 — верно,
  1 — частично, 0 — неверно. Планка pre-MVP: **≥ 80 % верных по корпусу и
  ≤ 20 % ложных ответов вне корпуса**.
- **Неверная ссылка** — ссылка `[n]` на выдержку, которая не подтверждает
  утверждение. Считается в процентах от утверждений и от ответов. Для нас
  это доверие: сотрудник открыл ссылку, а там другое — он перестаёт
  верить всем ссылкам.

### Деньги и скорость

- **Цена ответа, ₽** — токены на входе и выходе по тарифу AI Studio.
- **Задержка p50 / p95** — медиана и время, в которое укладываются 95 %
  ответов. p95 важнее: сотрудник запоминает долгие ответы.

### Отчёт о пробелах

- **Precision** — из тем, помеченных как «пробел», доля настоящих:
  документа правда нет. Низкая → клиенту советуют писать документы,
  которые у него уже есть.
- **Recall** — из настоящих пробелов доля найденных. Низкий → отчёт
  молчит о реальных дырах.
- **Чистота кластера** — доля вопросов в группе про одно и то же.

### Как читать сравнения: «лучше» или «шум»

Любая разница двух вариантов проверяется `eval.compare` двумя способами:
- **95 % доверительный интервал (CI)** — диапазон, в котором с 95 %
  уверенностью лежит настоящая разница. Считается бутстрепом: тысячи раз
  случайно пересобираем набор вопросов и смотрим, как гуляет разница;
- **p-value** — вероятность увидеть такую разницу, если на самом деле
  разницы нет. Считается перестановочным тестом.

**«B лучше A»** — только если CI не содержит ноль **и** p < 0.05. Иначе
пишем «в пределах шума» и решение не принимаем. На 20–40 вопросах шум
большой: интервал около ±20 п. п.

### Согласие судьи с человеком

- **Совпадение** — доля ответов, где LLM-судья поставил ту же оценку, что
  человек.
- **Каппа Коэна** — то же, но за вычетом случайного совпадения. Если почти
  все ответы верные, судья, который всегда пишет «верно», получит
  совпадение 90 % и каппу 0.
- Судье верим при **≥ 40 ручных оценках, совпадении ≥ 85 % и каппе ≥ 0.6**.

### 5.15. Форматы файлов: .xlsx, .pptx и .doc (Р-5, 01.10)

Решение Артёма: новые форматы по одному, следующий — после проверки
качества предыдущего, статистика по каждому (`ml-formats.md`). Первый —
.xlsx. Пять вымышленных книг и то же содержание в .docx, 25 вопросов:

| | .xlsx | .docx (шапка помечена / нет) |
|---|---|---|
| «ключ: значение» в строке таблицы | **100 %** | 91 % / 0 % |
| балл судьи (24 вопроса по документам) | **1,58** | 1,42 / 1,42–1,50 |

.xlsx не хуже .docx (p = 0,51), поиск по золотому dev не изменился —
**формат принят ML**, бэкенду — BH-33 (без новых зависимостей). Находка:
таблицы Word без помеченной шапки теряли ключи (0 %) — починено в
`preprocess` тем же днём (91 %, как с пометкой; в длинной таблице ключи
теперь во всех фрагментах).

**.pptx — тоже принят 01.10.** Четыре вымышленные презентации и то же в
.docx, 24 вопроса: ключи таблиц 28 / 28 (у .docx 20 / 28), значения
диаграмм с подписями 12 / 12 (у .docx 0 / 12), заметки докладчика и
порядок слайдов на месте; ответы — как у .docx (1,83), золотой dev не
изменился. Бэкенду — BH-34.

**.doc — тоже принят 01.10.** Проверен на файлах, которые сохранил сам
Word: текст совпадает с независимой программой antiword, ключи таблиц
100 % (у .docx 91 %), оглавление и удалённый рецензентом текст
выбрасываются; ответы не хуже .docx (1,70 против 1,65 на 60 вопросах).
Бэкенду — BH-35. Все три формата Р-5 приняты ML.

**Сноски — на месте ссылки (01.10).** Раньше конвертеры клали сноски в
конец документа: условие из сноски попадало в чужой фрагмент, модель не
видела, к чему оно. Теперь `preprocess` ставит текст сноски на место
ссылки («(сноска: …)»; у заголовка и шапки таблицы — абзацем после
строки), копия всех сносок остаётся в конце — для .docx, .doc и Markdown.
На 11 вопросах с ответом только в сноске поиск находит нужный фрагмент
первым во всех 11 (было MRR 0,64 и 0,54, разница вне шума), балл судьи
1,18 → 1,64 (.docx) и 1,00 → 1,73 (.doc) — в ту же сторону, но на 11
вопросах ещё шум; золотой dev не изменился (`ml-formats.md`).

## 6. Что не сделано и риски

- **Встраивание бэкендом** — снято 30.09–01.10: BH-28…BH-35 в `main`.
  Ждёт только BH-36 (верхний индекс в .docx) — после PR ML #46.
- **Порог 0,59 отсекает часть ответов** (04.10): на стенде бэкенда — 13
  из 140 вопросов с ответом, на наборах ML — 5 из 120. Предложение —
  отдельным PR («Порог: развести роли»), решение — после финала.
- **Разбор PDF под AGPL** (П-12): pymupdf и pymupdf4llm нельзя держать
  в закрытом репозитории без лицензии Artifex. Замена на библиотеке с
  разрешительной лицензией — после финала (промежуточный итог —
  отдельным PR).
- **Финальные числа — на holdout** (19 вопросов, один прогон 04.10):
  ✅ см. таблицу выше и `ml-report.md`, «Финал на holdout». Протокол
  записан 01.10, до прогона
  ([`ml-holdout-protocol.md`](ml-holdout-protocol.md)). На dev всё решено
  (5.9), но dev маленький (39 вопросов): различимы только крупные эффекты.
  «8 фрагментов» и «600/50» выглядели чуть лучше и вернутся на пересмотр
  по живым логам.
- **Судья откалиброван, но строже человека.** По 39 ручным оценкам
  Артёма (26.09) совпадение 89 %, каппа 0.77 — планка пройдена. Четыре
  расхождения разобраны по документам: в двух ошибся судья (снизил за
  форму), в двух — человек (пропущенный шаг); после исправления — 95 %,
  каппа 0.89. Судья ни разу не завысил, поэтому числа по ответам в 5.9 —
  нижняя граница.
- **Ложные посылки и сравнения** — главный источник ошибок, и это поиск
  (5.9). Фильтр по программе не помогает (проверено). Реранкер лечит
  часть таких вопросов (5.12) — встраивать ли, решает Артём; дальше —
  гибрид только для имён собственных, ответ с цитатой.
- **Память диалога**: `RAG_HISTORY_TURNS=3` по замеру 01.10 (5.16). Уточнение с
  местоимением без предмета («а что это за проект?») переписывается не
  всегда верно; попытка `condense-v2` это не исправила и начала
  переписывать самостоятельные вопросы — остаётся `condense-v1`.
- **Устаревшие общие знания** в общем ответе — см. 5.5.
- **Таблицы**: в PDF колонки иногда перемешиваются; вопросы по таблицам
  отсекал порог 0.51 — с 30.09 порог 0.59 (5.13). Строку таблицы поиск
  иногда ставит далеко от вопроса (4 из 24 на наборе .xlsx, у .docx так
  же). Проба «строка — отдельный фрагмент» (ML-4б) — после финала: она
  меняет нарезку всего корпуса, до holdout её не трогаем. В таблицах
  Word объединённые ячейки (шапка в две строки, строки-группы) теряют
  часть смысла — markdownify их не разворачивает.
- **Форматы**: .xlsx, .pptx и .doc приняты ML 01.10 и встроены (5.15,
  BH-33…BH-35). Сноски с 01.10 стоят на месте ссылки (5.15): поиск по
  вопросам из сносок — 11 из 11 первым. Остались ответы, где модель не
  считает сноску ответом («отлагательное условие» — не «условие гранта»).
  Верхний индекс, набранный вручную, больше не прилипает к числу
  («2 500 000³ ₽» было «2 500 0003 ₽») — в .doc, .xlsx, .pptx; у .docx
  — после BH-36 (одна строка у бэкенда). Сноски PDF на место ссылки не
  переносятся: проверено 01.10, вопросы о сносках выигрывают, а золотой
  dev проигрывает (MRR 0,747 → 0,715 — длинная сноска-ссылка размывает
  фрагмент). Тот же риск — у .docx с десятками длинных сносок. Текст на
  картинках в презентациях не читается (OCR — не MVP).
- **Сканы PDF и картинки не читаются**: OCR и описание картинок — не MVP.
- **Права внутри компании — только у документов из подключённых систем**:
  их права повторяются из Битрикс24, Confluence, Яндекс 360. Загруженные
  файлами документы видит вся компания.
- **Сравнение с Алисой AI для бизнеса**: часть 1 сделана (5.10); тариф и
  версия Алисы не записаны, четыре вопроса сорвались технически — их
  надо переспросить; часть 2 (holdout) — в октябре.
