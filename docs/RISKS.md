## Средние

### 15. Стоимость и последствия «общего ответа» не измерены на случае (б)

Режим Р1: когда выдержки нашлись, но модель по ним отказала, идёт второй
вызов без выдержек. ML замерял только случай (а) — пустой поиск. Риск:
общий ответ противоречит частично найденным документам компании.

**Что делать.** Замер на золотом наборе (задача ML 2.3/2.4). До него —
пометка и `origin` обязательны, плашка на фронте крупно.

### 16. Пороги полнотекста для отчёта о пробелах не заданы

`classify_miss` различает «в базе нет» и «есть, но вектор промахнулся»
по `ts_rank_cd`, а пороги ML подобрал на другой метрике. Пока
`GAPS_STRONG_FULLTEXT`/`GAPS_EMPTY_FULLTEXT` не заданы, полнотекст в
классификации не участвует: часть `retrieval_miss` попадёт в отчёт как
`gap`, precision ниже замеренных 0,88.

**Что делать.** Подобрать на живых логах после первых недель
эксплуатации (ML).

### 17. Перерасход пула кредитов на границе

Проверка пула без блокировки: параллельные вопросы одной компании могут
перерасходовать пул на число одновременных вопросов. Для 30 мест это
десятки кредитов из 12 600.

**Что делать.** Ничего до появления оплаты сверх лимита; тогда —
резервирование кредита до вызова (`DECISIONS.md`, пул кредитов).

### 19. Regex-маскирование персональных данных неидеально

`mask_pii` (ML) закрывает почту, телефоны, паспорта, карты, СНИЛС и
имена по списку. Редкое имя или фамилия без имени пройдут в `qa_log`
и в промпт подписи кластера.

**Что делать.** Срок хранения `qa_log` 90 дней ограничивает ущерб.
Список имён и правила — расширять по находкам; NER-модель — только если
находок много.

### 20. Ограничитель одновременных запросов к LLM — на процесс

`LLM_MAX_CONCURRENCY` — семафор в памяти процесса. При N воркерах
uvicorn квота каталога делится руками: `10 / N`. Ошибка в расчёте —
429 от провайдера и ретраи.

**Что делать.** Слоты в Redis, как у эмбеддингов, — когда процессов
станет больше одного.

### 21. Redis — точка отказа лимитов и квоты

Без Redis приложение в `production` не стартует (осознанно). При падении
Redis в работе: лимиты входа закрываются (503 на вход), лимиты FAQ и
квота эмбеддингов открываются.

**Что делать.** Redis с рестартом (`unless-stopped`) и алерт на 503 у
`/auth/login`. Кластер Redis — не для MVP.

### 22. Планировщик — cron на хосте

`purge` и `gaps` зависят от crontab, который не в репозитории. Забытый
cron = журнал вопросов, который не удаляется по сроку.

**Что делать.** Пункт чек-листа в `DEPLOY.md`. Сервис-планировщик в
compose — когда задач станет больше двух.

### 23. Нет сквозного теста с настоящим Yandex Cloud

Все тесты — с фейковыми адаптерами; формат ответа провайдера
проверяется на записанных телах. Смена формата API обнаружится в бою.

**Что делать.** Ночной прогон `eval.run_eval e2e` против стенда
(ML) — это и есть такой тест; закрепить в расписании после запуска стенда.

### 27. Фильтр прав в векторном поиске — без индекса и после отбора

`_visible_to` (EXISTS по `material_access`) применяется в том же
запросе, что и `ORDER BY distance LIMIT k`. Пока по `chunks.embedding`
нет ANN-индекса, это точный перебор и результат полный. При появлении
HNSW/IVFFlat фильтр после отбора может вернуть меньше k строк
(документы, невидимые сотруднику, займут места в кандидатах).

**План.** При добавлении индекса — либо `ef_search`/oversampling
(брать 5k кандидатов и фильтровать), либо предварительный список
видимых материалов в запросе. Замерить на живых данных клиента.

### 28. Семантика режима `per_user`: документ живёт, пока его кто-то видит

Документ коннектора `per_user` удаляется, когда после полного обхода
всех активных грантов он не встретился ни в одном листинге. Истёкший
грант (`expired`) тоже не листится: если документ видел только он,
документ уйдёт — и вернётся после повторной авторизации сотрудника
(с повторной загрузкой и индексацией). Это честно по правам, но
стоит эмбеддингов.

**План.** Если на практике гранты истекают часто (короткие токены
Битрикс24 без refresh), держать документ N дней без владельцев вместо
удаления. Решить по логам этапа 2.

### 29. Egress воркера ограничен только кодом

Проверка адресов (`core/outbound.py`) — единственная линия против
SSRF; сетевой политики для контейнера `worker` на стенде нет.
Уязвимость в `httpx`/`httpcore` или ошибка в проверке открыла бы
внутреннюю сеть.

**План.** Правила `nftables`/egress-политика по `DEPLOY.md` § 9a при
развёртывании стенда; проверить `curl` из контейнера до метаданных
облака и до базы мимо приложения.

### 32. Контрактные фикстуры Битрикс24 — из документации, не с портала

Сетевая политика окружения не пропускает `*.bitrix24.ru` и
`oauth.bitrix24.tech`, поэтому ответы REST для контрактных тестов
(`tests/connectors/fixtures/bitrix24/`) взяты из образцов официальной
документации (зеркало `bitrix-tools/b24-rest-docs`), а не записаны с
тестового портала. Формы ответов могут расходиться с живыми в деталях:
типы полей (строки вместо чисел), формат `DATE_MODIFY` страниц базы
знаний (зависит от локали портала), состав `disk.storage.getlist` в
режиме сотрудника, ответ `landing.site.getlist` со `scope=GROUP` на
порталах без баз знаний групп.

**План.** Открыть хосты в сетевой политике окружения, выполнить `cli
connector-check --record` с вебхуком тестового портала, положить
записи рядом с фикстурами и поправить разбор там, где разойдётся.
Живая проверка этапа 2 (документ виден в ответе со ссылкой) — после
этого.

### 35. Версия страницы базы знаний — строки дат портала

Изменение страницы определяется по `DATE_MODIFY` и `DATE_PUBLIC`
страницы, а не блоков: правка блока без перепубликации страницу может
не менять. Тогда текст обновится только после публикации. Для базы
знаний это ожидаемо (черновики не индексируются), но подтвердить на
живом портале.

### 36. «База знаний 2.0»: адрес документа в интерфейсе не известен

REST `note.*` не отдаёт ссылку на документ, а публичный путь раздела в
документации не описан. Материалы модуля `knowledge_base_v2` получают
`source_url` на раздел базы знаний портала (`/knowledge/`), а не на
страницу: сотрудник попадёт в базу, но не на документ. Сам модуль не
проверен на живом портале — у тестового вебхука нет scope `note`, и
неизвестно, включена ли База знаний 2.0 на порталах клиентов.

**План.** На живом портале открыть документ в интерфейсе, снять адрес
и собрать ссылку по `collectionId`/`id`; если адреса нет — оставить
раздел и сказать об этом в интерфейсе источника ответа.

### 37. Адаптер Confluence написан без документации и без живого сервера

Документация Atlassian из среды недоступна (сетевая политика), тестового
Confluence нет. Адаптер (`connectors/confluence/`) написан по
устоявшемуся REST API Server/DC, формы ответов зафиксированы в
поддельном сервере (`tests/connectors/fake_confluence.py`). Что
может разойтись с живым Confluence:
- поля ответов `/rest/api/content` (`version.when`, `ancestors`,
  `_links.webui`), `restriction/byOperation` (`read.restrictions.
  user.results[].username`), `group/{name}/member`;
- **права пространства**: REST Server/DC не отдаёт, кто может
  просматривать пространство (только JSON-RPC). Принято: страница без
  ограничений чтения по цепочке предков видна всей компании —
  админ выбирает пространства (`spaces`) и отвечает за то, что они
  общие. Закрытое пространство, попавшее в список, станет видно всем;
- **почта сотрудника**: REST Server не отдаёт e-mail пользователя,
  почта строится из логина по шаблону `email_template`
  (`{username}` или `{username}@company.ru`). Логины без соответствия
  почте → права не сопоставятся, документ останется невидимым;
- списки ограничений и участников групп читаются одной страницей
  (до 200 участников): бо́льшие группы обрежутся — участники сверх
  страницы прав не получат;
- storage-формат: обработаны код, панели, ссылки, задачи, колонки;
  остальные макросы остаются текстом, каким его увидит `markdownify`.

**План.** Тестовый Confluence DC (Docker-образ с пробной лицензией) →
`cli connector-check --kind confluence` с записью ответов → сверить и
поправить разбор; решить, нужен ли JSON-RPC для прав пространств.

### 38. Адаптер Яндекс Диска написан без документации и без живого Диска

Сайты Яндекса из среды недоступны, организации Яндекс 360 нет. Адаптер
(`connectors/yandex/`) написан по устоявшимся REST Диска и OAuth
Яндекс ID; формы ответов — в поддельном сервере
(`tests/connectors/fake_yandex.py`). Что сверять на живом Диске:
- поля листинга `resources` (`_embedded.items[].resource_id`,
  `md5`, `modified`, `public_url`), параметр `fields`, лимит страницы;
- коды ошибок (`UnauthorizedError`, `DiskNotFoundError`,
  `DiskForbiddenError`, `TooManyRequestsError`) и статусы;
- выдаёт ли Яндекс новый `refresh_token` при продлении (адаптер
  сохраняет прежний, если нового нет);
- как общие папки Яндекс 360 выглядят в листинге сотрудника и есть ли
  у файла адрес в интерфейсе без публикации (сейчас ссылка ведёт на
  папку файла в веб-клиенте Диска);
- права приложения: `cloud_api:disk.read`, `cloud_api:disk.info`.
Вики Яндекс 360 не начата: API вики знаю недостаточно, нужна
документация (`yandex.ru/support/wiki/…/api-ref`).

**План.** Организация Яндекс 360 с тестовым сотрудником и
OAuth-приложение → `cli connector-check --kind yandex360` (нужен
access_token сотрудника: пройти OAuth на стенде) → сверка; затем
модуль Вики по документации.

## Закрыто

### 18. GitHub Actions закреплены тегом, образ — тегом (закрыто 25.09)

`uses:` переведены на SHA коммита с комментарием версии (`# v5`):
`actions/checkout`, `astral-sh/setup-uv`, `actions/upload-artifact`,
`gitleaks/gitleaks-action`, `github/codeql-action`; SHA сняты `git
ls-remote --tags` (peeled `^{}`), Dependabot (`github-actions`)
обновляет их с сохранением комментария. `FROM python:3.12-slim` в
обоих стадиях — с digest индекса образа (`registry-1.docker.io`,
`Docker-Content-Digest`), Dependabot (`docker`) обновляет digest.
Осталось тегами: сервисные образы CI (`pgvector/pgvector:pg16`,
`redis:7-alpine`) — тестовая инфраструктура, не поставка; сканер
`ghcr.io/aquasecurity/trivy:latest` в `run:` — Dependabot его не
обновлял бы, а замороженный сканер стареет быстрее, чем подменяется.

### 33. `state` OAuth не одноразовый (закрыто 25.09)

`jti` из `state` гасится через лимитер приложения (`hit` с `limit=1`
на срок жизни state): Redis в бою, память в разработке. Повтор
перехваченного редиректа — `state_reused` до обращения к серверу
авторизации; недоступный Redis — отказ (`temporarily_unavailable`), а
не пропуск. Тест: `test_state_is_single_use`.

### 34. Скачивание файла — целиком в память до проверки размера (закрыто 25.09)

`OutboundClient.download` читает тело кусками и обрывает чтение,
как только оно превысило лимит (`OutboundTooLargeError`);
`Content-Length` — только повод отказать раньше, не доверие.
Адаптер Битрикс24 скачивает через него.

### 30. Нет OAuth-обмена для режима `per_user` (закрыто 25.09, этап 2)

Ручки `POST /connectors/{id}/oauth/start` и `GET
/connectors/oauth/callback`, подписанный `state` (`core/security.py`),
обмен кода адаптером Битрикс24, продление по `expired_token` с
сохранением новой пары в грант (`refreshed_credentials`), `expires_at`
в учётных данных. Остаток — №33.
