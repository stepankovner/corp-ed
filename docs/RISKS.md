## Средние

### 15. Стоимость и последствия «общего ответа» не измерены на случае (б)

Режим Р1: когда выдержки нашлись, но модель по ним отказала, идёт второй
вызов без выдержек. ML замерял только случай (а) — пустой поиск. Риск:
общий ответ противоречит частично найденным документам компании.

**Что делать.** Замер на золотом наборе (задача ML 2.3/2.4). До него —
пометка и `origin` обязательны, плашка на фронте крупно.

**Дополнение 26.09.** Частоту и цену случая (б) ML замерил при переходе на
`faq-v2.4`: 7 из 32 общих ответов на полном корпусе и 22 из 64 на
урезанном пришли после отказа модели по выдержкам, каждый — ещё один
вызов за 0,03 ₽ и 0,6 с. Не замерено другое: не противоречат ли такие
общие ответы документам — проверить на золотом наборе.

### 16. Пороги полнотекста для отчёта о пробелах не заданы

`classify_miss` различает «в базе нет» и «есть, но вектор промахнулся»
по `ts_rank_cd`, а пороги ML подобрал на другой метрике. Пока
`GAPS_STRONG_FULLTEXT`/`GAPS_EMPTY_FULLTEXT` не заданы, полнотекст в
классификации не участвует: часть `retrieval_miss` попадёт в отчёт как
`gap`, precision ниже замеренных 0,88.

**Что делать.** Подобрать на живых логах после первых недель
эксплуатации (ML).

### 17. Перерасход пула кредитов на границе

Проверка пула без блокировки: параллельные вопросы одной компании могут
перерасходовать пул на число одновременных вопросов. Для 30 мест это
десятки кредитов из 12 600.

**Что делать.** Ничего до появления оплаты сверх лимита; тогда —
резервирование кредита до вызова (`DECISIONS.md`, пул кредитов).

### 19. Regex-маскирование персональных данных неидеально

`mask_pii` (ML) закрывает почту, телефоны, паспорта, карты, СНИЛС и
имена по списку. Редкое имя или фамилия без имени пройдут в `qa_log`
и в промпт подписи кластера.

**Что делать.** Срок хранения `qa_log` 90 дней ограничивает ущерб.
Список имён и правила — расширять по находкам; NER-модель — только если
находок много.

### 20. Ограничитель одновременных запросов к LLM — на процесс

`LLM_MAX_CONCURRENCY` — семафор в памяти процесса. При N воркерах
uvicorn квота каталога делится руками: `10 / N`. Ошибка в расчёте —
429 от провайдера и ретраи.

**Что делать.** Слоты в Redis, как у эмбеддингов, — когда процессов
станет больше одного.

### 21. Redis — точка отказа лимитов и квоты

Без Redis приложение в `production` не стартует (осознанно). При падении
Redis в работе: лимиты входа закрываются (503 на вход), лимиты FAQ и
квота эмбеддингов открываются.

**Что делать.** Redis с рестартом (`unless-stopped`) и алерт на 503 у
`/auth/login`. Кластер Redis — не для MVP.

### 22. Планировщик — cron на хосте

`purge` и `gaps` зависят от crontab, который не в репозитории. Забытый
cron = журнал вопросов, который не удаляется по сроку.

**Что делать.** Пункт чек-листа в `DEPLOY.md`. Сервис-планировщик в
compose — когда задач станет больше двух.

### 23. Нет сквозного теста с настоящим Yandex Cloud

Все тесты — с фейковыми адаптерами; формат ответа провайдера
проверяется на записанных телах. Смена формата API обнаружится в бою.

**28.09 — один ручной прогон.** `tests/live/test_stand_yandex_live.py`
прошёл с ключами сессии: сквозной сценарий через HTTP API на настоящих
`text-embeddings-v2` и Alice AI LLM Flash (`WORKLOG.md`, запись 28.09
«живой прогон с Yandex Cloud»). Регулярного прогона по-прежнему нет —
смена формата API между ручными прогонами всё так же обнаружится в бою.

**Что делать.** Ночной прогон `eval.run_eval e2e` против стенда
(ML) — это и есть такой тест; закрепить в расписании после запуска стенда.

### 27. Фильтр прав в векторном поиске — без индекса и после отбора

`_visible_to` (EXISTS по `material_access`) применяется в том же
запросе, что и `ORDER BY distance LIMIT k`. Пока по `chunks.embedding`
нет ANN-индекса, это точный перебор и результат полный. При появлении
HNSW/IVFFlat фильтр после отбора может вернуть меньше k строк
(документы, невидимые сотруднику, займут места в кандидатах).

**План.** При добавлении индекса — либо `ef_search`/oversampling
(брать 5k кандидатов и фильтровать), либо предварительный список
видимых материалов в запросе. Замерить на живых данных клиента.

### 28. Семантика режима `per_user`: документ живёт, пока его кто-то видит

Документ коннектора `per_user` удаляется, когда после полного обхода
всех активных грантов он не встретился ни в одном листинге. Истёкший
грант (`expired`) тоже не листится: если документ видел только он,
документ уйдёт — и вернётся после повторной авторизации сотрудника
(с повторной загрузкой и индексацией). Это честно по правам, но
стоит эмбеддингов.

**План.** Если на практике гранты истекают часто (короткие токены
Битрикс24 без refresh), держать документ N дней без владельцев вместо
удаления. Решить по логам этапа 2.

### 29. Egress воркера ограничен только кодом

Проверка адресов (`core/outbound.py`) — единственная линия против
SSRF; сетевой политики для контейнера `worker` на стенде нет.
Уязвимость в `httpx`/`httpcore` или ошибка в проверке открыла бы
внутреннюю сеть.

**План.** Правила `nftables`/egress-политика по `DEPLOY.md` § 9a при
развёртывании стенда; проверить `curl` из контейнера до метаданных
облака и до базы мимо приложения.

### 35. Версия страницы базы знаний — строки дат портала

Изменение страницы определяется по `DATE_MODIFY` и `DATE_PUBLIC`
страницы, а не блоков: правка блока без перепубликации страницу может
не менять. Тогда текст обновится только после публикации. Для базы
знаний это ожидаемо (черновики не индексируются), но подтвердить на
живом портале.

### 36. «База знаний 2.0»: адрес документа в интерфейсе не известен

REST `note.*` не отдаёт ссылку на документ, а публичный путь раздела в
документации не описан. Материалы модуля `knowledge_base_v2` получают
`source_url` на раздел базы знаний портала (`/knowledge/`), а не на
страницу: сотрудник попадёт в базу, но не на документ. Сам модуль не
проверен на живом портале — у тестового вебхука нет scope `note`, и
неизвестно, включена ли База знаний 2.0 на порталах клиентов.

**План.** На живом портале открыть документ в интерфейсе, снять адрес
и собрать ссылку по `collectionId`/`id`; если адреса нет — оставить
раздел и сказать об этом в интерфейсе источника ответа.

**28.09:** модуль скрыт из каталога до живой проверки (решение владельца
продукта, `preview=True`); включается `CONNECTOR_PREVIEW_MODULES=
knowledge_base_v2` — так же для `connector-check`.

### 37. Адаптер Confluence написан без документации и без живого сервера

Документация Atlassian из среды недоступна (сетевая политика), тестового
Confluence нет. Адаптер (`connectors/confluence/`) написан по
устоявшемуся REST API Server/DC, формы ответов зафиксированы в
поддельном сервере (`tests/connectors/fake_confluence.py`). Что
может разойтись с живым Confluence:
- поля ответов `/rest/api/content` (`version.when`, `ancestors`,
  `_links.webui`), `restriction/byOperation` (`read.restrictions.
  user.results[].username`), `group/{name}/member`;
- **права пространства**: REST Server/DC не отдаёт, кто может
  просматривать пространство (только JSON-RPC). Принято: страница без
  ограничений чтения по цепочке предков видна всей компании —
  админ выбирает пространства (`spaces`) и отвечает за то, что они
  общие. Закрытое пространство, попавшее в список, станет видно всем;
- **почта сотрудника**: REST Server не отдаёт e-mail пользователя,
  почта строится из логина по шаблону `email_template`
  (`{username}` или `{username}@company.ru`). Логины без соответствия
  почте → права не сопоставятся, документ останется невидимым;
- участники групп читаются постранично (`start/limit` по 200) до
  короткой страницы — сверить, что DC отдаёт `size`/`_links.next` так же;
  прежняя формулировка «одной страницей, бо́льшие группы обрежутся»
  была неверна (проверка кода 26.09) — участники сверх
  страницы прав не получат;
- storage-формат: обработаны код, панели, ссылки, задачи, колонки;
  остальные макросы остаются текстом, каким его увидит `markdownify`.

**План.** Тестовый Confluence DC → `cli connector-check --kind
confluence` с записью ответов → сверить и поправить разбор; решить,
нужен ли JSON-RPC для прав пространств. *28.09:* свой DC не поднять —
Atlassian с 30.03.2026 не выдаёт пробных лицензий Data Center новым
клиентам, DC работает у действующих до 28.03.2029 (дальше — только
чтение). Живая проверка — на чужом DC (тестовое пространство и токен
только на чтение); варианты — `OPEN-QUESTIONS.md`, П-8.

### 38. Адаптер Яндекс 360: сверен с документацией, живым Диском не проверен

28.09 документация стала доступна; сверка нашла и исправила: общие
диски организации — отдельный API (`virtual-disks`), а не часть
`disk:/` сотрудника (модуль `shared_disks`, нужен ID организации);
ссылке на скачивание нужен тот же OAuth-токен (на хост хранилища после
302 он не уходит); refresh-токен живёт столько же, сколько access —
продление заранее, за 30 дней до истечения; карта ошибок OAuth
(`unauthorized_client`, `bad_verification_code`, …); 423 — повтор;
403 на корне — ошибка, а не пустой Диск; хосты скачивания — только
`.yandex.ru`/`.yandex.net`; `uid` вместо логина; `force_confirm` и наш
`redirect_uri` в адресе авторизации.

**Сверить на живой организации:** форма путей внутри общего диска
(документация показывает и составные, и относительные — принимаются
обе); веб-адрес файла общего диска (`/client/vd/<hash>`); появляются ли
в `disk:/` папки, открытые по персональному доступу; предел `limit`
листинга; сколько живут токены приложения.

### 39. Режим `via_proxy` снимает закрепление адреса

За egress-прокси (`CONNECTOR_OUTBOUND_VIA_PROXY=true`) запрос уходит по
имени: имя резолвится и проверяется перед запросом, но подключается
прокси, и подмена DNS между проверкой и подключением (rebinding) — на
его политике. Флаг, включённый без прокси, — просто отключение
закрепления. На стенде включать только там, где есть `HTTPS_PROXY`
(`DEPLOY.md` §9a). **Предохранитель сделан 28.09:** в `production` флаг
без `HTTPS_PROXY`/`https_proxy` в окружении — отказ старта. Остаётся:
политика самого прокси должна не пускать к внутренним адресам.

### 40. Модель разметки PDF пришла транзитивно и стоит ×5 CPU

`pymupdf4llm` 1.28 тянет `pymupdf-layout` (onnxruntime) и включает
модель разметки сама, если пакет установлен; в `DECISIONS` записан
только `pymupdf4llm`. Замер на двух PDF тестового портала (4 ядра):
49 страниц — 12 с по стене / 41 с CPU / 363 МБ с моделью против 5,7 с /
7,3 с / 154 МБ без неё; 85 страниц — 23 с / 75 с / 374 МБ против 14 с /
16 с / 153 МБ; объём текста тот же (97,6 и 207–211 тыс. символов).
Модель обещает лучшие таблицы и заголовки — на этих документах не
сравнивалось. С ней бюджет запуска синхронизации (20 мин на 200
документов) при 20–25 с на документ не выполняется. Решение за
командой: оставить или выключить; сравнить качество чанков на золотом
наборе ML. **С 28.09 это одна переменная:** `INGEST_PDF_LAYOUT=false`
(по умолчанию `true` — как было); песочница передаёт её дочернему
процессу аргументом.

### 43. Модуль Вики Яндекс 360 написан по документации, живой Вики нет

Публичный API Вики (`api.wiki.yandex.net/v1`) работает от имени
сотрудника с заголовком `X-Org-Id`; права приложения — `wiki:read`.
Способа перечислить всю Вики без корня в документации нет: обход идёт
от разделов из настройки подключения (`wiki_roots`, по умолчанию
`homepage`). Версия страницы — `modified_at`; динамические таблицы и
шаблоны пропускаются; вложения страниц — не читаются.

**Сверить на живой организации:** работает ли токен из обмена кода с
`wiki:read` вместе с правами Диска; покрывает ли `homepage` всю Вики
или нужны корни разделов; реальное содержимое страниц каждого типа;
меняется ли `modified_at` при каждой правке; коды ошибок (недоступная
страница, API выключен админом, лимиты); сотрудники с федеративным
входом (документация требует для них IAM-токен).

### 46. Ссылка-приглашение — на предъявителя, почта не подтверждается

По ссылке (`/join/<код>#<токен>`) учётку сотрудника заводит любой, у
кого она есть, пока она действует; почта присоединившегося не
подтверждается — почтового канала нет. Кто-то может занять чужой
адрес, и настоящий сотрудник получит «почта уже есть». Смягчения: срок
1–30 дней, лимит использований (по умолчанию — число мест), отзыв,
домен почты, только роль сотрудника, событие аудита с id ссылки,
список сотрудников у админа (блокировка лишнего). **Закрыть:**
подтверждение почты или одноразовые персональные ссылки — когда
появится почтовый сервис (восстановление пароля — там же).

### 47. Запись на созвон: мы оператор персональных данных

Форма на `/pricing/request` собирает имя, телефон и почту тех, кто ещё
не клиент. Код готов к приёму, но по умолчанию он выключен: включение
(`LEADS_ENABLED=true`) требует адреса и версии политики, иначе старт
отменяется. Самой политики, согласия в редакции юриста и уведомления
Роскомнадзора нет (досье 17.1 — после регистрации юрлица). Меры в коде:
минимум полей, IP не хранится, в журналы — только id заявки, согласие с
версией политики, срок хранения 180 дней (`cli purge`), лимиты по IP и
общий суточный, ловушка для ботов. О новой заявке команда узнаёт от
бота в Telegram (с 28.09) — в сообщении только тариф, число мест и окно
созвона, контакты — в `cli leads list`. **Что делать:** политика и
уведомление РКН → включить на стенде.

### 48. Yandex AI Studio по умолчанию сохраняет наши запросы

«По умолчанию модели сохраняют все данные запросов»; запросы с

Уходят вопросы сотрудников (маскирование неидеально, №19) и фрагменты
документов клиентов, а с 08.09.2026 Яндекс — прямой конкурент («Алиса
AI для бизнеса»). **30.09:** заголовок передаётся во всех запросах
(`llm/yandex_headers.py`, тест `tests/llm/test_yandex_no_logging.py`).
На живом API все три адаптера отвечают 200; OpenAI-совместимый
возвращает заголовок в ответе, нативный и эмбеддинги — нет, а
документация называет генерацию, классификаторы и YandexART, но не
эмбеддинги. **Осталось:** подтверждение от Яндекса для эмбеддингов.

### 49. Один поставщик ML, отказ — 502, загрузка теряет документы

Эмбеддинги и генерация — Yandex AI Studio. Отказ любого — 502
сотруднику, хотя полнотекстовый поиск есть; медленный провайдер держит
запрос до ~3 минут (60 с × 3 попытки), предохранителя нет; сбой
эмбеддингов дольше ~7,5 минут переводит загружаемые документы в
`FAILED` без возврата. **Что делать:** быстрый отказ, частичный ответ,
загрузка без потерь, запасная модель после замера ML
(`RESILIENCE-RESEARCH.md` §2, `OPEN-QUESTIONS.md` ML-5).

### 50. Telegram как канал уведомлений может не работать с сервера в РФ

### 51. Ключи коннекторов не входят в план восстановления

DEPLOY §8 считает единственным состоянием PostgreSQL, но
`CONNECTOR_SECRETS_KEYS` живут только в `.env` на сервере; потеря

### 52. Стенд — прерываемый сервер: лежит каждые сутки

Selectel останавливает прерываемый сервер в любой момент в течение 24
часов, и сам он не поднимается (`STAGE.md` §2). Workflow «Stage resume»
возобновляет его раз в 10 минут, но расписание GitHub запаздывает под
нагрузкой — стенд лежит обычно 10–30 минут. Выкатка в этот момент
падает на SSH. Сохраняется ли публичный IP — в документации не сказано,
проверить после первого прерывания. Ключ сервисного пользователя
управляет всеми серверами проекта — поэтому в проекте только стенд.
**Что делать:** демо и замеры ML — с запасом по времени; для пилота —
не прерываемый сервер.

### 53. Память диалога теряется при перезапуске Redis

Реплики диалога живут только в памяти Redis (решение 30.09: ответы не
пишутся на диск и в бэкапы). Перезапуск Redis — выкатка, сбой,
прерывание стенда — стирает историю: следующий уточняющий вопрос
разбирается как самостоятельный. Ответ не ломается, качество уточнения
падает. Вопрос в истории — после `mask_pii`, как в журнале: «а у него
сколько дней?» после вопроса с ФИО переписывается хуже (контракт ML
BH-28). **Что делать:** смотреть долю деградаций `dialogue_store` в
мониторинге; если мешает — хранить без маскирования в Redis (только
память, 12 часов).

### 54. Реранкер делит процессор с API и воркером

mMiniLM на 4 vCPU — ~1,9 с на 30 фрагментов одного вопроса (замер
30.09); несколько одновременных вопросов делят ядра, а разбор PDF
занимает все. Сервису отведено 3 ядра (`compose.yaml`), таймаут 4 с — при
перегрузке ответ идёт по порядку вектора, без ошибки. **Что делать:**
включать после holdout ML; смотреть `rerank_ms` в диагностике и долю
деградаций `rerank`; глубину 20 вместо 30 или ONNX int8 (~1,2 с) — по
замеру ML.

## Закрыто

### 44. Токены сессии фронтенда в `localStorage` (закрыто 28.09)

Пара access/refresh лежала в `localStorage`: XSS на origin приложения
унесла бы refresh-токен и сессию на 14 дней. Решение владельца 28.09 —
закрыть до пилота. Refresh — в httpOnly-cookie `kronto_refresh`
(`SameSite=Strict`, `Path=/api/v1/auth`, `Secure` в production); ручки
обновления и выхода читают её и сверяют `Origin` с `Host`; access-токен
— только в памяти вкладки, после перезагрузки вкладка получает новый по
cookie. В `localStorage` — только признак «здесь входили», без токенов.
Остаётся: пока XSS на странице активна, она может пользоваться сессией
(обновлять access), но не унести её. `DECISIONS.md`, 2026-09-28
«Refresh-токен в httpOnly-cookie».

### 42. Алерт CodeQL на PR #15: печать временного пароля (закрыто 28.09)

`cli create-tenant` печатал сгенерированный временный пароль
администратора (`py/clear-text-logging-sensitive-data`, high). Решение
владельца продукта 28.09 — «как безопаснее»: пароль задаёт оператор,
скрытым вводом дважды или первой строкой stdin
(`--admin-password-stdin`), CLI его не генерирует, не печатает и не
пишет в файл; политика паролей та же, что у пользователей, смена при
первом входе. Файл с правами 600 отвергнут: при `docker compose run
--rm` он исчезает вместе с контейнером, а сканер отмечает хранение
секрета открытым текстом. CI e2e генерирует пароль сам и маскирует его.

### 18. GitHub Actions закреплены тегом, образ — тегом (закрыто 25.09)
