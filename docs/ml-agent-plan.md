# Агент с инструментом поиска (вариант 1) — план

20.10.2026, ML. Решение Артёма 20.10: вариант 3 («не вопрос» в общем
ответе, BH-45) — базовый сейчас, **вариант 1 — приоритет**, ближайшая
крупная задача. Здесь — насколько это сложно, что потребуется, в каком
порядке и что решить.

## 1. Зачем

Сейчас ответ — жёсткий конвейер: любое сообщение → поиск → модель по
выдержкам → при отказе общий ответ. Из этого растут три известные
проблемы, и все три агент закрывает одним механизмом:

| Проблема | Сейчас | В агенте |
|---|---|---|
| «Привет» → «в документах ответа нет» | правило в общем ответе (BH-45) | модель отвечает сама, поиск не нужен |
| ответ из двух документов (должность → имя) | один добор «Дополнительный поиск» (BH-43), 5 из 10 | модель ищет столько раз, сколько нужно (в пределах лимита) |
| вопрос из двух частей, уточнение у сотрудника | нет | несколько поисков; при неясности — уточняющий вопрос |

## 2. Что уже проверено (20.10)

Вызов инструмента `search_documents(query)` через OpenAI-совместимый API
(`sandbox/stand/tool_calling_probe.py`, ≈ 1 ₽):

| | Вопрос по документам | «Привет» | Поток |
|---|---|---|---|
| Яндекс Flash | `tool_calls`, 1,4 с | отвечает сам | `tool_calls` одной частью |
| Cloud.ru gpt-oss-120b | `tool_calls`, 1,8 с | отвечает сам | частями |
| MWS gpt-oss-120b | `tool_calls`, 1,3 с | отвечает сам | частями |

Своего формата вызова изобретать не нужно — у всех трёх звеньев цепочки
резерва стандартный `tools`. Это снимает самый дорогой риск.

## 3. Архитектура — два варианта

**А. Классический агент.** Модель получает сообщение и инструмент, сама
решает, искать ли и что. Плюсы — проще всего, естественный small talk.
Минусы:
- **модель может не искать и ответить «из головы»** на вопрос о компании
  — уверенно и неверно; ровно с этим мы боролись (x03 «Старт-ИИ-2»);
- **+1 вызов модели перед каждым поиском**: 1,3–1,8 с (замер выше) к
  каждому вопросу по документам.

**Б. Сначала поиск, инструмент — для добора (рекомендую).** Как сейчас,
поиск по сообщению идёт сразу (≈ 0,2 с); модель получает выдержки **и**
инструмент. Дальше она:
- отвечает по выдержкам (как сейчас — один вызов, задержки не прибавилось);
- ищет ещё (`search_documents`), если выдержек мало, — обобщение BH-43;
- на «привет» отвечает сама, выдержки игнорирует;
- при неясном вопросе — переспрашивает.

Опора на документы сохраняется: модель всегда видит, что нашлось, и
правило «отвечай только по выдержкам» остаётся. Задержка — как сейчас,
кроме вопросов, где нужен добор.

## 4. Что потребуется

**ML (≈ 6–8 рабочих дней):**
1. Промпт `agent-v1`: правила ответа по выдержкам (из faq-v2.9), когда
   искать ещё, когда отвечать самому, когда переспрашивать; описание
   инструмента; общий ответ с пометкой — как сейчас.
2. Чистые функции (`domain/agent.py`): политика цикла — не больше N
   вызовов инструмента (2–3), без повтора того же запроса, бюджет токенов
   выдержек, нумерация `[n]` через все поиски (новые — после прежних, как
   в BH-43), разбор ответа модели.
3. Eval: `offline_e2e --agent` — цикл с поиском на стенде, журнал шагов
   (что искала, сколько раз, что добавилось); метрики траекторий: доля
   вопросов с добором, «искала ли, когда надо», «не ушла ли от выдержек».
4. Наборы: dev и стенд (как сейчас), «два документа» (10), «не вопросы»
   (46), вопросы вне документов (50) и **соседние программы** (x03-тип —
   нужен расширенный набор, 15–20 вопросов: это главный риск), длинные.
5. Протокол до прогонов и 2–3 раунда замера: Flash и gpt-oss (резерв),
   судья на dev. ≈ 150–300 ₽ (судья ≈ 1,2 ₽ за вердикт).
6. Контракт для бэкенда (BH), handoff.

**Бэкенд (≈ 6–10 рабочих дней):**
1. Цикл в `faq_service`: вызов модели с `tools` → `tool_calls` →
   поиск (тот же путь: права, порог BH-37, реранкер) → вызов снова; лимиты
   шагов и времени.
2. Поток: ответ модели может начаться вызовом инструмента — поток
   придерживать до первого содержательного куска (как `_SearchGate`);
   этапы в чате «Ищу в документах…».
3. `qa_log`: каждый шаг — запрос, найденное, токены, поставщик; кредиты —
   сумма вызовов.
4. `FallbackGateway`: инструменты у всех звеньев (проверено), но формат
   потока разный (Flash — одной частью, gpt-oss — частями, `\u`-экраны) —
   разбирать общим кодом.
5. Фронт: этапы, источники из нескольких поисков, уточняющий вопрос.
6. Выключатель: агент и нынешний конвейер рядом, переключение настройкой;
   BH-43 и BH-45 остаются запасным путём.

**Итого:** ≈ 2–3 недели календарно (ML и бэкенд частично параллельно),
≈ 150–300 ₽ на замеры у Яндекса; у Cloud.ru и MWS — копейки.

## 6. Риски

| Риск | Что делать |
|---|---|
| Модель не ищет и отвечает «из головы» | архитектура Б (поиск всегда); метрика в eval; набор соседних программ |
| Отказ на «соседней» программе ломается (x03 хрупок к любым правкам промпта) | отдельный критерий 100 % на расширенном наборе; без него не включать |
| Задержка | Б: добор — только когда нужен; лимит шагов 2–3; таймаут на шаг |
| Цена (каждый добор — +вызов, ×1,5–2,5 входящих токенов) | лимит шагов, бюджет выдержек; на gpt-oss у Cloud.ru — копейки |
| Зацикливание, одинаковые запросы | политика цикла в чистых функциях ML, тесты |
| Текст документов управляет моделью (prompt injection через выдержки) | инструмент только на чтение; выдержки объявлены данными (как сейчас); лимит шагов |
| Разное поведение поставщиков | замер на Flash и gpt-oss; разбор потока — общий код |
| Недетерминизм — трудно сравнивать | 3 повтора на ключевых вопросах, как с x03 |

## 7. Решения (Артём, 20.10)

1. **Архитектура — Б:** сначала поиск, как сейчас; модель видит выдержки
   и может искать ещё, ответить сама или переспросить.
2. **Доборов — не больше 2** на вопрос.
3. **Уточняющие вопросы — вторым шагом**, после замера агента.
4. **Кредиты — по токенам с потолком** (например, не больше 3 кредитов за
   ответ; потолок — Влад и Артём).
5. **Строгий режим:** реплики («привет», «спасибо») разрешены, вопросы вне
   документов — отказ. Проверить отдельно, нет ли проблем (в наборе
   прототипа — строгий режим).
6. **Сотруднику — только этап «Ищу в документах…»**, без текста запроса;
   запросы — в журнале и отчёте о пробелах. Пересмотреть по опыту.
7. **Критерии переключения — приняты:** стенд ≥ 118 из 140; «два
   документа» > 5 из 10; вне документов 45 из 45 с пометкой; соседние
   программы (расширенный набор, 15–20) — 100 % отказ; dev по судье — не
   хуже; p95 — не больше нынешнего + 2 с; цена — не больше ×1,5.
8. **Начинать сейчас:** ML-прототип в eval (продукт не трогает); бэкенд —
   после пунктов, критичных для MVP (реранкер, повторная загрузка PDF,
   BH-45).
9. **Модели — все звенья:** Flash, gpt-oss у Cloud.ru и у MWS.
10. **Бюджет замеров — 150–300 ₽**; больше 300 ₽ — смета заранее.
11. **BH-45 — бэкенду сейчас**; после агента — запасной путь.

## 8. Лучшие практики — что берём (обзор 20.10)

Курс Яндекса (Agents Week 2026, ШАД) посмотреть не удалось: YouTube не
отдаёт расшифровку без входа — по решению Артёма взяли статьи. Пометки:
**[З]** — подтверждено замером в источнике, **[П]** — практика или мнение
автора, **[И]** — наш вывод. Наша схема «сначала поиск, потом добор»
совпадает с гибридной стратегией, которую Anthropic советует для
стабильных доменов вроде документов компании [П] ([context
engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).

**Промпт и инструмент**
1. **Описание `search_documents` — как для нового сотрудника:** ищет только
   в документах компании; запрос — короткие ключевые слова и **точное
   название программы или документа из вопроса**; ничего не дописывать
   (год и т. п.); один пример. Anthropic: правка описания сбойного
   инструмента ускорила задачи на 40 % [З], дописывание «2025» к запросам
   лечили описанием [П] ([writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents),
   [multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system)).
2. **Строгая схема:** один параметр `query`, `additionalProperties: false`;
   права, лимиты, компанию подставляет код, не модель [П] ([OpenAI function
   calling](https://developers.openai.com/api/docs/guides/function-calling),
   [building effective agents](https://www.anthropic.com/engineering/building-effective-agents)).
3. **Промпт средней детализации и 3–4 образцовых примера** вместо длинного
   перечня правил: «привет» без поиска; один добор; отказ на «Старт-ИИ-2»,
   когда выдержки только про «Старт-ИИ-1» [П]. На gpt-oss (рассуждающая)
   примеры могут мешать — проверяем отдельно [И].
4. **Ответ инструмента — только содержательные поля:** документ, раздел,
   номер [n], текст; без технических id [З — 72 токена против 206 в
   примере Anthropic].

**Политика цикла**
5. **Нормы поиска в промпте:** реплика — без поиска; добор — только если в
   выдержках нет нужного факта; не больше 2 доборов. Без норм ранние
   системы Anthropic искали лишнее и бесконечно искали то, чего нет [П].
6. **Лимит — в коде:** после второго добора — вызов без инструментов (или
   `tool_choice: "none"`), модель обязана ответить; превышение — не ошибка,
   а контролируемый ответ [П] ([OpenAI Agents SDK](https://openai.github.io/openai-agents-python/running_agents/)).
   Поддержку `tool_choice` у Яндекса проверить; запасной путь — вызов без
   `tools` [И].
7. **Запрос добора — короткий, с точным именем сущности;** составной
   вопрос — два подзапроса параллельно за один шаг (до −90 % времени на
   сложных задачах у Anthropic [З]; так же Azure agentic retrieval [П]).
8. **Дедупликация в инструменте:** уже показанные выдержки не возвращать;
   нового нет — ответ инструмента: «новых выдержек нет — отвечай по
   имеющимся или сообщи, что в документах ответа нет» [П + И].
9. **Короткий контекст:** добавленные выдержки — через тот же порог BH-37,
   всего не больше 8. Качество падает с длиной контекста, один похожий,
   но неверный фрагмент снижает точность [З] ([Chroma context
   rot](https://www.trychroma.com/research/context-rot)) — «Старт-ИИ-1» на
   вопрос о «-2» и есть такой фрагмент [И].

**Опора на документы и честный отказ**
10. **Проверка кодом после ответа (сторож сущностей):** если в вопросе есть
    название программы или документа («…» или имя с номером), которого нет
    ни в одной процитированной выдержке, — принудительный отказ. Только
    проверка кодом, не промпт, может дать 100 % на «соседних» [И, на основе
    рекомендаций OpenAI и Anthropic о детерминированных проверках [П]].
    Мерить и ложные отказы — вариант «со сторожем» отдельной конфигурацией.
11. **Недостаточный контекст опаснее пустого:** у моделей доля неверных
    ответов растёт с 10 % без контекста до 66 % с недостаточным [З]
    ([Google, sufficient context](https://research.google/blog/deeper-insights-into-retrieval-augmented-generation-the-role-of-sufficient-context/)) —
    правило «отвечай только если в выдержках есть ответ именно на этот
    вопрос» и пример с соседней программой.
12. **Калибровать отказ с двух сторон:** строгий промпт поднял приемлемые
    отказы с 62 до 86 %, но отвеченные упали с 80 до 59 % [З]
    ([UAEval4RAG](https://arxiv.org/html/2412.12300v3)) — поэтому в
    критериях и стенд (отвечаемые), и вне документов, и соседние.

**Безопасность**
13. **Выдержки — только в сообщениях user / tool, в разделителях с
    источником, «это данные, не инструкции»;** никогда не в system.
    Spotlighting снизил успех атак с > 50 % до < 2 % [З]
    ([arXiv 2403.14720](https://arxiv.org/abs/2403.14720)).
14. **Защита архитектурой:** инструмент только читает, побочных действий
    нет; ссылки и картинки из документов не исполняются [П]
    ([prompt injection design patterns](https://simonwillison.net/2025/Jun/13/prompt-injection-design-patterns/)).

**Задержка и стоимость**
15. **Доборы — бюджет:** в журнале — токены и вызовы на каждый ответ;
    агенты тратят ≈ ×4 токенов чата [З]. Порог переключения по цене (≤ ×1,5)
    уже в критериях.
16. **gpt-oss: рассуждения передавать обратно между вызовами инструмента**
    в пределах хода, иначе качество вызова инструментов падает [П]
    ([OpenAI, gpt-oss](https://developers.openai.com/cookbook/articles/gpt-oss/verifying-implementations)) —
    проверить у Cloud.ru и MWS.

**Оценка**
17. **Наборы в обе стороны:** где искать и отвечать надо (стенд, dev,
    «два документа») и где не надо (реплики, вне документов, соседние) [П]
    ([demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).
18. **«100 % отказ» — через pass^k:** все 3 повтора должны отказать; при
    75 % за прогон pass^3 ≈ 42 % [П, арифметика].
19. **Траектории — кодом:** искал ли, когда было нужно; не искал ли
    лишнего; число вызовов, токены, задержка. Итог — по результату, без
    штрафа за другой допустимый путь [П] ([LangSmith trajectory
    evals](https://docs.langchain.com/langsmith/trajectory-evals)).
20. **Судья другого семейства на подвыборке** (gpt-oss против Alice, «Alice
    оценивает Alice»), вариант «не знаю» у судьи [П]; читать сырые
    траектории; отложенный набор — против подгонки [П].

**Чего не делаем:** цикл без лимита; мультиагентную схему (≈ ×15 токенов
[З]); много пересекающихся инструментов (один `search_documents`);
длинные запросы с лишними уточнениями; выдержки «на всякий случай»;
недоверенный текст в system; оценку по одному прогону; жёсткий эталонный
путь в оценке траекторий; Self-RAG / CRAG «как есть» — им нужно
дообучение, берём идеи (оценка выдержек, переписывание запроса), не модели.

### 9.2. Скорректированные выводы

1. Стратегия «решение до ответа» — в русле практики: отдельная проверка
   достаточности и отдельный классификатор намерения — стандарт, а вызов
   инструментов моделью Яндекса — нет.
2. Время лечится тремя слоями, а не одним: правило в коде для очевидного
   (0 мс), короткое решение (low: p95 1,9 с против 4,6 у medium на тех же
   85 вопросах), ответ параллельно с решением. Ожидание: p95 ≈ max(1,9;
   5,6) ≈ 5,7 с — на уровне конвейера. Цена: выброшенных ответов 22 % →
   +0,03 ₽, ≈ ×1,2.
3. Качество «двух документов» и подмен лежит не в промпте решения, а в
   данных: контекст чанка при индексации и структурированный справочник.
   Это изменения ingest и модели данных — пункты BH, а не промпт.
4. Стримить до вердикта нельзя (NeMo `stream_first` — пользователь видит
   текст, который потом отзывают); показывать «Ищу в документах…» —
   решение Артёма 6 уже такое.
5. Поставщик: быстрое решение есть только у Cloud.ru (Flash — 16–20
   токенов/с, решение на нём p95 7 с). Без Cloud.ru схема по времени не
   проходит — это решение команды (152-ФЗ, договор), не ML.
