## 1. Как ранжировал и как читать

### 1.1. Формула (порядок критериев)

1. **Достижимость из нашего облака по публичному HTTPS.** SaaS — да.
   Коробка — делится на две группы:
   - *обычно опубликована в интернет* (Битрикс24 коробочный — без
     этого не работают приложения и мобильный клиент; Nextcloud;
     Confluence DC — прецедент: коробка уже в каталоге; в реестре пока все виды `base=True`). Такая
     коробка может быть **базовой**: проверка адреса (`url_field`,
     SSRF) уже есть, и требование «портал доступен из интернета»
     пишется в форму подключения;
   - *обычно во внутренней сети* (СЭД, 1С:Документооборот, МойОфис
     Частное облако, Р7 Корпоративный сервер, SharePoint Server,
     сетевые папки). По умолчанию — **волна 3 / «Корпоративный»**
     (контур, агент или VPN).
2. **Режим прав** (что даёт API источника), в терминах `ConnectorMode`
   и `UserAuth` из `connectors/registry.py`:
   - **org** — `organization`: админ подключает один раз, API отдаёт
     ACL (пользователи, группы) **и почту** для сопоставления. Лучший
     вариант;
   - **per_user/OAuth** — `per_user` + `UserAuth.OAUTH`: каждый
     сотрудник проходит OAuth, видимость = «документ есть в его
     листинге» (как Битрикс24 и Яндекс сейчас);
   - **per_user/токен** — `per_user` + `UserAuth.FIELDS`: сотрудник
     **вставляет свой личный токен или пароль приложения** (поле
     `credential_fields`). Права зеркалируются так же — по листингу, —
     но опыт хуже, чем у OAuth. Механизм в ядре уже есть, поэтому
     системы «только с личным токеном» **не** приговорены к режиму
     «всё видят все»;
   - **всем** — права получить нельзя: коннектор возможен только в
     режиме «всё видят все» (`MaterialVisibility` на компанию). Помечено
     ⚠.
3. **Спрос** — опубликованные числа (с источником и оговоркой);
   при их отсутствии — «чисел нет».
4. **Трудозатраты** — S (≤2 дня), M (3–5), L (>5). Калибровка по
   репозиторию: адаптер Confluence ≈ 700 строк кода и ≈ 500 строк тестов,
   написан за ночь по памяти + день живой проверки; адаптер Яндекса
   (Диск + Вики + OAuth) ≈ 830 строк; модуль поверх готового клиента
   (например, «База знаний 2.0» Битрикс24) ≈ 150 строк. Оценки — за
   адаптер с тестами и живой проверкой, **без** фронта и без ожидания
   тестового доступа.

### 1.2. Метки достоверности

- **[П]** — проверено: страница документации API или первоисточник
  открыт 09.10.2026, факт взят оттуда.
- **[В]** — по пересказу в поисковой выдаче или во вторичном источнике;
  первоисточник не открыт.
- **[Пр]** — предположение (по аналогии, по памяти, по названию метода);
  проверять на живой системе.

### 1.3. Что ограничивает все кандидаты одинаково

- Ингест принимает `.docx .pdf .txt .md .xlsx .pptx .doc`
  (`ingest/extract.py`). **`.odt/.ods` (ODF) нет** — это важно для
  МойОфис, Р7 и Nextcloud/ownCloud, где ODF встречается чаще. Без
  поддержки ODF часть документов этих систем будет пропущена (ядро их
  посчитает как «неподдерживаемый формат»).
- Нативные документы облачных редакторов (Google Docs, документы Kaiten в
  ProseMirror JSON) требуют экспорта/конвертации — это входит в оценки.

## 4. Кандидаты подробно

### 4.1. Битрикс24 коробочный — волна 1, S

1. **Спрос.** 49 % компаний, использующих CRM, называют основной
   Битрикс24 (J'son & Partners, прошлое исследование). Разбивки облако /
   коробка **нет**. Косвенно: интеграторы пишут, что компании «начинают
   с облака и переходят в коробку при новых требованиях» —
   [infostart](https://infostart.ru/pm/2777397/), мнение продавца
   миграций [В].
2. **Доступность.** Российский вендор, без ограничений.
3. **API.** Тот же REST, что у облака. Приложения коробки авторизуются
   через **тот же сервер `oauth.bitrix24.tech`**: «Коробочный Битрикс24
   … обращается к внешним сервисам Битрикс24, принимает вызовы методов
   REST от приложения»; «Сервер авторизации `oauth.bitrix24.tech` выдаёт
   и продлевает токены приложения» [П —
   [network-access](https://github.com/bitrix-tools/b24-rest-docs/blob/main/settings/cloud-and-on-premise/network-access.md),
   [oauth](https://github.com/bitrix-tools/b24-rest-docs/blob/main/settings/oauth/index.md)].
   Исключение — коробка со «своим провайдером авторизации»: тогда токены
   выдаёт сама коробка [П, там же]. Входящие вебхуки работают как в
   облаке.
4. **Права.** Как у облака: per_user/OAuth (видимость по листингу),
   ACL диска REST не отдаёт (прошлое исследование).
5. **Облако/коробка.** Коробка. По документации на стороне коробки нужны
   **«Серверы приложений — входящие https — вызовы методов REST от
   приложения»** [П]. То есть портал обязан быть доступен нашему облаку
   по HTTPS — это и есть условие подключения. Ограничение среды
   разработки: коробка, закрытая фаерволом, — не наш клиент на «Базовом».
6. **Трудозатраты: S.** Адаптер и OAuth уже есть. Поле `portal` в
   `bitrix24/adapter.py` проверяется только как `url_field` (SSRF),
   **домен не ограничен `*.bitrix24.ru`** — то есть коробочный портал,
   скорее всего, подключается уже сейчас тем же видом [Пр — не
   проверено живьём]. Работа: живая проверка на коробке (вебхук и
   OAuth), подсказка в форме («портал должен быть доступен из
   интернета»), ветка «свой провайдер авторизации» (токены выдаёт сам
   портал). Делать **опцией существующего вида**, а не новым — ≤1–2 дня.
7. **Тест.** Пробная коробочная версия у 1С-Битрикс (на своём сервере,
   нужен публичный адрес) [Пр]; официального Docker-образа нет [Пр],
   есть «Битрикс24 в Яндекс Облаке»
   ([маркетплейс](https://yandex.cloud/ru/marketplace/products/yc/bitrix-app)) [В].

### 4.2. Google Drive (Документы, Таблицы, общие диски) — волна 1, M

1. **Спрос.** Прямых чисел по РФ нет. Косвенно: 16 % перешедших на
   Яндекс 360 раньше работали с Google Workspace (TelecomDaily, 2025)
   [П]; в 2023 писали, что «около 30 % корпоративной информации
   российских компаний хранится на серверах Google» [В — пересказ в
   [securitylab](https://www.securitylab.ru/news/540843.php), метод не
   указан]. Малые компании часто работают в личных Google-аккаунтах
   сотрудников [Пр].
2. **Доступность.** Сервисы работают; прямые платежи российскими картами
   невозможны, новый платный аккаунт из РФ открыть нельзя, продление —
   через зарубежную карту или посредника [В —
   [vc.ru](https://vc.ru/services/3070120-oplata-google-workspace-iz-rossii),
   источники — сами посредники]. В августе 2023 Google блокировал
   Workspace компаниям под санкциями
   ([CNews](https://www.cnews.ru/news/top/2023-08-11_v_rossii_nachalas_blokirovka)) [В].
   **Риск:** клиент может потерять доступ в любой момент — коннектор
   должен переживать это как обычный `AdapterAuthError`.
3. **API.** Drive API v3 — зрелый. `permissions.list`: `type` = user /
   group / domain / anyone, `emailAddress`, `role`,
   `permissionDetails[].inherited` [П —
   [permissions](https://developers.google.com/workspace/drive/api/reference/rest/v3/permissions)].
   Лимиты: 1 000 000 единиц квоты в минуту на проект и 325 000 на
   пользователя; чтение — 5 единиц, листинг — 100; превышение → 403,
   экспоненциальная пауза [П —
   [limits](https://developers.google.com/workspace/drive/api/guides/limits)].
   Google Docs/Sheets скачиваются экспортом в .docx/.xlsx (`files.export`)
   [Пр — стандартный метод, страница не открывалась].
   **Главное ограничение:** `drive` и `drive.readonly` — **restricted
   scopes**: публичному приложению нужны «restricted scope OAuth App
   Verification» и, если данные хранятся на сервере, **security
   assessment** [П —
   [api-specific-auth](https://developers.google.com/workspace/drive/api/guides/api-specific-auth)].
   Для российского разработчика это внешняя зависимость с неясным
   исходом [Пр].
4. **Права.** Лучший вариант — **org**: ACL с почтой и группами,
   наследование помечено. Для общих дисков — `useDomainAdminAccess`
   (админ домена) [П —
   [manage-sharing](https://developers.google.com/workspace/drive/api/guides/manage-sharing)].
   Обход верификации [Пр]: (а) domain-wide delegation сервисного аккаунта
   — админ Workspace сам выдаёт доступ нашему client ID; (б) **клиент
   создаёт свой OAuth-клиент типа «Internal»** в своём Google Cloud и
   отдаёт нам client_id/secret — ровно модель `app_credential_fields`,
   как у локального приложения Битрикс24. Оба пути требуют платного
   Workspace; для личных Gmail остаётся per_user/OAuth в тестовом
   режиме (до 100 пользователей [Пр]).
5. **Облако.**
6. **Трудозатраты: M** для org через сервисный аккаунт или «Internal»
   клиента (листинг, экспорт, ACL с наследованием, группы через Admin
   SDK Directory [Пр]); **L**, если идти в публичную верификацию.
   Google Таблицы и Документы входят сюда же — отдельный коннектор не
   нужен.
7. **Тест.** Бесплатный личный аккаунт Google + проект в Google Cloud,
   OAuth-клиент в режиме «Testing». Для domain-wide delegation нужен
   Workspace (пробный период требует оплаты не из РФ [Пр]).

### 4.4. WebDAV-основа и Nextcloud (ownCloud) — волна 1, M + S

1. **Спрос.** Чисел по РФ нет ни для Nextcloud, ни для ownCloud.
   Аргумент за — **один протокол покрывает несколько систем**: Nextcloud,
   ownCloud, Диск VK WorkSpace (WebDAV `https://webdav.cloud.<домен>`
   [П — [VK WorkSpace](https://workspace.vk.ru/docs/on-premises/disk/webdav-access/)]),

   [Пр]).
2. **Доступность.** Свой сервер — да.
3. **API.** WebDAV `PROPFIND` (листинг, `getetag`, `getlastmodified`) +
   `GET`. Nextcloud дополнительно: OCS Share API
   `GET /ocs/v2.php/apps/files_sharing/api/v1/shares` с `path`,
   `reshares`, `subfiles`; обязателен заголовок `OCS-APIRequest: true`
   [П — [OCS Share API](https://docs.nextcloud.com/server/latest/developer_manual/client_apis/OCS/ocs-share-api.html)].
   Метод описан как «Get all shares **from** the user» — шары, которые
   **создал** пользователь токена; параметр «расшарено мне», поля ответа
   (`share_with` и т. п.) и админский «все шары компании» на странице
   **не описаны** [П — отсутствие]. Типы 0 — пользователь, 1 — группа,
   3 — ссылка, 4 — e-mail, 6 — федеративный, 7 — круг, 10 — Talk указаны
   для аргумента `shareType` при **создании** шары [П]. Вывод: org-режим
   потребовал бы токен каждого владельца — то есть по сути тот же
   per_user.

   в настройках безопасности, эндпоинты `/apps/oauth2/authorize` и
   `/apps/oauth2/api/v1/token`, токен Bearer, **без scope — полный доступ
   к аккаунту** [П —
   [admin manual](https://docs.nextcloud.com/server/latest/admin_manual/configuration_server/oauth2.html)].
   Срок жизни токена и работа с WebDAV на странице не указаны [П].
   Лимитов как у SaaS нет — только защита от перебора [Пр].
4. **Права.** per_user/OAuth (Nextcloud) или per_user/токен (пароль
   приложения — ownCloud, VK WorkSpace, Облако Mail.ru): документ виден
   сотруднику, если есть в его листинге. Это ровно модель Битрикс24 —
   ядро уже умеет.
5. **Коробка**, обычно опубликована (мобильные и десктопные клиенты
   ходят снаружи) [Пр].
6. **Трудозатраты.** WebDAV-основа — **M** (PROPFIND-парсер, глубина,
   кодировки путей, `etag`, ограничение размера, общие папки как
   «смонтированные» каталоги). Модуль Nextcloud с OAuth — **S**. Каждый
   следующий продукт на WebDAV — **S** (адрес, вид учётных данных,
   особенности путей).
7. **Тест.** Docker `nextcloud` (официальный образ) за любым публичным
   HTTPS; ownCloud — Docker `owncloud/server` [Пр].

  **SharePoint Server** в коробке (у крупных) — тот же REST, но внутри
  сети [Пр].

  поля ответа на странице не описаны. Авторизация — токен по логину и

  прав проектов + уровни безопасности задач, считать дорого — **L** [Пр].

- **Minerva Knowledge:** облако 500 ₽/польз. и коробка
  ([sostav](https://www.sostav.ru/blogs/286486/74971)) [В]; документации
  API не найдено. Ориентирована на контакт-центры и крупные компании [В].
- **СЭД.** ELMA365: Web API `https://{company}.elma365.ru/pub/v1`,

## 5. Предложение «базового пула» в три волны

Правило: волны 1–2 — `KindSpec.base=True` (доступны во всех тарифах,
считаются в лимит 5 на «Базовом»); волна 3 — по умолчанию `base=False`
(«Корпоративный»), кроме self-hosted вики, которые можно открыть в
базовом, если клиент даёт публичный адрес.

### Волна 1 — делать сразу (≈ 2–2,5 недели)

| Что | Оценка | Почему сейчас |
|---|---|---|
| Битрикс24 коробочный (опцией существующего вида) | S | 49 % CRM-рынка — Битрикс24; код и OAuth уже есть; условие «портал доступен из интернета» проверяемо |
| Google Drive (+Документы, Таблицы) | M | лучший API прав с почтой (org); закрывает «Google Таблицы»; риск блокировок принимаем — адаптер падает как обычная ошибка авторизации. Идти через OAuth-клиент клиента («Internal») или domain-wide delegation, **не** через публичную верификацию. **Условие:** производственный режим — только для компаний с платным Google Workspace; личные Gmail не поддерживаем (без верификации — только тестовый режим с ограничением числа пользователей). Если опросник пилотов покажет, что у клиентов в основном личные Gmail, — Google уходит в волну 2, а Kaiten поднимается в волну 1 |
| Публичный сайт / справочный центр | S–M | есть у каждого; без прав; ядро очистки HTML готово. Предложение: не считать в лимит 5 |
| WebDAV-основа + Nextcloud | M + S | один протокол → Nextcloud, ownCloud, затем VK WorkSpace и Облако Mail.ru за S каждый; режим per_user, как у Битрикс24 |

### Волна 2 — следом (≈ 2–3 недели)

| Что | Оценка | Условие |
|---|---|---|
| Яндекс Трекер — модулем коннектора Яндекса | S–M | не тратит лимит подключений |
| Диск VK WorkSpace, Облако Mail.ru — модули WebDAV | S + S | после живой проверки WebDAV облачного VK WorkSpace |
| Kaiten (документы) | M | per_user по личному токену; конвертер ProseMirror |
| TEAMLY | M–L | **только после** получения документации API от вендора |
| Outline / Yonote | M (+S) | если пилоты попросят; иначе в волну 3 |

### Волна 3 — потом или только «Корпоративный»

- Потом, базовые при публичном адресе: BookStack, Wiki.js, Seafile,
  DokuWiki, MediaWiki, GitLab-вики, amoCRM (файлы, ⚠ права).
- Только «Корпоративный»: Microsoft 365 / SharePoint (Online и Server),
  Р7 Корпоративный сервер, Jira DC, Minerva, СЭД (1С:ДО, ELMA365,
  Directum RX, Тезис), сетевые папки (агент).

**Почему такой порядок.** Числа есть только для Битрикс24, Яндекса,
Microsoft 365, amoCRM, 1С и Atlassian — первые два уже сделаны,
Microsoft недоступен для новых клиентов, 1С — учёт, а не документы. Поэтому
волна 1 выбрана не «по долям рынка», которых нет, а по **покрытию на
единицу труда**: коробка Битрикс24 — почти даром; Google — самый
зрелый API прав и частый «старый» источник у малых компаний; сайт —
у всех; WebDAV — одна основа на 4–5 систем. Волна 2 — российские SaaS,
где права либо частичные, либо API не документирован, поэтому сначала
нужен тестовый доступ.

## 7. Что проверить до решений

1. **Битрикс24 коробочный:** живая проверка существующего вида на
   коробке (домен в коде не ограничен); как выглядит ветка «свой
   провайдер авторизации».
2. **Google:** реально ли клиенту без платного Workspace (личные Gmail)
   подключиться в тестовом режиме OAuth; работает ли domain-wide
   delegation без верификации приложения [Пр].
3. **VK WorkSpace (облако):** адрес и вход WebDAV — документация найдена
   только для коробки.
4. **TEAMLY:** запросить документацию API; ключевой вопрос — отдаёт ли
   API участников пространств и права статей.
5. **Kaiten:** есть ли способ узнать, кто приглашён в документ `by_invite`
   (группы — `group-entities`, люди — ?).
6. **Nextcloud:** работает ли OAuth-токен для WebDAV (страница не
   говорит); срок жизни токена.
7. **ODF (.odt/.ods):** добавлять ли в ингест до WebDAV/Р7 — иначе часть
   файлов Nextcloud и Р7 будет пропускаться.
8. **Опросник пилотов:** вопрос «где лежат документы» теперь должен
   содержать варианты из волн 1–2, чтобы проверить порядок на живых
   клиентах — открытых чисел по сегменту 30–250 нет.
