# Набор для глобальной проверки коннекторов

Одна вымышленная компания — ООО «Северный ветер», ~120 сотрудников, шесть
подразделений (кадры, бухгалтерия, продажи, ИТ, юристы, руководство) — и
её 61 документ лежат во всех системах. Сценарий проверяет полный путь
каждой системы через ядро kronto: документы появились, каждый сотрудник
видит ровно положенное, правка, удаление, отзыв доступа и перенос в
закрытую папку доходят до kronto. **Качество ответов ассистента не
проверяется** — это зона ML (`src/corp_ed/ingest`, `prompts`, `llm` набор не
трогает).

Всё вымышленное: имена, почты (`@severny-veter.test`), реквизиты, суммы.
Совпадения случайны.

## Что здесь

| Что | Где |
|---|---|

| Манифест: сотрудники, зоны, документы, системы, шаги | `manifest.toml` |

| Что делать владельцу для облаков | `OWNER-CHECKLIST.md` |

### Корпус

Документы — регламенты, положения, инструкции, протоколы, прайс-листы,
типовой договор, вопросы и ответы отделов, приказы. В каждом первой строкой
после заголовка — **шифр** (`Шифр документа: SV-HR-003`): по нему сценарий
узнаёт документ в kronto, не полагаясь на название и путь, которые разные
системы оформляют по-разному.

- **Закрытые** зоны: зарплаты (`payroll`: ведомость, положение об оплате
  труда, протокол по окладам — только расчётная группа), приказы о премиях
  (`awards` — руководители отделов и расчётная группа), юридические споры
  (`disputes` — юристы и директор).
- **Противоречия** — раздел `[[conflicts]]` манифеста: срок заявления на
  отпуск (14 / 7 / 10 дней), режим работы (2025 и 2023), суточные (1 500 /
  1 200 / 1 800 ₽) и срок авансового отчёта, начало ДМС (3 или 6 месяцев),
  цена ВГ-1500 (189 000 / 172 000 / 185 000 ₽), срок оплаты по договору
  (30 или 45 дней), длина пароля (10 или 12). Тест `test_manifest.py`
  держит каждый факт в исходниках.
- **Форматы.** md — 24 документа, остальные — docx, xlsx, pptx, pdf, txt.
  Генератор не берёт ничего, кроме того, что уже есть в проекте: в
  зависимостях нет python-docx, openpyxl, python-pptx, reportlab, поэтому
  OOXML собирается стандартным `zipfile` (как в `tests/ingest/*_samples.py`),
  PDF — строками в формате. Форматы читаются продуктовым разбором
  (`corp_ed.ingest`) — это проверяет `test_corpus_build.py` для каждого
  документа в каждом формате. Оговорка по PDF: шрифт с кириллицей не
  встроен (нет библиотеки), буквы заданы кодировкой с именами глифов;
  текст из файла извлекается верно, а нарисует его просмотрщик шрифтом-
  заменителем — вид на экране может отличаться.
- Справочник всех 120 сотрудников — `python -m tests.acceptance.corpus.build
  ПАПКА` (файл `staff.xlsx`); в манифесте — 18 человек с учётными
  записями в системах (по 3–4 из отдела).

### Манифест

TOML (разбирается стандартной библиотекой). Разделы: `[company]`,
`[departments]`, `[[employees]]` (логин, почта, отдел, группы), `[zones.*]`
(кто читает зону: `all`, `dept:…`, `group:…`, `login:…`), `[[documents]]`
(файл исходника, зона, формат, подпапка), `[bundles]` (наборы документов),
`[systems.*]` (что в какой системе лежит), `[[steps]]` (изменения).

**Кто должен и кто не должен видеть документ.** Документ наследует права
зоны. Должны — читатели зоны (`readers`), не должны — все остальные
сотрудники с учётной записью в системе: сценарий считает это сам и
проверяет обе стороны. Зона — это папка (книга, пространство, коллекция)
со своими правами в системе; `python -m tests.acceptance.run --plan
--system nextcloud` печатает, что куда кладётся и кто видит.

**Шаги изменений** (после каждого — синхронизация и сверка):

| Шаг | Что делается | Что ожидается в kronto |
|---|---|---|
| `edit` | в три документа дописывается абзац с меткой `ПРАВКА-N` (в том числе в закрытый) | `updated` не меньше числа правок; метка в тексте; права прежние |
| `delete` | удаляются архивный документ и документ из закрытой зоны споров | `removed` не меньше числа удалений; материалов больше нет |
| `revoke` | `petrenko` убрана из зоны зарплат; `lebedeva` лишена всех доступов | они больше не видят закрытое (только эту зону — остальные зоны у `petrenko` остались), у `lebedeva` пусто |
| `move` | прайс 2025 уходит в зону руководства, памятка о ДМС — в зону кадров | документ виден только читателям новой зоны |

## Как запускать

Нужны Postgres (отдельная тестовая база: `ACCEPTANCE_DATABASE_URL`, иначе
`TEST_DATABASE_URL`) и, для Docker-стендов, Docker. Сценарий идёт в этом же
процессе, API не нужен: заводит в базе новую компанию (код `acc-…`) и
сотрудников, подключение вида с учётными данными, гоняет
`ConnectorSyncService` и сверяет. Прошлые запуски (компании `acc-…`)
перед каждой системой убираются вместе с учётками сотрудников: почта в
kronto уникальна, а у приёмки она одна и та же. База должна быть тестовой.

```bash
export PYTHONPATH="$PWD/src:$PWD"
export ACCEPTANCE_DATABASE_URL=postgresql+asyncpg://corp_ed:postgres@localhost:5432/<тестовая_база>

python -m tests.acceptance.stand up bookstack                  # порт 8520
python -m tests.acceptance.run --system bookstack --seed --json out.json
python -m tests.acceptance.stand down bookstack
```

`--seed` раскладывает корпус и права по манифесту в чистый стенд и пишет
его учётные данные в `~/.kronto-acc/credentials.json` (0600; вне
репозитория). Дальше `run` без `--seed` проверяет уже засеянную систему.
Для облака `--seed` не нужен: учётные данные кладёт владелец, документы
раскладывает он же (`OWNER-CHECKLIST.md`).

Ключи запуска: `--system X [Y …]` (идентификатор системы из манифеста,
вид, `docker`, `cloud` или `all`), `--credentials ФАЙЛ`, `--steps
sync,resync,edit,…`, `--json ФАЙЛ`, `--list` (что готово), `--plan`,
`--reset-db`. Код выхода 1 — есть `fail`.

Итог — таблица «система × шаг» в stdout и JSON:

```
система    sync     resync   edit     delete   revoke   move
bookstack  ok       ok       ok       ok       ok       ok
```

- `ok` — совпало с манифестом.
- `fail` — расхождение; под таблицей подробности: `нет документа …`,
  `УТЕЧКА: <логин> видит <шифр>, а не должен`, `<логин> не видит <шифр>, а
  должен`, `правка … не дошла`, статус синхронизации.
- `skip` — шаг не выполнялся, причина — в подробностях: нет учётных данных,
  драйвер не умеет операцию, начальная синхронизация не прошла.

Столбцы: `sync` — первая синхронизация (документы появились, права
верны), `resync` — повторная без изменений (ничего не скачано заново),
дальше шаги манифеста.

**Как считается видимость.** По правилу ядра `visible_to` из
`chunk_repository.py` — тому же, что у поиска ассистента, а не по сырым
записям доступа. Все проверяемые сотрудники в kronto — `EMPLOYEE` (у
администратора kronto свои права). В JSON у каждого шага есть
`checked_visible` и `checked_hidden` — сколько пар «сотрудник — документ»
проверено; нули означали бы пустую проверку.

**Самопроверка сценария.** `test_scenario.py` прогоняет весь сценарий на
поддельной системе (`fake.py`) без Docker и убеждается, что сценарий
замечает утечку закрытого документа и отзыв доступа, не дошедший до
источника.

## Учётные данные

Файл `~/.kronto-acc/credentials.json` (или `--credentials`,
`ACC_CREDENTIALS`): ключ — идентификатор системы; поля `config` (адрес…),
`organization` (учётные данные организации), `app` (секрет приложения),
`users.<логин>` (учётные данные сотрудника: пароль приложения, токен,
OAuth-токены) и `extra` (`url` стенда, `email_domain` для облака). Те же
поля — переменными: `ACC_<СИСТЕМА>_<ПОЛЕ>` и
`ACC_<СИСТЕМА>_<ЛОГИН>_<ПОЛЕ>` (верхний регистр), переменные перекрывают
файл. Для per_user-видов нужны данные каждого сотрудника: без них
сотрудник из проверки исключается. OAuth-токены сотрудников получает
`oauth_login.py`.

## Системы

| Система | Режим | Стенд Docker | Засев и шаги | Облако |
|---|---|---|---|---|
| bookstack | organization | порт 8520 | да | — |
| nextcloud | per_user | порт 8521 | да | — |
| owncloud | per_user | порт 8522 | да (та же логика, что у Nextcloud) | — |
| dokuwiki | organization | порт 8529 | да | — |
| seafile, webdav, outline, confluence_dc, wikijs, mediawiki | см. ниже | нет (в наборе нет засева) | нет | — |
| bitrix24, yandex360, gdrive, vk_workspace_disk, mailru_cloud, kaiten, yonote, outline_cloud, amocrm, elma365, m365 | см. манифест | — | проверяют разложенное; шаги — `skip` | `OWNER-CHECKLIST.md` |

Системы без засева в наборе пока не умеют раскладывать корпус: у них
готовы стенды `tests/live/<вид>/` со своим небольшим составом
сотрудников, а засев по манифесту (18 сотрудников, 10 зон) не написан.
Запись в манифесте у них есть — драйвер по умолчанию проверит уже
разложенное, если дать ему учётные данные.
